Prince of Persia on the PicoComputer 3

What it would actually take to bring Jordan Mechner’s 1989 Apple II Prince of Persia to the PC3 in MMBasic, measured against the released source rather than guessed at: what the original is, what the PicoMite gives us, what has to be transcribed, what can be deleted, and the one constraint that is not technical at all.

Every number in this document was measured from the released repository — the 6502 sources, the sixteen image tables and the fifteen level files — not taken from secondary accounts.

The argument

The most comfortable frame budget of any port so far, attached to the largest body of code

Prince of Persia is not a performance problem. It is a transcription problem, and an unusually well-posed one, because what was released is the actual source — labelled, commented, and structured into named modules — not a reverse-engineered disassembly. Against that, it is the biggest body of game logic we have looked at: roughly 20,000 lines of 6502 across 29 files, of which about 12,000 lines are game behaviour that has to come across.

The decisive number is in the game’s own timekeeping. SPECIALK.S defines a game minute as 725 frames and its author annotated the constant with a note that the actual frame rate is approximately eleven a second. That is 83 milliseconds a frame. Thrust had 30 ms and Exile 40 ms. We have more than twice Exile’s budget for a game that, once the Apple II’s memory-banking and disk machinery is stripped out, does considerably less per frame than Exile does.

The renderer is cheap, because the PicoMite already has the primitive the original spends a third of its code emulating. Prince of Persia’s HIRES.S is 1,293 lines of shift tables, carry bytes, five opacity modes and a “peel” buffer, all of it there to move a masked bitmap across a screen whose bytes hold seven pixels apiece. BLIT FLASH with a transparent colour does the same job in one call, and the RAM image slots added in b11 hold every image the game owns with room to spare.

The risk is not the frame rate and not the memory. It is volume, it is the music that was never released with the source, and it is the discipline needed to keep the game’s own content out of the thing we hand people.

In one line

Technically the easiest of the four ports we have scoped, and by a wide margin the longest. It ships as an engine that reads data the player converts for themselves, which is settled in the next section and shapes the build from the first line written.

Settled — and it shapes the build

We ship the engine. The player converts the data.

Mechner’s README is unusually direct and is worth taking at face value rather than as boilerplate. He released the code as a historical artifact, says he has no objection to anyone studying, modifying or running it, and then states plainly that this grants no rights to Prince of Persia itself, and that Ubisoft alone has the right to make and distribute Prince of Persia games.

Those two halves point in different directions, and the port is built to sit on the permissive one. What we write is a translation of published code into another language, which is a modification, and modification is invited. What we must never hand anyone is the game’s content. So the deliverable is an engine plus a converter, and the content reaches a player only by their own hand, from their own copy of the published repository.

This is the model ScummVM, OpenRCT2, DevilutionX and CorsixTH have all run on for years. It is also a pattern this repository already uses: the Exile census harness takes a path to Jon Saffron’s world generator rather than vendoring it, and the generator is in .gitignore precisely so it cannot be shipped by accident.

The rule that makes it work

Nothing that is data in the original may become text in the program. Not the 415 frame definitions, not the 114 animation sequences, not the 15 level blueprints, not one image. The obvious build would paste those tables into the .bas as arrays, and that would put the game’s content straight back into the thing we distribute. Every one of them is a converter output, written to a data file beside the artwork, loaded at run time.

The program that ships therefore contains the interpreter, the renderer and the game logic, and no game data at all. It does nothing until a player points it at their own converted files. This is the same discipline the 144 KB program limit already demands, so it costs nothing to adopt and it is worth adopting for both reasons at once.

Three conditions

The converter takes a path

It reads the player’s own clone of the published repository, named on the command line. No vendored assets, no bundled sample data, and no built-in download. Fetching the files on the player’s behalf is the one thing that would turn a tool into a distribution channel.

A neutral name

The trademark is the real exposure, not the code: it is live, it has products shipping now, and it is what triggers takedown requests in practice. It is also the cheapest thing to fix, and the Picanoid rename is the precedent. The engine is named for what it is and says factually which data it reads.

No charge, no bundle

Free, and never pre-installed on hardware that is sold. Non-commercial status is most of what keeps this model unchallenged, and there is nothing to gain by testing it.

Two things this does not claim. It is not legal advice, and the residual risk is a takedown request rather than damages. Set against the earlier ports, though, the position is better on the axis that matters most: Thrust and Exile were built on disassemblies carrying no licence at all, where this carries an explicit invitation to modify the code. It is the name, and only the name, where this one sits worse.

The animation system is the game

Everything that makes Prince of Persia feel like Prince of Persia lives in two tables and an interpreter, and all three are small. FRAMEDEF.S holds 415 frame definitions in five bytes each: the image to draw, which sword image goes with it, how far the character moves in x and y that frame, and a packed collision descriptor. SEQTABLE.S holds 114 named sequences — the run cycle, the hanging drop, the block-to-strike, the stair climb — written in a byte code of fifteen instructions that can jump, turn the character round, change floor level, alter x or y, set the action class, trigger a fall, test weightlessness, kill, and advance the level.

That is a virtual machine, and porting a virtual machine is the most reliable kind of transcription there is: the interpreter is perhaps 150 lines of MMBasic, and the sequences themselves are data that a Python script converts once and never touches again. Get the interpreter exactly right and every movement in the game is exactly right, including the ones nobody can describe in words.

The world is a blueprint, not a bitmap

A level is 24 screens of 30 blocks, ten across and three down. Each block carries a type from a list of 30 — floor, spikes, gate, loose floor, pressure plate, torch, mirror, exit, slicer — and a one-byte modifier. Alongside that sits a link table saying which screen lies left, right, above and below each screen, a 96-byte map, and 256 bytes of starting information: where the Kid begins, which way he faces, where the sword lies, and the block, facing, position and behaviour program for each of up to 24 guards.

The whole thing is 2,304 bytes, and the layout in the released equates accounts for all of it with nothing left over. That is a format you can trust without a single guess, which is not something we have had before. Across the fifteen levels only 28 of the 30 block types are ever used, and 42 guards are placed in the entire game.

A block draws in five pieces

The reason the original’s renderer is more complicated than it looks is that a block is not one image. It is up to five, drawn in a fixed order: a back section, a middle section, a front-of-middle section, a floor section, and a foreground piece that draws over the character. Each has its own image number, its own vertical offset, and in two cases its own mask. This is how a character walks behind a pillar and in front of the back wall on a machine with no sprite priority hardware, and it has to be reproduced exactly or the depth reads wrong. A block’s appearance also depends on the block to its left and the row below, which is why the draw loop carries the preceding block’s identity forward.

Evidence

The measurements that shape the port

957 images, 671,083 pixels

Sixteen image tables parse cleanly against the format documented in HIRES.S: a pointer table indexed from one, then each image as a width in bytes, a height in lines, and packed rows. No compression, no surprises. One level’s working set is 468 of them.

The artwork is effectively one bit a pixel

The Apple’s palette-select bit is set on 100.0% of image bytes in every table. There is no per-byte palette decision to carry across. A pixel is on or off, and its colour follows from its position: black, white, blue and orange, four of MODE 2’s sixteen.

Every character image faces left

The frame tables note it explicitly, and the right-facing half of the game is produced by a mirror bit in the opacity byte. BLIT FLASH has no mirror. Pre-mirroring the 290 character images at build time costs 117 KB and removes the problem entirely.

83 milliseconds a frame

725 frames to a game minute, sixty game minutes to a game: 43,500 frames, 12.08 a second. The Apple never locked to the display at all — the rate was whatever the redraw cost, and the clock was calibrated to the average.

One opponent at a time

The blueprint reserves 24 guard slots a level and the busiest level uses six, but the engine tracks a single opponent. The per-frame character load is the Kid, at most one opponent, and the occasional mouse or falling debris.

Twenty sound effects, sixteen tunes, none of them portable

The effects are speaker-toggle routines with hand-counted delays — they describe a waveform, not a note, and cannot be transcribed. The music player is in the support tree; the songs it plays are not in the repository at all.

Design

Architecture for the port

Redraw everything, every frame

The largest single file in the game exists to avoid work we no longer need to avoid. FRAMEADV.S maintains eight redraw buffers, tracks which of the 30 blocks changed, saves the background behind each character before drawing it and peels it off afterwards — all so the Apple did not have to repaint 8 KB at 1 MHz. With 83 ms and a framebuffer, the port clears the F buffer, walks the 30 blocks drawing their five sections in order, draws the characters, draws the foreground pieces over them, draws the meters, and copies. The peel machinery, the redraw buffers and the dirty-block bookkeeping all go.

What must survive from that file is the order, not the optimisation: the plane model of background, middle, objects, foreground and messages, and the rule that a block’s appearance depends on its neighbours. Those are correctness, not speed.

Measured on the board, not inferred. The background pieces turn out to be small: 178 of them across the two dungeon tables, median 21 by 12 pixels, largest 112 by 64. A frame of 150 BLIT FLASH calls at the median size costs 6.0 ms of drawing, and 14.3 ms including the BASIC loop that issues them and the present. At the largest size the game owns, 150 calls cost 14.6 ms of drawing and 22.9 ms all in. The framebuffer copy is 0.09 ms.

So a typical frame spends 14 ms of its 83, and the pathological frame 23. Two things make those figures conservative: the board was at 315 MHz rather than the 378 the plan recommends, and the 150 blits are an upper bound, since many blocks leave several of their five sections empty. The renderer is settled, and the interesting result is the one underneath it — more than half the cost is the interpreter issuing the calls, not the drawing. That is where the frame budget will actually go, and it is an argument for keeping the per-block loop lean rather than for worrying about blit sizes.

Twelve frames a second, exactly

At 378 MHz the PC3 runs 640×480 at 60 Hz, and presenting one frame in five gives exactly 12.000 fps against the original’s 12.083. A sixty-minute game would run about twenty-five seconds long, which nobody can perceive and which keeps the interpreter at its fastest clock. The alternative — 315 MHz for a 75 Hz display — divides to 12.5, which is further out and costs interpreter speed.

As with Thrust and Arkanoid, the per-frame constants are integers and must not be rescaled. The sequence byte code moves a character by whole pixels per frame; the timers count frames. Change the tick rate and every one of them is wrong together, which is the failure mode that is hardest to see because nothing looks broken — the game just plays wrong.

Artwork in PSRAM image slots

The b11 RAM image slots land exactly where this port needs them. Everything the game owns, both facings pre-mirrored, is 571 KB — four of the five PSRAM slots, leaving the three flash slots free and the library slot untouched. Nothing needs loading between levels, which deletes the whole of the original’s set-management logic and the disk track tables that feed it.

Slots are volatile, so the installer writes them once per run from a bitmap on the A: drive, the same pattern Arkanoid uses. A 320×240 image loads into a RAM slot in 28 ms, so a cold start costs well under a second.

One pixel grid, no scaling

280×192 centred in 320×240 is the authentic grid at 1:1. The 20-pixel side borders and 24-pixel top and bottom are roughly what an Apple II displayed into an overscanned television. Resist the temptation to stretch it: the artwork was drawn for pixels of this shape, and MODE 2 pixels on the PC3 are close enough to the Apple’s that the proportions come out right by doing nothing.

Pipeline

Getting the data across

Four converters, all offline Python, all validated before a line of game logic is written. This is the pattern that worked for Thrust, Exile and Arkanoid and there is no reason to depart from it.

One rule governs all four, and it comes from the distribution decision rather than from engineering: a converter writes a data file, never a line of BASIC. The temptation with the smaller tables is to emit them as DATA statements and paste them into the program, which is how the earlier ports handled tables of this size. Here that would carry the game’s content into the file we distribute. Everything below lands on the player’s drive as its own file, produced on their machine, from their copy of the published repository, named to the converter on the command line.

The program-size cap points the same way, so nothing is given up. What does change is the loader: the engine reads four files at startup rather than carrying three of them in its own text, and it must fail clearly and kindly when they are not there, because a player who has not run the converter yet is the normal first-run case rather than an error.

1Images

Image tables to one RGB121 sheet per slot

Walk the pointer table, decode each image from its width and height header, expand the packed rows applying the Apple colour rule, emit both facings for character tables, and pack the lot into sheets with an index. The output is a bitmap per slot plus an index file giving every image its origin, width and height, read at startup like the rest.

Validation: render a known frame and compare against an emulator screenshot pixel for pixel, as the Exile sprite sheet was validated.

2Levels

Fifteen blueprints to one data file

The layout is fully documented in the equates and the files match it exactly. Emit all fifteen as a single file read with MEMORY INPUT into an integer array at startup — 34,560 bytes, trivial on a machine with 6 MB of PSRAM free.

3Frames

Frame definitions to a table file

415 rows of five bytes, plus the two alternate sets that re-point the same poses at the opponent’s image table. The packed collision descriptor should be unpacked into its fields once, at conversion time, rather than masked at runtime in the interpreter. Read into an integer array at startup, not embedded.

4Sequences

Byte code to byte code

The 114 sequences assemble into a byte stream with absolute addresses for the jumps. The converter resolves the labels to array indices and emits the same stream with the same semantics. The MMBasic interpreter for it is a SELECT CASE over fifteen opcodes.

This is the highest-value converter in the set and the one to write first, because the interpreter can be exercised against it long before anything is drawn.

Scope

What we delete, and what is simply missing

Deleted — about 4,400 lines of Apple II plumbing

  • The blitter (HIRES, HRTABLES, HRPARAMS, 1,560 lines). Shift tables, carry tables, mirror tables, mask tables, five opacity modes and the peel buffer. Replaced by one firmware call.
  • The bank-switching layer (GRAFIX, 1,292 lines). The game runs in auxiliary memory and reaches main memory through a jump table; every graphics call in the game is really two calls and a pair of soft-switch writes. All of it evaporates.
  • Disk everything. The custom 18-sector format, the loader, the track tables, the side-two prompts. Also the two folders of disk routines and the entire copy-protection tree, which are not game logic at all.
  • The title-screen decompressor (UNPACK, 577 lines), which unpacks double hi-res images the repository does not contain.

Missing from the release — decide what to do about each

  • The music. The player is in the support tree, credited to Kyle Freeman’s Music System II of 1986 and adapted in July 1989, and it contains no songs. The sixteen game tunes and the title music were loaded from disk tracks and are not in the repository in any form. They would have to be recovered from a disk image or re-transcribed by ear.
  • The title and cutscene screens. The attract sequence unpacks double hi-res images by address, and those images are not here either. The artist’s working files in the support tree hold a great deal of packed material but not, on inspection, the finished title screens.
  • The sound effects. Present as code, but as speaker-toggle loops with hand-counted delays. They have to be re-created as PLAY SOUND effects by ear. Thrust and Arkanoid both hit this and it was a day’s work each; twenty effects here rather than seventeen.

Worth keeping that you might not expect

The demo and attract playback in AUTO.S is a recorded input stream replayed through the normal control path. That is free once the control path works, and it doubles as the best regression test the port could have: record a run, replay it, and any divergence in the state machine shows up as the Kid walking into a wall.

Plan

Phases

0Spike

Prove the frame, settle the budget Done

Done on a b11 board. See the architecture section for the figures.

A sheet written by the converter loads into a PSRAM image slot in 40 ms and blits back pixel for pixel: every sampled point matched the pattern it was written with, so the four-bit BMP writer, the slot load and the blit path are all exact, with no vertical flip and no palette drift. A frame of 150 blits costs 14.3 ms of the 83 ms budget. The renderer is a non-issue and needs no CSUB.

Two findings worth carrying forward. More than half the frame cost is the interpreter issuing the calls rather than the drawing, so the per-block loop is what to keep lean. And the Pixel statement takes an RGB colour, not a colour index, so a test cannot learn the index mapping by drawing it; compare against the firmware's own palette table instead. That cost one wrong run.

The spike deliberately uses a generated test pattern rather than converted artwork, so it needs no game data and puts none on the board.

1Data

The four converters Done

All four run and are validated. One tool, one command.

Images, levels, frame definitions and sequences all convert. The frame table and the sequences are not binaries in the release but assembler source, so the converter carries a small two-pass assembler covering the dozen directives those two modules use. Both assemble to exactly their declared layouts: 240 frames of five bytes with the alternate sets at the stated offsets, and 114 sequences.

Every address in the sequence module is rebased to an offset at conversion time, so the engine never needs to know what address the original was assembled at. A validator then walks all 114 sequences through the fifteen opcodes, which tests the assembler, the rebasing and the operand counts together: step into the middle of an instruction and the walk runs off the end. It does not. 2,406 instructions, 1,358 frame references, no problems.

Two things caught here rather than in Phase 2. The sequence pointer table cannot be sized from its first entry, because entry one does not point at the byte after the table — another sequence is assembled in between; count the leading addresses instead. And the artwork needs four image slots, not five, once the intro-only tables are left out, which matters because the fifth RAM slot is where a library lives.

2Engine

The sequence interpreter and the frame table Done

Running on the board, and exact.

Fifteen opcodes in a SELECT CASE, driven from the converted data with no world around it. The board walks all 114 sequences and reports 2,406 instructions and 1,358 frame references, which is what the host-side walker counts from the same bytes. Exact agreement is the evidence: a wrong operand count steps into the middle of an instruction, and the totals diverge or the walk leaves the data.

The data loads through MEMORY INPUT into a packed array and then MEMORY UNPACK at eight bits, which gives one byte per array element. That is the form to keep, because the interpreter then indexes the byte code directly rather than calling a function per byte.

Cost, measured: about 139 µs per byte-code instruction, consistent with the roughly 9 µs a statement the Phase 0 loop showed and with Thrust's array-access figures. That sounds slow against an 83 ms frame until you count what a frame actually runs: the interpreter advances each character by one frame, which is a few instructions, so three active characters cost one to two milliseconds. The whole-sequence walk is a test, not a workload.

3World

Blueprint rendering and screen linking In progress

Data and drawing load settled. The on-board render is written but not yet run.

The block tables are converted and checked. A piece number under $80 names an image in the first background table and one at or above it names the second, less $80; that rule holds for every entry of every piece table, with no value falling outside its table. Thirty block types, twenty-eight of which are ever used, and a type draws at most five sections.

The drawing load is now known rather than assumed. Across all 360 screens in the game the busiest draws 120 sections and the median 86. The renderer runs on the board against converted artwork in four PSRAM slots, and a real screen of 100 sections costs 17.6 ms, so the busiest in the game is about 46 ms at 315 MHz, or 38 at the 378 the plan asks for.

That table is the whole lesson of the phase. Walking a lookup chain per section cost fifty-seven times the drawing it fed; resolving every section of every block type once at load time removed it. What remains is not indexing but argument evaluation: a blit takes nine arguments, each costs about 13 µs to evaluate, and that is three times the blit. Flattening the tables from two dimensions to one bought only eleven per cent, which says the floor is the interpreter reading arguments, not how they are stored.

The lever, if the worst screens prove too tight: compose the static sections of each block type into a single image at conversion time. Fifty-seven of the 150 possible sections are empty and only fourteen block types have a foreground piece, so a screen would fall from about 100 blits to roughly 44. The foreground piece must stay separate because it draws over the character, and animated blocks such as gates and spikes would keep their own path. This changes the converter, so it is a decision rather than a tidy-up.

One coupling removed on the way: the converter now publishes each table's number by name, because which tables are present depends on which artwork set is converted. An engine that hard-coded them drew from the wrong table and reported the wrong image count, which is exactly the kind of fault that looks like a rendering bug.

The neighbour model is the part that is easy to get wrong, and the first version had it wrong. A block's sections do not all come from that block. The floor and back sections belong to the block itself, the middle section to the block on its left, and the front-of-middle section to the block below and to the left, and they draw in that reverse order rather than the order the tables are written in. Reading all five from the block itself produces a plausible-looking screen that is quietly incorrect.

The renderer now sources each section from the right block and draws the foreground piece in a second pass, after the point where characters will go, which is what lets a character walk behind a pillar. Resolving neighbours cost about four milliseconds a frame until the screen's block types were unpacked once into a grid padded with an empty row and column, so a neighbour off the edge reads as empty with no test at all. That is the same lesson a third time: the work belongs outside the loop.

That is workable but not comfortable, and it is the argument for one of the two levers already identified: composing the static sections at conversion time, or moving the draw loop into a CSUB.

4Control

The player state machine In progress

The frame advance, the floor test, landing, the ledge grab and the moving-parts hooks are in and exact against host references. A scripted coverage pass reaches 115 of the 240 poses. Sword and guard handling are Phase 6.

Two bookkeeping errors were found late and are worth recording, because neither produced an error and both survived every visual check. Screens are numbered from one, and the blueprint's planes are laid out from screen one at offset zero: the engine indexed them by the screen number itself, so every room was read one screen along while the map of neighbours was read correctly. He fell out of one room into a room that was not below it, and the scenarios had been sited against rooms that did not exist. The second: the jaru instruction takes no operand. The sequence walk could not tell, because jaru,79 parses either way, and reading it as an operand silently dropped the touch-ceiling pose. The dispatcher in COLL.S is the only authority on operand counts; the sequences are not.

The foundation is in and verified: the character record, and the frame advance that turns a sequence into movement. One advance runs the byte code until it reaches a frame number, updating the character on the way, and that frame becomes the pose. Every sequence was run for twenty-four frames on the board and the resulting states checksummed: 2,736 advances, nothing stalled, and the checksum matches the host reference exactly.

One distinction is worth stating because getting it wrong would be invisible and everywhere. The chx and chy instructions move the character, and only chx is adjusted for which way he faces. The frame table's own displacements are drawing offsets, applied when the sprite is positioned and never to the character's position. Treating them as movement would make everything drift, in a way that looks like bad physics rather than a bookkeeping error.

Facing is minus one for left, which is how every character image is drawn, and zero for right, which is mirrored. Moving forward while facing left decreases x. Cost is 587 µs an advance, which is a few byte-code instructions at the rate Phase 2 measured; a frame advances each character once, so three characters cost under two milliseconds.

The input layer is done, and it is worth copying exactly rather than inventing. The original tracks three axes and, separately, a "fresh press" flag for each direction and the button. A flag goes negative on the frame a press appears and is set once something acts on it, so one press cannot be consumed twice. Holding a key is a different input from pressing it, and several states depend on the difference: standing still and holding back turns you round, while a fresh press of back with the button down is a measured step.

The neat piece is the facing normalisation. Forward and back are mirrored once on the way in and once on the way out, so every branch of the decision tree reasons in forward and back terms and never in left and right. One normalisation at the edge removes a facing test from every branch inside.

Also done: the pose dispatch, which works out what the character is doing from the previous frame number rather than from a stored state, and the movement half of the standing state. Twenty-one checks pass on the board.

What that testing does and does not prove. These checks compare the engine against the specification written down here, which for the input layer is the original's own documented model. They do not prove the port behaves like the original, because nothing here has been compared against it running. That comparison needs an emulator or a person who knows how the game feels, and it is the right check to apply at the end of the phase rather than the middle.

The floor test is done and exact. Every frame the engine asks whether the character is standing on something, falling towards it, or passing through it. Run over every cell of every screen of a real level at a spread of heights, 3,600 cases, the board matches the host reference on every count and on the checksum.

Two things there are worth knowing because neither is guessable. The block under his feet is his own cell, because the row index names the floor he stands on rather than the space he occupies. And a solid block counts as no floor, which looks like a bug until you see it handled separately: you do not stand on a solid block, you are pushed out to one side of it. Eight of the thirty block types are in that no-floor set.

Coverage, not just correctness. A scripted-scenario harness now reports which paths actually execute, and its first run was sobering: 70% of the animation had never run, two of three landing severities had never fired, and the ledge grab had never once succeeded. Chasing those found five real defects the rule tests could not see, among them a stun timer that was never decremented, a reach that carried the character out of the only column where a grab could work, and a block lookup that rewrote the caller's coordinates through MMBasic's by-reference parameters. Every one was found by a frame-by-frame trace or an exhaustive comparison, and none by inspection. The grab, the bump, all three landings, cross-screen falls, the stoop and stand-up, the running jump, the dive-roll and the turn at speed are now proven to execute, and coverage has gone from 63 to 105 of the 240 poses. One more of the defects deserves a line: the floor test was running regardless of the action class, so any jump that crossed a gap was turned into a freefall the instant it left the floor. The original dispatches that test on the action class, and once the port did too, a single run added seventeen poses.

The one that could never have been seen. The frame table is one-based: the original subtracts one from the frame number before multiplying by five. The port had indexed it by the frame number since the phase began, so every pose was drawn with the next frame's image and offsets. Adjacent frames of a rotoscoped run look almost identical, which is why weeks of watching the character would not have found it. It surfaced only because the same wrong index made a climb frame appear to carry a floor-check flag that belongs to its neighbour, and the trace of that climb would not add up.

What remains is the bulk: the rest of CTRL and CTRLSUBS. The standing state alone reaches into the sword, the opponent's distance and the decision to go on guard, which belong with the guards in a later phase; and the ledge grab with its lead time, the landing choice by fall distance, the bump and the drink are all still to come. Still most of a week's work, and still where the port either feels right or does not.

5World logic

Traps, gates and the level machinery In progress

The state machines are done and exact. Drawing is in. The exit and the level transition, the potions and the strength meter are in. The mirror, the timer and the closing-gate knock-aside are not started.

MOVER and SUBS: spikes, slicers, loose floors, pressure plates and the gates they drive, rubble, the exit, the mirror, the potions, the level timer and the level transitions.

One mechanism drives all of it. A block's state byte in the blueprint is advanced once a frame for every object on a transition list; floors in free fall are a second, shorter list. A plate's state is its index into the link table, whose timer field counts it back up; a gate's state is its height, and above fully open it becomes the timer that closes it again; a spike pit's state counts out, holds with the high bit set, and counts back; a loose floor counts down to letting go, or wobbles with the high bit set. The transcription (moverref.py, movertest.bas) was checked by scripting a run on level one that raises two gates, closes one of them while it is still rising, springs spikes twice, drops a floor through an empty row onto the one below, crushes a plate to rubble and lets a floor fall on the character, and a second run on level three's slicers. Three hundred and one hundred and twenty frames, the blueprint and both lists checksummed after every frame, and the board agrees with the host exactly on both.

The mover module is code, not data, so its constants are read from it by an assembler that skips instructions. Its equates refer to the data modules, which are assembled first and handed over; a table inside a code module is read relative to the nearest label. The random generator that picks a torch's flame is four instructions and is reproduced with the same seed on both sides.

Drawing follows the original's split. The static background keeps everything whose picture is fixed; anything that depends on state is left out and drawn fresh every frame from the live blueprint, before the character: a gate's grille as a bottom piece, as many eight-line middle pieces as fit and a part piece to finish; spikes by how far out; a loose floor by its wobble; a plate by whether its timer is running; a slicer by its stroke; a torch by its flame. A block that changes type, a floor that has gone or a plate crushed to rubble, marks the background stale and it is rebuilt before the next frame. The frame costs about 38 ms of the 83 on a screen with two gates, two plates, two torches and a loose floor.

The exit exposed a converter fault that no test had caught. The stairs sequence keeps a disabled alternative inside a do 0 … fin block. The assembler had been treating conditional assembly as listing control and emitting the block, so the sequence walked, checksummed and played correctly right up to the point where it should have ended the level, and instead put him back on his feet. Conditional assembly is now honoured, the sequence data is seven bytes shorter, and every reference number was regenerated. Verified by still: level one's plate opens its door, he climbs the stairs, and level two begins at its own start block with the door behind him closed.

6Guards

Sword fighting In progress

Guards are placed, think, follow into the next screen, fight and die; the player draws, strikes, blocks, advances and retreats; he bumps off a guard's blade with his own sheathed; common and special guards wear different colours; level three's skeleton rises from its bones and cannot be killed. Not yet: the shadow and the vizier, which belong with the cut scenes.

The guard is the same character with a different mind. The engine works on one set of character variables; the other character lives in a record and the two are swapped in and out each frame, as the original does with its kid and shadow blocks. The guard's controller presses the same stick and buttons the player has, and the shared fight controls do the rest. His temperament comes from twelve columns of probabilities, one per skill level, indexed by the same eight-bit random generator; the converter reads those tables out of the AI module. Strike detection is the original's: a blade at full stretch within range stabs unless the other is blocking, in which case the striker is turned aside and, if he is a guard, his blocking is impaired for a few frames.

Two drawing facts came out of the first stills: a right-facing image sits to the left of its anchor, which the edge computation in the source states and nothing else does; and the sword's offset is added facing right and subtracted facing left. Both were wrong for every mirrored frame drawn until then and nobody could have told from a walking figure alone.

The level-one walkthrough now meets the guard on the third screen, stops, draws, fights him to the death, sheathes, and goes on to the exit.

Four days.

AUTO and the fighting half of COLL: the guard behaviour programs, the strike, block and advance sequences, the strength meters, and the grace periods and patience timers that make guards feel like opponents rather than obstacles.

7Finish

Sound, messages, the clock, the interludes In progress

The clock, the messages, the twenty sound effects and the cut-away scenes are in. The music is not in the released source, and the attract demo is not started.

The effects ported because they are not recordings. Each is a short routine that flips the one-bit speaker through a shared helper, so it reduces to a pitch and a count of flips, and the converter turns those into a frequency and a length from the processor's clock rate. The only liberty is a floor on the duration: played literally most of them last under a millisecond, which no modern sound chip would make audible. The music is a different matter, since the cue names are in the source but the tunes are not.

Three days.

Twenty effects by ear, the message boxes, the hourglass and torches, the sixty-minute clock, and the recorded demo replayed as both attract mode and regression test.

The interludes are the picture, not the choreography. The game cuts away to the princess’s room on the way into levels 2, 4, 6, 8, 9 and 12 and at both endings, and the scene routines that place and animate her, the vizier and the mouse are all in the source, down to the frame counts. What is missing is the thing they animate over. The room is a full-screen packed picture, held on the shipped disk as a block number rather than as a file; the copy that is in the release is the artist’s composite, with the princess and the vizier already painted into it. Drawing the engine’s own characters on top of that would put two of each in the room, so a scene is shown as the picture itself, held, with any key to skip. That is very close to what an interlude looks like anyway: the princess and the vizier, waiting, while the sand runs. The endings now happen there rather than as a line of text.

The packed form took a decompressor of its own, in packpic.py. The compression is trivial, one escape byte and a run length; the work is the order, because the bytes follow the path the original’s unpacker takes through the Apple’s interleaved screen rather than reading order. The decoder reproduces that walk literally instead of trying to state it as a formula.

One trap worth recording, and it cost a day. A picture drawn straight to the screen has its colours matched against the palette that is live at the time, so a file whose colours are not already the game’s comes out in the wrong ones. Loading it into an image slot and blitting it instead copies the pixel values untouched, which is how the artwork sheets already reach the screen, so that is what the room does. The trap is the check, not the fix. SAVE IMAGE writes its palette with the colour channels in the opposite order to the one it reads them back in, so a saved frame is not only shifted in colour but permuted in value: a pixel written as twelve is saved as five and coloured as five. Read literally it says the whole palette is scrambled, which is wrong and which led to a pickup being given its colour in the wrong slot. The permutation is its own inverse and runs 0 8 2 10 4 12 6 14 1 9 3 11 5 13 7 15. Undo it before judging any colour from a screenshot, or look at the display.

Roughly four weeks of evenings, against Thrust’s seven phases and Exile’s larger plan. The estimate is honest about volume and optimistic about nothing except the renderer, which genuinely is easy here.

Decisions

D1 is taken. The rest are recommendations.

Taken
  1. D1 — Distribution. Engine and converter, no content. The program is freely distributable because it holds no game data: the converter runs on the player’s machine, against their own clone of the published repository, named on the command line. No vendored assets, no bundled samples, no built-in download. Free, and never pre-installed on hardware that is sold. The supporting rule is that no converter may emit a line of BASIC.
  2. D8 — Name. Pico Persia. What is being supplied is a BASIC program and a Python script, neither of which holds any of the game. The program will not start until the player has run the converter against a copy they obtained themselves, and what they do with it after that is theirs to decide. On that footing the name is a description of what the program is for. The design documents still name the original, because they are about porting it; the product carries the new name.
Still open — recommendation given in each case
  1. D2 — Tick rate. 12.000 fps, one present in five at 60 Hz, CPU at 378 MHz. Do not rescale any per-frame constant.
  2. D3 — Screen. 280×192 at 1:1, centred in MODE 2’s 320×240, four colours from the palette.
  3. D4 — Mirroring. Pre-mirror the character images at conversion time and draw everything with BLIT FLASH and a transparent colour. Do not use sprite buffers.
  4. D5 — Redraw. Full redraw into the F buffer every frame. Delete the peel and dirty-block machinery; keep the plane order and the block dependencies.
  5. D6 — Artwork residency. Everything in PSRAM image slots at startup, nothing swapped between levels.
  6. D7 — Music. Ship without it initially. Decide separately whether recovering the songs from a disk image is a project you want.
  7. D8 — Controls. KEYDOWN with the original’s key layout and a modern alternative; gamepad optional and later.
