Interpreter Performance Plan

1 · Purpose

Purpose and ground rules

MMBasic spends most of its time interpreting, not computing. The work it repeats on every execution is fixed for the whole RUN. This plan measures that work first. It then moves the answers into the stored program, written once when the program is saved, and never into heap tables that grow with the program.

The short version

  • Overhead is most of the run time. Peter's mmb2csub pairs show that the same routine as native code runs about 4x faster, even when the heavy lifting is already in optimised firmware such as the graphics commands. On solar_eclipse.bas about 80% of the run time is interpreter overhead: 1 − 2.5/13 = 80.8% from Peter's figures, or 1 − 2.7/13 = 79% from the 252 MHz pair in docs/mmb2csub.md:670.
  • The overhead is repeated work. Each statement is scanned to its end. Arguments are split again, names are hashed again and NEXT or LOOP is found again. A SUB's parameter list is re-read on every call, and the firmware polls for events that almost never happened.
  • The trace cache shows what not to do. It kept its answers in one fixed heap slab, which has to be made bigger as the code grows (Elite needed 256 slots). It keyed them on buffer addresses and invalidated them through one global counter. It rarely pays, and it can make programs slower.
  • Phase 0 measures before anything is built. It uses the anchor benchmark and its CSUB twin as the floor, a matrix of runs that needs no build, and OPTION PROFILING, extended one argument at a time as the hypotheses need it.
  • Route A makes the text cheaper. It adds an attention word in place of per-statement polling, call descriptors, symbol ids for names with storage bound lazily at run time, and block-partner tables. The ids, descriptors and partner tables are kept in the stored image. RAM grows only with the number of unique names.
  • Route B comes only if the numbers justify it. It is a compiled statement stream, written when the program is saved into a slot beside the text that LIST, EDIT and SAVE use. For testing, the slot is a RAM slot on the PC3 and a flash slot on the RP2040.
  • The yardstick is the fraction of the anchor's measured overhead removed. MicroPython, doing the same double-precision arithmetic, removes about 37% of it (8.8 s against 12.5 s, with the CSUB at 2.5 s). That is the bar Route A should reach.

Why first principles, and not more tuning

Tuning hot functions has been tried several times and has not moved the overhead:

  • A word-level heap bitmap scan was 17% slower on knivd.
  • Moving the double-precision routines to RAM only shuffled code placement.
  • Dispatch tables in RAM gained 0.4%.
  • One TinyUSB debug flag moved knivd by about 4% (11,840 against 12,330) through code placement alone. Any claimed gain must beat that noise.

Integer and float benchmarks run at almost the same speed, so the arithmetic is not the cost. The question is not "which function is slow". It is "what does the interpreter work out again on every execution that it could have worked out once".

Ground rules

  • Scope. This is the development branch, and everything may change: the stored program format, the tokeniser, LIST/EDIT/SAVE, the library and RAM-slot image formats, and interrupt-check timing. The trace cache is out of scope: Peter will probably remove it, and the plan ignores it.
  • The hard constraints are RAM and flash, and nothing else.
    • Firmware flash per variant:
      • VGAUSBRP2350's margin is not known until that variant is built again. It outgrew its 1040 KB offset, and commit 564fcff (2026-09-21) moved it one 16 KB step to 1056 KB (configuration.h:146).
      • RP2040 VGA has 13,340 B: buildRP2040L/PicoMite.bin is 822,244 B against the 816 KB offset.
      • Flash moves in 16 KB steps.
    • RAM-resident code on the RP2040 costs whole 4 KB pages.
    • struct option_s is exactly 896 bytes.
    • The function token table is 7-bit and nearly full: HDMIWEB is at 127.
  • Program capacity. In Peter's words, "going very fast but only supporting small programs isn't a step forward".
    • The largest programs today are about 100 KB on the RP2040 VGA, 144 KB on the PC3's HDMIWEB build and 300 KB on PICORP2350 (configuration.h:109,200,326). MAX_PROG_SIZE equals the heap, except that every RP2040 PicoMite build (PICO, PICOUSB and PICOMIN) fixes it at 120 KB (:393-397). That is the whole heap on PICO, but less than the heap on PICOUSB (124 KB) and PICOMIN (128 KB) (:356, 361).
    • Every proposal is priced in bytes of RAM and bytes of program flash per KB of user program.
    • Heap used by a side table is heap taken from the user's variables. The RP2040 has no PSRAM.
  • Method.
    • Measure before building.
    • One mechanism per build and per commit.
    • Every step runs on the board against golden outputs.
    • No benchmark may get slower beyond the placement floor.
    • A per-statement cache keyed on an address, or a heap table that grows with the code, is rejected on sight (§3.5).
  • Hardware.
    • PC3 on COM16: RP2350B with PSRAM and HDMI, running HDMIWEB with WiFi live.
    • RP2040 VGA on COM7: a LOWRAM build with no trace cache and no label hashing. findvar, DefinedSubFun and the FOR, IF, NEXT, DO and INC handlers run from flash.
  • Etiquette.
    • Never drive a board Peter is using. He types RUN.
    • Never build while he builds.
    • Serial lines go at least 20 ms apart.
    • Every result is logged with MM.DEVICE$, MM.VER, the git hash, the CPU speed and OPTION LIST.
2 · The model

How the interpreter spends its time today

This section follows one statement through the firmware. Every step was read in the code. The cycle cost of each step has not been measured on either board; Phase 0 exists to measure it.

What the program looks like in memory

The program runs directly from its tokenised image in flash, read through the 16 KB XIP cache. On the PC3 the RAM library and the RAM slots sit in PSRAM behind the same cache (PSRAMbase 0x11000000, configuration.h:524).

  • Only keywords are tokens. Names, numbers, spaces and trailing comments stay as ASCII.
  • Each line starts with T_NEWLINE and a skip byte (MMBasic.h:98-107, written at MMBasic.c:1698-1720).
  • Statements end in a 0, and the program ends with 00 00.

The same image is the source for LIST, EDIT and SAVE, which is why it stays text.

One statement, step by step

  1. Line header (MMBasic.c:1834-1859), once per line: set CurrentLinePtr, write the TraceBuff ring, test TraceOn, and step over the line number and label.
  2. Pre-scan (1879-1881): skipelement(nextstmt) walks every byte to the terminating 0, including any trailing comment. ExecuteProgram uses the skip byte only to jump over comment-only lines (1863-1875).
  3. Dispatch (1890-1917): commandtbl_decode, then commandtbl[].fptr(). The table is const, so it is in flash. A user SUB name goes through FindSubFun and then DefinedSubFun. setjmp runs only while ON ERROR SKIP, IGNORE or RESTART is in effect, that is while OptionErrorSkip is not 0 (1925-1938; Commands.c:8546-8575).
  4. The command reads its own text again.
    • getargs/makeargs copy it into a 384 B stack buffer, calling strchr on each top-level byte (MMBasic.c:5551). A bracketed argument or function call is found with getclosebracket and copied in one memcpy (5600-5607).
    • LET scans for = with a tokenfunction table lookup on each byte (an inline macro, MMBasic.h:227-230; Commands.c:1787-1788), then skipvar, then findvar on the left side (Commands.c:1818).
  5. Expressions. evaluate calls getvalue for the first operand, then doexpr while an operator follows (MMBasic.c:2889-2891). doexpr calls getvalue for each next operand and recurses on precedence (3066, 3146).
    • Literals are parsed again on every evaluation (MMBasic.c:3336-3398).
    • Operators receive their operands through globals and are reached by an indirect call (3135).
  6. Every name. findvar upper-cases and FNV-hashes each character, then takes % maxglobalvars at run time (4689-4701). Inside a SUB it probes the local table before the global one.
  7. Every name(. FindSubFun runs first (3277-3279), so every array read asks "is this a function?".
    • On the RP2040 that starts by counting subfun[] one entry at a time (2027-2028).
    • Array indices then go through a getargs copy, a bracket re-scan and skipvar.
  8. Every built-in function that takes arguments (T_FUN, 3245-3253; Memory.c:1852-1860): getclosebracket, then a zeroed 256 B temp page, then a memcpy of the argument text. The page is freed at the end of the statement. Functions with no arguments, such as TIMER and PI, skip the copy (3254-3256).
  9. Tail (MMBasic.c:1940-1952):
    • ClearTempMemory if anything was allocated.
    • The core1 stack canary, which is not compiled on WEB builds (1944).
    • Unless NOCHECK is set, CheckAbort() and then check_interrupt():
      • CheckAbort calls ProcessWeb(1) on every statement on WEB builds (PicoMite.c:2682-2687), and HDMIWEB is one (CMakeLists.txt:798-806). ProcessWeb reads time_us_64, walks the PCBs, and polls cyw43 every 100 calls or every 1 ms (net/WiFi.c:295-345).
      • routinechecks calls time_us_64() and returns if less than 100 µs have passed (PicoMite.c:893-901).
      • check_interrupt calls ProcessTouch on every statement while GUI controls exist. Otherwise it returns unless InterruptUsed is set. Once any interrupt has been set, checkdetailinterrupts runs on every statement until END (MM_Misc.c:10558-10586). That is a 350-line function in flash (10209-10557) that tests every interrupt source in turn.

Control flow and calls

  • FOR entry (Commands.c:5121-5235):
    • getargs, which trims argbuf in place (5130-5133).
    • Removal of any stale entry for the same loop from the FOR stack.
    • A forward scan to the matching NEXT. For each NEXT it meets, it runs mystrncasecmp at every byte offset of that NEXT's argument list (5198-5235).

    NEXT itself is a pointer compare (5278-5284). An inner loop therefore re-scans its body once per outer iteration.

  • DO scans forward to LOOP on entry (5378-5394). SELECT walks the arms on every dispatch (4729-4912).
  • GOTO and GOSUB. findline is a linear walk on both chips (MMBasic.c:3547). findlabel is hashed on the RP2350 (3742) and linear on the RP2040 (3802).
  • SUB and FUNCTION calls (DefinedSubFun, 2232-2709):
    • makeargs runs over the caller's argument list and over the definition's parameter list (2392, 2398).
    • For each parameter: the BYVAL/BYREF test twice, skipvar, CheckIfTypeSpecified (2527), and findvar(V_LOCAL).
    • The RP2350 clears 600 B per call (2370-2371). The RP2040 allocates and zeroes 75 × 29 + 512 = 2,687 B per call (2376-2385).
    • A FUNCTION re-enters ExecuteProgram (2679), which copies the jmp_buf on entry and again on exit.
    • On return, ClearVars walks the whole hash list (6356+).

Where the code runs

  • RP2350. ExecuteProgram, the evaluator, findvar, the operators and the hottest handlers are RAM-resident. checkdetailinterrupts and most fun_ routines run from flash; fun_sin is at 0x1000cbfc in the HDMIUSB map (buildRP2350L).
  • RP2040 VGA (LOWRAM). These also run from flash:
    • findvar and DefinedSubFun (MMBasic.c:4643, 2227);
    • cmd_for, cmd_if, cmd_else, cmd_next, cmd_do and cmd_inc (Commands.c:5097, 3659, 3947, 5256, 5327, 909).
  • Flash clock.
    • The RP2350 runs the flash at CLKDIV 2 up to 288 MHz and CLKDIV 4 above (PicoMite.c:3758-3761); the RP2040 VGA is always at CLKDIV 4 (CMakeLists.txt:588-591, PicoMite.c:3825-3827).
    • Not pursued. Peter's judgement is that flash timing is not very relevant, because its effect is confounded by the QMI cache, and placement effects are already known to be about 4%. The plan runs no flash-clock experiments.

What has been learned already

3.1 The overhead, measured against CSUB twins of the same routine

Split the interpreted time as T = W + O: the work itself plus the interpreter's overhead. mmb2csub converts about 132 of the 166 routines in its corpus (mmb2c's tests/, plus se.bas, julia.bas and knivd.bas). The same routine therefore exists interpreted and native, and T_native is a measured floor for W.

What this implies:

  • Even where the firmware does the drawing, three quarters of the time goes between the firmware calls, getting arguments out of text and into C.
  • Code built from SUBs with locals is almost pure overhead.
  • Nothing that speeds up the arithmetic can matter.

This gives the yardstick used everywhere below. It is measured per board, within one build and one condition:

removed(X) = (T_interp − T_interp,X) / (T_interp − T_native)

Removing 10% of the overhead counts the same on a 4x routine as on a 35x one. The floor needs two caveats:

  • It is slightly optimistic. A CSUB skips bounds checks, per-statement Ctrl-C and interrupts, and error line numbers (docs/mmb2csub.md Appendix A).
  • It is pessimistic on the RP2350. The blobs are M0+ code, helpers are reached through the CallTable, and a 37 KB blob runs from XIP flash.

The sefunc CSUB barely scales with the clock: 2.7 s at 252 MHz and 2.48 s at 378 MHz (docs/mmb2csub.md:668-672). Between those two clocks the flash clock fell from 126 to 94.5 MHz while the CPU rose 1.5x. The interpreted remainder, flash fetch or the CallTable's double routines could each explain that. The plan does not chase it (flash timing is confounded by the QMI cache); it takes the floor as measured, on the same build as the interpreted time.

3.2 What MicroPython's lead teaches

On the same chips, MicroPython written to mimic BASIC is up to about 30% faster than MMBasic (Peter's figure). Peter's MicroPython is his own PC3 port (\\wsl.localhost\Ubuntu\home\peter\src\micropython\ports\rp2, board PICO_COMPUTER_3). It uses double-precision floats and arbitrary-precision (MPZ) integers, so it does the same arithmetic as MMBasic (mpconfigboard.h:24-26; DEVELOPMENT_NOTES.md §1). On the anchor, the line-faithful port tests/solar_eclipse.py takes about 8.8 s against MMBasic's 12.5 s at 378 MHz on the same chip, with digit-identical output. That removes (12.5 − 8.8)/(12.5 − 2.5) ≈ 37% of the overhead.

What it resolves once

  • It compiles once: lexer, whole-module parse tree, then bytecode (py/compile.c).
  • Identifiers are interned to qstrs at parse time, and bytecode names them by a small per-module index.
  • Function locals get fixed slots. LOAD_FAST is fastn[-n] plus a NULL check, and an unassigned slot is NULL.
  • Pending work is flagged by events. Ctrl-C and IRQ callbacks set two words, which are tested inline only in jump opcodes. Nothing polls per opcode.
  • for over range compiles to an inline counter, and const() is folded.
  • Line numbers live in a compressed table that is decoded only when an exception is raised.
  • Dispatch is by computed goto, about 10% faster than a switch on rp2.

What eats the gain

  • Type dispatch on every binary operation.
  • Floats are boxed. In Peter's double-precision build a 64-bit double cannot fit in the 32-bit object word, so every float result is a heap allocation from the GC under a mutex (his DEVELOPMENT_NOTES.md says so too).
  • Integers beyond 31 bits become MPZ bignums on the heap.
  • Its flash runs slower than MMBasic's: capped at 63 MHz (divider 6 at 378 MHz, MICROPY_HW_FLASH_MAX_FREQ), against MMBasic's 94.5 MHz. Its VM core is in RAM and its bytecode is in RAM.
  • Its sin is software double precision. The ulab variant, with the series vectorised, still takes 7.4 s, and its README puts the remainder down to sin.
  • BASIC-style module-level code uses LOAD_NAME/STORE_NAME dictionary operations, and builtins first miss in the globals.
  • nlr_push on every call.
  • Its own documentation puts the native emitter at about 2x bytecode. The big factors come only from viper, which uses machine integers.

Implication. A suffix-typed BASIC that adopts these resolution ideas without the dynamic object model has a higher ceiling than 1.3x. An Amdahl projection from the 300% overhead: cutting the overhead by 5x would give about 2.5x on graphics-heavy code and 4-5x on compute kernels. This is unverified.

A consistency check, also unverified. An assignment costs about 1,900-2,270 cycles in MMBasic (6 µs at 315 or 378 MHz), against a few hundred for MicroPython's x=x+1. That predicts far more than 1.3x on scalar code. The arithmetic is the same, so precision does not explain the gap. Two things could:

  • If the 30% came from mixed programs, time spent in C (builtins, graphics) dilutes the difference.
  • MicroPython's own costs: a heap allocation for every float result, dictionary lookups for module-level names, and a slow software sin on an anchor with about 450 SIN( calls in its text.

Either way, MicroPython carries costs MMBasic does not have and still wins. That points at MMBasic's operand handling, not at its arithmetic.

The E pairs in Phase 0 settle it.

Memory-model warning

MicroPython compiles in RAM. The whole-module parse tree is held until every scope has compiled, so peak RAM is O(source). It also keeps bytecode in RAM, for .py and for .mpy (persistentcode.c copies it). Only frozen bytecode, or ROMFS (off by default on rp2), runs from flash. An unverified anecdote: a 100 KB .py ran out of memory compiling on a Pico W, and a 28 KB .mpy used 60 KB of heap.

MMBasic today uses no RAM for program text; only small indexes, such as the IF table and the sub tables, live in RAM. Any compiled form of MMBasic must therefore be written when the program is saved, into flash (or into a RAM slot while testing), beside the text that LIST/EDIT/SAVE round-trip. BASIC can compile line by line with a forward-jump fixup list, so it needs no parse tree.

Do not adopt: dictionary globals, boxing, GC, compiling into RAM, or whole-module parse trees.

3.3 What is already resolved once

  • The line skip byte (MMBasic.h:98-107; MMBasic.c:1698-1720). ExecuteProgram uses it only to jump over comment-only lines (1863-1875). Every executed statement is still scanned byte by byte (1881).
  • FOR and DO iterations. forptr and nextptr sit on the FOR stack, and loopptr on the DO stack (Commands.c:5391, 5492-5496), so NEXT and LOOP jump straight back. What remains is the forward scan each time a FOR (Commands.c:5198-5235) or DO (5378-5394) is entered, which for an inner loop is once per outer iteration.
  • Multi-line IF/ELSEIF/ELSE/ENDIF uses a sorted jump table built at PrepareProgram (Commands.c:3250-3565). It lives in the heap.
  • Labels and SUB names on the RP2350 are hashed into funtbl (MMBasic.c:3654). The RP2040 does not have this.
  • Still unresolved: the SELECT CASE walk on every dispatch, line-number targets, and labels on the RP2040.

So block partners are mostly done already. The remaining gaps are the entry scans and SELECT.

3.4 Binary literals: tried, no gain

Peter stored numeric literals in binary behind a pretend function token, and there was no noticeable improvement. That fits the model. Converting a literal is a small part of a statement whose evaluator still walks the text around it, hashes the names and copies the arguments.

The lesson is general: removing one piece of text parsing buys little while the evaluator still re-walks the text. The gain arrives only when the walk itself stops. Symbols (S5-S6) start that, and a compiled stream (Route B) finishes it.

3.5 The trace cache, and why a per-statement cache fails to pay

OPTION TRACECACHE ON [size[,flags]] is off by default and exists only on CACHE builds (CMakeLists.txt:297-309): HDMIWEB has it, the RP2040 VGA does not. It compiles the right-hand sides of LET, IF, INC, DO and SELECT, and caches jump targets. Entries are keyed on the statement's source address, through a golden-ratio hash with up to 8 probes (MMtrace.c:407-452). A cached statement replays a small typed stack machine.

It fails for six reasons.

  1. The lookup costs about what it saves, and the frame stays.
    • Every hit pays a multiply-hash, up to 8 probes, and a replay with a stack check and a type tag on every op.
    • It skips findvar and the evaluator for one statement. It does not skip the pre-scan, the dispatch or the tail. IF's getargs runs before the cache is even checked (Commands.c:3694 against 3722).
    • The dispatch-level hook TraceCacheTryExec is a stub (MMtrace.c:3376-3381).
    • Even in the best case, a fully cached DO loop is still 2.9x slower than the FOR loop.
  2. The binding lifetime is wrong.
    • One global 16-bit counter, g_local_frame_gen (MMtrace.h:50-59), changes on every frame entry and exit.
    • After any call, every cached statement that uses a local re-resolves it with a linear scan (MMtrace.c:822-878).
    • For SUBs with locals called once a tick this costs more than findvar. That is why the Exile kernel got slower.
  3. The identity is wrong.
    • The key is a buffer address. The stack argbuf, which runs a single-line THEN a ELSE b (Commands.c:3787), and tknbuf, which runs EXECUTE and the prompt, present one key for different code.
    • physics.bas:450 and :452 are both If cy Then X = a Else X = 0. That is the probable cause of the CollTiles result. This comes from reading the code; it has not been reproduced.
  4. The coverage is wrong. It covers expression right-hand sides, including simple 1-D and 2-D array element reads and writes (MMtrace.c:15-18, 1482-1553). Real programs spend their time on calls, array traffic and command arguments ("calls and array traffic, not tight arithmetic", design review :372). It does not cover calls to user SUBs and FUNCTIONs, or command arguments.
  5. It is a second semantics.
    • Eight divergences are known from reading the code:
      • ^ is right-associative;
      • INT^INT goes through pow();
      • >> is an arithmetic shift;
      • NOT 0.4 gives 1;
      • NaN compares differently;
      • float-to-integer conversion truncates instead of rounding in the side paths: the DO fast-path limit, an INC float step on an integer, and SELECT CASE constants (MMtrace.c:3497, 3847, 4135). LET and IF round, as the interpreter does;
      • RND advances twice when a statement bails out;
      • computed GOTO targets are frozen.
    • The DO fast path (Commands.c:5415-5450) is gated only by #ifdef CACHE. On COM16's HDMIWEB build it is live today, with no option set.
  6. Its size must grow with the code, and it never shrinks.
    • The slab is allocated once, at the size the user sets (default 64 entries; MMtrace.c:79-83, 373-377). What grows with the code is the number of slots needed to stop missing. Each slot is 216 B (MMtrace.c:115, 314-329), so Elite's 256 slots take about 55 KB of heap.
    • It compiles on the first visit and never evicts. One bail-out marks a statement BAD for the rest of the run.
    • Every CACHE build pays about 10 KB of RAM-resident code plus 9 KB of flash whether the option is used or not. The HDMIUSB map (buildRP2350L) shows 10,038 B of .time_critical and 9,138 B of .text, 19.2 KB in all.
    • Part of the invalidation its header documents (MMtrace.c:74-77) is not wired up. NEW, RUN and EDIT drop the whole cache (Memory.c:2010; misc/Editor.c:629), and the file-manager relaunch frees it (misc/Editor.c:4440), but DIM, ERASE, OPTION BASE and OPTION EXPLICIT do not invalidate it.

R6 CoverageTarget a bucket the measurements show is large, including polling and argument passing, not only expressions.

How symbol ids differ from the trace cache

A symbol id identifies a name as it appears in the program text. It does not identify a variable, and it does not identify a statement address.

  • Ids are assigned when the program is tokenised, because every name in the program is known at that point.
  • Storage is still bound at run time, and lazily. On first use an id has no binding, so findvar runs exactly as today and its result is recorded against the id. Implicit creation, conditional DIM and LOCAL, OPTION EXPLICIT and recursion all behave as they do now.
  • A binding changes only when storage changes: a local created or destroyed, ERASE, CLEAR, RUN or CHAIN.
  • Copies cannot alias. A fragment copied into argbuf carries its own ids.
  • Names that never appear in the program text keep today's by-name path. These are EXECUTE strings, CALL by string and the prompt.

The trace cache bound results to a statement address and invalidated them globally on every frame change. Ids bind to a name and change only on the events listed above.

The plan ignores the trace cache from here on. Peter will probably remove it from main, because mmb2csub is far more powerful. Nothing below measures it, keeps it or tries to match it; it appears in this document only as the lesson above. Removing it frees 19.2 KB of text on the CACHE builds, about 10 KB of it RAM-resident (HDMIUSB map in buildRP2350L). It also removes the always-on DoFast path and its truncation bug (§7).

5 · Options

Candidate architectures compared

Five strategies were written independently and then judged. None is adopted as written. The recommended programme takes the measurement discipline from one, the identity layer from another, a binding mechanism from a third, the yardstick from a fourth, and the design rules for a later compiler from the fifth.

measure-first: keep the text, add side tables

Profile first. Then remove structural repetition inside shared primitives, using tables built at PrepareProgram as the IF table is:

  • amortised polling;
  • a FOR/DO/SELECT structure table;
  • array indices evaluated in place;
  • call descriptors;
  • a binding cache.

RP2040: the tables compete with the 100 KB heap, and findvar and the FOR, IF, NEXT, DO and INC handlers run from flash. RP2350: a 12 KB binding cache.

Kept: the whole Phase 0/1 skeleton and the attention word.

Changed:

  • Its binding cache is keyed on the address of the name text, which is the trace cache's key shape. Symbol ids replace it.
  • Its heap structure table becomes a partner table stored in the image.

prepass: link the program at RUN

One pass at RUN builds a side structure in the heap:

  • a statement spine;
  • block links;
  • call descriptors;
  • symbols with shallow binding;
  • operand sites.

Cost: by its own estimate about 0.4 KB of heap per KB of program for the spine and links, and 0.9 KB per KB with sites. The speed-up disappears exactly on large programs.

Kept:

  • Its shallow binding (L5a), keyed by symbol id.
  • Its rule that the builder calls the runtime pairing scan, which keeps one semantics.
  • Its ceiling hack, made safe (0g).

bytecode: compile units to a typed VM

SUB bodies and hot loops compile to 16-bit typed wordcode in the heap. At every statement boundary, the state is the same as the text interpreter's.

Highest ceiling: 2.5-7x on kernels (its estimate).

Costs:

  • A second engine.
  • 15-25 KB of flash, which non-CACHE RP2040 builds do not have.
  • A heap budget of 8-16 KB on VGA that caps coverage.

Kept as Route B's design rules:

  • state equivalence at statement boundaries;
  • loops reuse the interpreter's stacks;
  • entry by subfun index;
  • the value splice;
  • shared operator helpers with a shadow mode;
  • the VM-as-CSUB prototype (at G3).

It is only acceptable as a stream written at save time into a slot, never compiled into the heap.

native: the CSUB boundary

This is not an interpreter speed-up. It contributes the yardstick, removed(X) against the CSUB floor, and the mmb2c corpus as a semantics oracle.

Its firmware items are cheap and touch only CSUB paths, at about 150-300 B each (its estimates):

  • F1: a CSUB call table indexed by subfun.
  • F2: a CSUB that returns a result, so a FUNCTION needs no interpreted wrapper.

Offer these separately from this plan.

format: symbol ids in the stored image

Repeated names become 2- or 3-byte references into a name block kept inside the image. The block holds each name's spelling, a hash16 identical to the text path's, and a static binding for every SUB, FUNCTION, CSUB and label. The tokeniser emits ids only in commands flagged as audited.

Costs:

  • RAM: under 1.2 KB, fixed.
  • Save-time scratch is borrowed from g_vartbl: 26,880 B on VGA and 47,104 B on the PC3.
  • Firmware: 3-5 KB (estimate); VGA has 13 KB free.

Speed alone is small: 3-20%, its estimate. But it is the identity layer every later step needs, and the only proposal that makes the stored program smaller.

Its gap: the speed-up rests on findvar still probing. Shallow binding fills it.

S6 in detail.

  • The RAM binding table holds, per symbol, the global slot, the local slot and the local level. It is set when a variable is created and restored by ClearVars and ERASE.
  • Reset events: CLEAR, RUN, NEW, ClearVars(0), CHAIN/RestoreContext, and LIBRARY LOAD ,RAM.
  • An unbound symbol takes findvar and then binds. This keeps implicit creation, conditional LOCAL, re-DIM and recursion exact.
  • Types come from the suffix, OPTION DEFAULT, DIM and LOCAL.
  • Library and program symbols are merged.
  • EXECUTE, CALL by string and the prompt use by-name lookup.
  • A shadow build also runs findvar on every hit and counts disagreements.

Not in the plan unless the measurements ask for it. Four hand micro-optimisations are left out: a static argument pool, zeroing sized by argument count, an early exit from ClearVars, and a register-local skipelement. Each is likely below the ~4% placement floor on the anchor. One is allowed only when the histogram shows its bucket at 2x the floor or more. Caching the subfun count (S2) is different: it is algorithmic, O(N) to O(1).

Kill rules for every Route A step
  • It delivers under 50% of its predicted gain on its own micro-benchmark.
  • Any macro benchmark is slower beyond the placement floor, or any never-slower micro regresses by more than 2%.
  • Any shadow-build mismatch that is not explained within the step.
  • Any corpus program stops fitting on COM7, or the image grows past measured slack.
  • RAM-resident growth crosses a 4 KB page with nothing removed to offset it.
When Route A is done or stops
  • Done: Route A has removed ≥ 37% of the anchor's overhead on the PC3 (MicroPython's bar; on the reference build, re-measure the interpreted and CSUB times first and take 37% of the difference) and ≥ 30% on COM7, with no macro slower. Go to G3.
  • Stop: under 15% removed on both boards after S1-S4. Stop adding interpreter tables and go to G3.
  • Firmware flash: VGAUSBRP2350's margin is not known until it is built again; it outgrew 1040 KB and moved to 1056 KB (commit 564fcff, 2026-09-21). Removing the trace cache, which Peter plans for main, frees 19.2 KB of text on every CACHE build, VGAUSBRP2350 included. The RP2040 VGA has about 13 KB.
G3DECIDE

Stop, or Route B

Route B is a go only when all of these hold:

  1. Overhead is still large. After Route A, the anchor's remaining overhead (Tinterp,A − Tcsub, same build and condition) is at least twice the CSUB time on both boards. On the PC3 that means at least 5 s.
  2. The prototype pays. The prototype is the VM as a CSUB, moved here from Phase 0: about 300 lines of C built through armcfgen, with hand-written wordcode for an integer loop, the Julia inner loop, an array routine and one sefunc callee. It must be ≥ 3x faster than the post-Route-A interpreter on the integer and array routines on both boards. Under 2x kills Route B. Its confounders are stated with the result.
  3. The subset covers the work. A census, weighted by the line histogram, shows ≥ 70% of executed statements on the anchor and the game macros fall in the compilable subset.
  4. Capacity. A host-side encoder shows the stream is no larger than the tokenised image for every corpus program (PoP, Elite, the anchor, Exile). Any program that fits today then gets its stream into one slot of MAX_PROG_SIZE, and RAM stays O(unique names + call depth).
  5. Firmware fits. On CACHE builds, the 19.2 KB freed by removing MMtrace pays for the VM. On the VGA it must fit within about 13 KB. Any 16 KB step is Peter's decision at that point.

The Exile kernel pair (9.8 ms against 0.1 ms) is a second floor. It checks that the anchor's result generalises to SUB-with-locals code.

RBIF G3

Route B: a compiled statement stream, written at save time

  • Where it is written. Save already tokenises line by line (tokenise(false) at PicoMite.c:4788). The compiler emits alongside it and appends a forward-jump fixup table, so there is no whole-program parse tree.
  • Records point back to the text for errors, TRACE and LIST. The per-line state (CurrentLinePtr, TraceBuff) is derived from the instruction pointer where possible.
  • Names and binding. Names are S5/S6 symbols, and binding uses the S6 table, so RAM stays O(unique names + call depth).
  • Typed operations with unboxed values. Types come from the suffix or from the binding (OPTION DEFAULT, DIM, LOCAL). Operations call the shared op_* helpers.
  • Loops reuse g_forstack, g_dostack and gosubstack. State is identical to the text interpreter at every statement boundary, so interrupts, ON ERROR, CONTINUE and EXECUTE work unchanged. S1c's pending word is the only per-statement test.
  • Fallback and splice. Anything not compiled falls back to its handler. Whitelisted commands take pre-evaluated arguments through the value splice.
  • Shadow mode: an OPTION argument, not a new token.

Delivery, each phase with its own gate:

  • P1 records only, calling the existing handlers. Gate: goldens pass and nothing is slower than text.
  • P2 numeric LET/IF/FOR/DO/EXIT on globals. Gate: shadow mode clean, and the prototype's speed holds in firmware.
  • P3 locals and calls. Gate: the Exile kernel matches all 2,384 ticks of run_phystest.py, and the anchor improves.
  • P4 arrays, SELECT, GOSUB, literal GOTO and simple strings.
  • P5 the value splice for SIN, COS and the other pure built-ins, then PIXEL, LINE and BOX.

Where the stream lives while testing:

  • PC3: a RAM slot. RAM 1-4 are image slots 4-7; RAM 5 holds the RAM library (configuration.h:400-410; ImageSlotAddress, misc/FileIO.c:1071). Each slot is MAX_PROG_SIZE. The stream is rebuilt at each save or RUN and is lost at power-off. This avoids repeated flash burns.
  • Timing check. PSRAM and flash both sit behind the XIP cache, with different timing. Before any figure is quoted as the flash result, it gets one confirming run from a flash slot.
  • RP2040 (no PSRAM, no RAM slots): flash slot 1 or 2, since slot 3 is the library. Iterations are batched to limit erases.

Where the stream lives once the concept is proven (in production, one of the user's flash slots while compiled mode is in use) is deferred until then. The capacity-optimal end state, a single executable image that LIST decompiles, is noted but not started.

Found along the way: correctness, not speed

These come from reading the code. Each has a short board repro in the dossier, and whether to act on each is Peter's call.

  • DoFast truncates a float DO limit. By reading, i%=0 : Do While i%<2.5 : Inc i% : Loop : Print i% prints 2 instead of 3. It is gated only by #ifdef CACHE (Commands.c:5415-5450), so it is live on COM16 today, with no option set. Removing the trace cache removes it, but the cmd_do/cmd_loop hooks must go with it.
  • Trace-cache keys alias through argbuf and tknbuf, the probable cause of the CollTiles result, and DIM, ERASE, OPTION BASE and OPTION EXPLICIT do not invalidate it (MMtrace.c:74-77). Both go away with the cache.
  • The RP2040 sub/fun name collision check is dead (MMBasic.c:5160-5166). x++ lands on the second token byte, which is 0x80 or more, so the test never matches. Symbols would make it live, and programs that pass today could start reporting a clash, as the RP2350 already does.
  • The interrupt frame imbalance is confirmed by reading, on CACHE builds only. g_LocalIndex itself balances through cmd_ireturn (MM_Misc.c:1883). The effect is limited to g_current_sub_idx, profiling and the trace cache's locals.
  • The dossier's RP2040 SIN/COS double evaluation is already fixed (fef1f0b, today).
