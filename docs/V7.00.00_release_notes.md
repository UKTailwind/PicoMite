**Release candidate 3 (V7.00.00RC3).** RC3 is RC2 with the reports of the
last few days answered, all listed under *Fixed since RC2*. A program too
big for the program memory, loaded without `,C`, no longer leaves the board
stopping at every prompt with "Program damaged: symbol table", and a board
that RC2 left in that state recovers when RC3 is installed. A WebMite or a
PicoMiteRP2350 with neither PSRAM nor a display can `LOAD` from the SD card
again. On the PicoCalc's PicoMiteRP2350, `PIXEL()` and `BLIT READ` return
the right colours. A `DO` loop in a recursive SUB or FUNCTION, `ON ERROR SKIP`
around a FUNCTION call, and the `ON ERROR` setting a program leaves behind
at the prompt all behave. `PRINT` counts a comma's tab as a terminal does and
keeps a file's column apart from the console's. On the USB host builds the
Nintendo Switch Pro Controller is supported, `DEVICE(MOUSE n, B)` reports
every button, a DualShock 4's diagonals are right, an unplugged gamepad
reads 0, and `GAMEPAD MONITOR OFF` ends the monitoring. The PicoMitePC3's
`WEB SCAN` finds and measures networks as a WebMite does, Bluetooth or not.
`EDIT` no longer shows an empty line after a file's last line, keeps a
paste and keys typed during a redraw, lets Esc discard changes with a line
over 255 characters, and keeps its line count after Beautify. On the
Bluetooth builds `GUI CURSOR LINK MOUSE` takes a Bluetooth mouse or a
Bluetooth keyboard's trackpad. The Print Screen key saves the display as a
BMP, at the prompt, in the editor and in the file manager. A save, import or
export that the editor cannot make no longer loses the edits, and its search
brings a match past the right edge into view. `MATH FFT` is about 20% faster.
The PicoMiteRP2040MIN leaves out `MATH SENSORFUSION`, to make room. The
supplementary manuals' tables are mended.
Coming from RC2 only the PicoMitePC3 resets its options (see the box below).
`MM.VER` reads `7.000053`.

**Release candidate 2 (V7.00.00RC2).** RC2 is RC1 with the reports of the
last three days answered. The PicoMitePC3 gets `OPTION RADIO BOTH | WEB |
BLUETOOTH | NONE`, so the one build serves as the all-in machine, a WebMite, a
Bluetooth host or a plain HDMI computer, with the half not in use costing
nothing (see *New since RC1: OPTION RADIO on the PicoMitePC3*). The file
manager plays a track list: mark audio files with the space bar and press
ENTER, step through them with `.` and `,`, and it shows a cursor at its text
prompts (see *New since RC1: the file manager plays a track list*). On the
Bluetooth host builds `BLUETOOTH CONNECT SPEAKER | SERIAL | KEYBOARD` says
what a device is when its Class of Device does not (see *New since RC1:
BLUETOOTH CONNECT SPEAKER, SERIAL and KEYBOARD*), and `OPTION PICO PLUS 2 ON`
works on the Pimoroni Pico Plus 2 W. The fixes under *Fixed since RC1* take
in the `OPTION DISK SAVE` decimals, the PicoMiteRP2040MIN's I2C OLED, the
structure, tokeniser, `MATH`, `DIM`, `JSON$` and `PRINT #GPS` faults reported
as issues 7 to 14, `PLAY` on a directory from another drive, and a PSRAM
part larger than 8 MB, which is now used as 8 MB. mmb2csub can also build
CSUBs for the Colour Maximite 2 (`--target cmm2`). Coming from RC1, three
builds reset at their first boot and every other build keeps everything: see
the box below. `MM.VER` reads `7.000052`.

**Release candidate 1 (V7.00.00RC1).** Version 7 makes MMBasic faster on
every board, and on the RP2350 it adds a compiler that runs most of a
program as native code while leaving it exactly as you wrote it. You do not
change your program to use it: switch it on, type `RUN`, and whatever the
compiler can take runs compiled while the rest runs as before. RC1 adds a
build for the Pico Computer 3, the PicoMitePC3, which puts the HDMI
PicoMite's video and USB, the WebMite's WiFi and the Bluetooth host's
keyboards, speakers and serial devices in one image with a 256K program
(see *New since RC0: the PicoMitePC3*). On the Bluetooth host builds a
speaker's stream now starts as soon as it connects, `BLUETOOTH CONNECT`
takes a PIN for devices that pair the older way, and only 44.1 kHz is
offered to a speaker (see *Changed since RC0: Bluetooth speakers, car
radios and PINs*); with a speaker configured these builds also run programs
faster, the service that fed it having run on every statement (see
*Changed since RC0: the Bluetooth host builds run faster with a speaker
configured*). RC1 also fixes a USB host build's serial adapter losing a
character whenever a USB keyboard was typed on at the same time, and a
Bluetooth LE serial module with a 16-bit service UUID, such as an HM-10,
that `BLUETOOTH CONNECT` never found (see *Fixed since RC0*). Coming from
RC0 every board keeps its options and files; the PicoMitePC3 is a new build,
so loading it over another one resets the options and the A: drive, and the
Pico Computer 3 configures itself again at the next boot. `MM.VER` reads
`7.000051`.

Release candidate 0 added `ZMODEM` to every build: it
moves programs and files over the console as `XMODEM` and `YMODEM` do, but
much faster, a lost or damaged block is sent again instead of ending the
transfer, and `ZMODEM RECEIVE "*"` takes any number of files at once (see
*New in RC0: ZMODEM*). On the two Bluetooth host builds, the
PicoMiteRP2350BTH and PicoMiteHDMIBTH, a Bluetooth serial device such as a
Bluetooth GPS, or a Bluetooth LE serial module, can now be the serial port
`COM7` (see *New in RC0: Bluetooth serial devices on COM7*). RC0 also
fixed a USB console that could lock up for good when characters arrived one
at a time, a `FLASH LOAD 1:EDIT` on one line (or on a function key) that
showed the program's names as `?` or hung the board, and two TFTP faults on
the WebMites; and the USB host builds now take serial adapters with a
Prolific PL2303 chip (see *Fixed since beta 8*). Coming from beta 8 most
builds keep everything; the PicoMiteHDMIWEB, PicoMiteHDMIBTH and
PicoMiteRP2350BTH reset their options, and the PicoMiteRP2040USB,
PicoMiteRP2040VGAUSB and WebMiteRP2040 start afresh (see the box below).
RC0's `MM.VER` read `7.00005`.

Beta 8 was mostly for the wireless builds. On the three Bluetooth builds the
radio is now serviced from the main loop, as the WiFi builds' radio already
was; in beta 7 it could take most of the processor, so I2S tones warbled
and ran on past their length and the PicoMiteRP2350BT's heartbeat stopped
(see *Fixed since beta 7*). Bluetooth
speakers that refused to connect, connected but stayed silent, or dropped out
every few seconds should now play, and `BLUETOOTH STATUS` says much more
about what a speaker is doing (see *New in beta 8*). The two Bluetooth host
builds, the PicoMiteRP2350BTH and PicoMiteHDMIBTH, now also take a Bluetooth
Classic keyboard, and the touchpad built into one, alongside a BLE keyboard and
a speaker (see *New in beta 8: Bluetooth Classic keyboards*). On the wireless builds
I2S audio now shares the radio's PIO block, which leaves PIO1 free for your
own PIO programs on the WebMiteRP2350, PicoMiteHDMIWEB and PicoMiteHDMIBTH. A
module that wires the WiFi and Bluetooth chip to other pins than the Pico 2
W, such as Waveshare's RP2350B Pico WiFi, can now say so with `OPTION CYW43
PINS`. Sound no longer stalls while a program loads BMP, JPG or PNG images
(see *Fixed since beta 7*), and on the RP2350 a PNG of any size now loads,
cropped to the screen like a BMP or JPG. On an RP2350 with 16 MB of flash
the A: drive now keeps its files through `OPTION RESET` and a change to
another build, and on every build the A: drive moves to littlefs 2.11.3,
which closes several ways a power failure could damage it (see *Other changes
in beta 8*). A new companion manual, the
*MMBasic Performance Guide*, measures what makes a program faster.

Beta 7 added Bluetooth speakers and headphones to the PicoMiteRP2350BTH, and
a new build, the PicoMiteHDMIBTH, that brings Bluetooth keyboards, mice and
speakers to the HDMI PicoMite (see *New in beta 7*). The audio of these two
Bluetooth builds is I2S and Bluetooth only, with no PWM, SPI DAC or VS1053.
Beta 7 also made `CALL` with a SUB's name and compiled `PIXEL` faster (see
*Faster in beta 7*), and on the PicoMiteRP2350BT and PicoMiteRP2350BTH
Bluetooth no longer erases part of the A: drive at boot (see *Fixed since
beta 6*).

Beta 6 made the compiled code itself faster: on a PicoComputer 3 the TSCP
chess bench runs in 37.5 s instead of beta 5's 58.9, two game benchmarks 12%
and 25% faster and solar_eclipse 13%, most of it in SUB and FUNCTION calls,
`LOCAL`, loops and jumps, and arrays of two or three dimensions (see *New in
beta 6*). On the WebMites a WiFi join that fails straight after a `CPU

Beta 5 compiled much more of a typical program: `LOCAL` in all its forms and
`STATIC`, `TEXT`, `CIRCLE`, `BLIT` (`BLIT MEMORY` too) and the other drawing
commands, the built-in functions most used in loops (`TIMER`, `INKEY$`,

calls with array elements, constants or brackets, and dotted names; and a

*New in beta 5*). It also fixed `NEXT` in a recursive SUB or FUNCTION, and
programs with large arrays that stopped with `Not enough memory` on an RP2350
with PSRAM although memory was free (see *Fixed since beta 4*).

Beta 4 found SUBs, FUNCTIONs, labels and line numbers through one index on
every board, made the RP2040 PicoMiteVGA, PicoMiteVGAUSB and WebMite quicker,
gave every RP2350 build another 20 or 24 KB of heap and three RP2040 builds

Beta 2 fixed the problems reported with beta 1 (see *Fixed since beta 1*) and

Please run your own programs on this release candidate, first as they are

## New since RC3

- `I2C READ`, `SPI READ` and `ONEWIRE READ` (and their second-channel and
  slave forms) receive into a structure member, as on the CMM2: a string
  member, up to its own `LENGTH`, or a number, alone or in a list
  (`SPI READ 2, r.v, r.f`). A whole structure, or a member of an element of
  a structure array given alone, is still refused. Not on the
  PicoMiteRP2040MIN, which has no structures.

## Fixed since RC3

- `SPI READ` and `SPI2 READ` with no destination, as in `SPI READ 3`, used an
  argument that was never set, giving an odd error or worse. It is now
  "Invalid syntax" (issue #58).
- `I2C READ`, `SPI READ` and `ONEWIRE READ` (and their second-channel and
  slave forms) into a string checked the count only against 255, not against
  the string's `LENGTH`. A longer read wrote past the string: a short one
  lives inside its variable's record, so the read corrupted that record and
  the ones after it. It is now "Number out of bounds" (issue #59).
- WebMite TCP server: it could close a connection it had just accepted,
  before the request arrived, or in the middle of sending a page, because
  a time comparison wrapped. The browser got an empty reply, or the program
  stopped with "No response to request from connection no. n".
- WebMite TCP server and telnet: after a connection was reset or aborted,
  the error handlers closed a connection that lwIP had already freed or was
  freeing. An idle connection that timed out left a marker in its slot that
  `RUN`, `NEW` or `EDIT` then handed to lwIP as a connection. A request
  answered at the command prompt waited for its reply inside lwIP's own
  receive handler. A telnet client that disconnected stayed connected on the
  board until the board next wrote to it. Telnet output was sent four bytes
  at a time from a buffer that was refilled before lwIP had sent it.
- With `OPTION RTC AUTO ENABLE`, the hourly clock read at the command prompt
  took a temporary string that was never freed. After about 64 hours idle at
  the prompt the board reported "Not enough memory".
- The USB connect and disconnect chime, when it finished, closed the file
  number of the last WAV file played, which could be a file opened since,
  and before any WAV file had played it could raise an old file error.

## New in RC3: Print Screen

- The Print Screen key saves the display, at the command prompt, in the
  editor and in the file manager, as the CMM2's does: `SCREENnnn.BMP`, the
  first number not used yet, in the root of the SD card when one is
  configured, otherwise of A:. It is written by `SAVE IMAGE`, so it works on
  any display `SAVE IMAGE` can read. Nothing is printed and a failure is
  ignored, so the editor and the file manager are not disturbed. A serial
  terminal can send the key's code, the byte &H9D. Not on the
  PicoMiteRP2040MIN, which has no room for it.

## Faster in RC3

- **`MATH FFT`** runs about 20% faster and **`MATH FFT INVERSE`** about 25%: a
  1024-point transform takes 10.4 ms instead of 12.9 ms, and its inverse
  12.4 ms instead of 16.7 ms (WebMiteRP2350). The complex arithmetic in `MATH`
  is compiled inline rather than through the C library's general routines,
  which also frees about 4 KB of flash on every build. Results are unchanged;
  only a complex multiplication or division of infinite or not-a-number
  values can now give NaN parts where it gave an infinity.

## Fixed since RC2

- `WS2812` with an array smaller than the LED count read past the array and
  sent what followed it to the LEDs; it is refused with "Array too small"
  (issue #15).
- `RIGHT$(s$)` with one argument read an unset argument instead of saying
  "Argument count" (issue #16).
- `LIST`, `EDIT` and `SAVE` unfolded the tokeniser's rewrites inside longer
  names, so a user function `TOBASE$(16, x)` was listed and saved as
  `TOHEX$(x)` (issue #17).
- A space before the bracket defeated the function rewrites: `LEFT$ (a$, 2)`,
  `MAX (1, 2)` and `HEX$ (255)` stopped with "not declared". The rewrite now
  takes the spaces with the name (issue #18).
- A statement made of two adjacent operator tokens, such as `^^` or
  `IF 1 THEN ^^`, was dispatched as a command whose number lay past the end
  of the command table and called whatever was there. Only a token that
  names a command is dispatched as one (issue #19).
- `LMID` moved the whole array when the replacement changed the length,
  writing past its end, and allowed a section one byte beyond the string
  (issue #20).
- `REDIM` copied each argument into a 33-byte buffer without a terminator
  when the name and its dimensions reached 32 characters, as
  `REDIM PRESERVE sensor_readings(reading_count% + 1)` does (issue #21).
- A CSUB's interrupt vectors (`CFuncmSec`, `CFuncInt1` to `4`) and
  `INTERRUPT`'s SUB survived `NEW` and `RUN`, so the next program's tick or
  pin edge called into the old code. They are cleared with the rest of the
  runtime (issue #22).
- `LOAD IMAGE` drew a top-down BMP (a negative height) upside down (issue
  #23), and decoded a 16-bit BI_BITFIELDS BMP with a V4 or V5 header, as
  GIMP writes RGB565, with the wrong masks: the masks live inside such a
  header, and were skipped (issue #24).
- `PLAY ARRAY` freed the buffers of whatever was playing instead of
  refusing with "Sound output in use" (issue #25). A play-once `PLAY
  MODFILE`'s context was freed twice at its end (issue #26); `PLAY SOUND`
  took the phase increment from the channel's old waveform when switching
  to or from white noise (issue #27); `PLAY MODSAMPLE` with a volume of 0
  played at full scale (issue #28); on the VS1053 builds `PLAY HALT` saved
  the position of its own .mem file instead of the track's for a track on
  A: (issue #29); a `PLAY TONE` that failed its checks cut a running
  endless tone to 1000 samples (issue #30); the last buffer of a play-once
  MOD kept its earlier fill after the module ended, so a burst of earlier
  music followed the last note (issue #31); and a finished sound's
  interrupt fired again when a later `PLAY TONE`, `ARRAY` or `SAMPLE`
  without one ended (issue #32).
- `CHAIN`: the chained program's TYPE definitions and its multi-line `IF`
  jump table were built in the empty heap before the kept variables were
  copied back over them, so both could point into the old program's
  variables. Both are now built again from the restored heap. A chained
  program that uses structures must define the same TYPEs in the same order
  as the program that chained to it, as a kept variable of a structure type
  refers to its type by number (issue 9).
- `LOAD JPG`: an invalid `ximage`, `yimage` or `scale` was rejected only
  after the file had been opened, so each such error left a file number open
  and the eleventh gave "Too many files open". The values are now read before
  the file is opened, and the two offsets are checked against the image's
  size with the file closed.
- PicoMiteRP2350 with `OPTION LCD SPI` (which `OPTION PLATFORM PICOCALC` sets
  on that build): `PIXEL()`, `BLIT READ` and the other reads of an SPI panel
  came back with every colour bit one clock late, so each read and write
  cycle shifted the colours further. The slow read clock was never applied
  when the display had its own SPI, and the panel was read at its write
  speed, 50 MHz on the PicoCalc's ST7365P. The reads now run at 12 MHz, or
  6 MHz for the ILI9488 group, as on the other builds.
- Mounting the SD card closed every open file, the A: drive's included: a
  file opened on A: before the first access to B: (or the first after an SD
  card error) was gone, and the next `SEEK` or `LINE INPUT` on it gave "File
  number". Mounting B:, or the USB drive C:, now closes only the files open
  on that drive, whose records are stale, and file number 10 is no longer
  skipped.
- USB host builds: a keyboard with media keys can present two boot-keyboard
  interfaces, and the second took a HID slot of its own: the console showed
  "USB Keyboard Connected on channel 1" and again "on channel 4", the slot
  was polled for nothing (in the boot protocol every key arrives on the
  first interface) and a gamepad or second mouse had one slot fewer. An
  interface whose device already has a keyboard slot now takes none (issue
  36).
- PicoMitePC3: the firmware's flash boundary has moved up one 16 KB step,
  from 1728 KB to 1744 KB, because the fixes since RC2 did not fit. On the
  first boot after the upgrade the board finds its options moved, so it
  resets them and clears its flash slots and program memory; the A: drive,
  which has a fixed place on a 16 MB board, is kept. Run `OPTION RESET PICO
  COMPUTER 3`, set up WiFi again and reload your program. A PC3 already on
  the RC2 files refreshed on 17 October has the new boundary and keeps
  everything.
- `PRINT`: a comma writes a tab character, but the column `PRINT` kept for
  `TAB()` and `POS` moved to the next 14-column zone, so after a comma both
  were wrong: in `PRINT 1, 2; TAB(30); "e"` the e landed in column 24 on a
  terminal and `POS` overstated the cursor. The column now moves to the next
  8-column stop, where a terminal or a file viewer puts a tab. The screen
  pads a tab to `OPTION TAB`, so with its default of 2 it still differs
  (issue 37).
- `PRINT #n` to a file or a COM port used the console's column and left its
  own behind: `TAB()` in a file line counted from wherever the console's
  cursor was, and could break the file's line with a CR LF; afterwards
  `TAB()` and `POS` on the console were wrong and the prompt could gain or
  lose a blank line. Each file and COM port now keeps its own column from
  the moment it is opened, and the console's is untouched (issue 38).
- USB host builds: `DEVICE(MOUSE n, B)` and the mouse interrupt saw only the
  left, right and middle buttons, although with `OPTION MOUSE SENSITIVITY`
  set the firmware already decodes every button a mouse declares. The whole
  bitmap is now kept: bits 0 to 2 are left, right and middle, the higher
  bits the mouse's further buttons in its own order (a five-button mouse
  puts its side buttons in bits 3 and 4). In boot mode, without that option,
  a mouse reports three buttons.
- RP2350 builds with PSRAM: `FRAMEBUFFER LAYER` (and `LAYER TOP` in MODE 3
  and MODE 5) was refused with "Layer Buffer must be in tightly coupled RAM"
  whenever the layer was bigger than half the SRAM heap, because the
  allocator sent such a block to PSRAM outright even when the SRAM heap had
  the room: on the PicoMitePC3 a MODE 5 layer (76800 bytes) could not be
  made. A layer now takes the SRAM heap directly and is refused, with "Not
  enough RAM for the layer (n bytes)", only when the SRAM heap really cannot
  hold it. A 640x480 MODE 3 layer is 153600 bytes, more than the PC3's
  whole SRAM heap, so that one is still refused, now with the reason.
- RP2350 builds without PSRAM and without a display (a WebMite or a
  PicoMiteRP2350 used with only an SD card): `LOAD` or `RUN` of a program on
  B: failed with "Not enough memory for 314368 bytes" (the number varies with
  the build), however small the program, while the same file loaded from A:.
  The variable records the firmware keeps at the top of the heap were freed
  only after the file had been opened, which left the file's buffers in the
  middle of the heap and the free space below them one page short of the
  buffer `LOAD` needs. They are now freed before the file is opened.
- A `LOAD` (or `AUTOSAVE`, `EDIT`, `RUN` of a file) of a program too big for
  the program memory, typically a large program loaded without `,C`, left
  the part already written in flash with its names stored as symbols but

## New since RC1: OPTION RADIO on the PicoMitePC3

`OPTION RADIO BOTH | WEB | BLUETOOTH | NONE` chooses which halves of the
Pico Computer 3's wireless chip the next boot brings up, so the one build
serves as the all-in machine, a WebMite, a Bluetooth host or a plain HDMI
computer, with the half not in use costing nothing.

- **BOTH** is the default and lists nothing in `OPTION LIST`.
- **WEB** leaves the Bluetooth host out: no stack, no firmware download, no
  polling. The `BLUETOOTH` commands and `OPTION AUDIO BLUETOOTH` answer
  "Bluetooth is off (OPTION RADIO)".
- **BLUETOOTH** leaves the WiFi down: no join, no TCP, TFTP or UDP servers,
  no NTP. The `WEB` commands answer "WiFi is off (OPTION RADIO)".
- **NONE** leaves the chip unpowered and untouched. Its four pins are
  ordinary I/O, and the heartbeat LED is on GP25, as on the PicoMiteHDMIUSB;
  `OPTION HEARTBEAT OFF` and `ON` act on it there.

The stored network and the Bluetooth pairings are kept, so any setting can
be changed back; the Bluetooth host cannot be switched off while the audio is
on Bluetooth. The setting is saved and the firmware restarts. Measured at
315 MHz, solar_eclipse runs in 14.15 s with NONE, the PicoMiteHDMIUSB's
speed, 14.57 s with WEB and WiFi joined, 15.11 s with BLUETOOTH and 15.04 s
with BOTH.

## New since RC1: the file manager plays a track list

Mark audio files in the file manager (`FM`) with the space bar and press
ENTER: when every marked item is an audio file, FM plays them in panel order
as a track list, the album that `PLAY WAV`, `FLAC`, `MP3` or `MIDI` builds
from a directory, so each track starts when the one before it ends. The
status line shows `Playing 2/5 name` and follows the track that is playing;
`.` or `>` skips to the next track and `,` or `<` returns to the previous
one, as `PLAY NEXT` and `PLAY PREVIOUS` do, and `F6` or `T` stops the list.
A list may mix WAV, FLAC, MP3 and MID files and holds at most 20 tracks; MOD
files cannot be in one. With any other marks, ENTER acts on the selected item
as before.

A directory's album may now mix those four formats too: `PLAY NEXT`, `PLAY
PREVIOUS` and the start of the next track pick the decoder from each file's
extension rather than from the one that is playing.

Also since RC1: the file manager shows a cursor at its text prompts (rename,
new file, new directory, filter, type-select); and `PLAY WAV`, `FLAC`, `MP3`
or `MIDI` on a directory takes the drive from the name, so
`PLAY FLAC "B:/music"` plays from A: as well. Before, the directory was only
found when its drive was the current one, and the command reported "Could
not find the file".

## New since RC1: BLUETOOTH CONNECT SPEAKER, SERIAL and KEYBOARD

On the Bluetooth host builds (PicoMiteRP2350BTH, PicoMiteHDMIBTH and
PicoMitePC3), `BLUETOOTH CONNECT` chooses what a device is by its Class of
Device: a keyboard, an audio device, or anything else, which is asked for a
serial port and otherwise tried as a speaker. A device that is two things at
once got only one of them. An RN52 module, for example, is a speaker with a
serial port, and does not present itself as an audio device, so `BLUETOOTH
CONNECT` always took its serial port, and a second one stopped with "Serial
device already connected". A word in front of the name now says which:

```
BLUETOOTH CONNECT SPEAKER "RN52-98F5"     ' as a speaker
BLUETOOTH CONNECT SERIAL "RN52-98F5"      ' its serial port, as COM7
BLUETOOTH CONNECT KEYBOARD "My Keyboard"  ' as a Bluetooth Classic keyboard
```

- **SPEAKER** connects the device as a speaker without asking it for a
  serial port. **SERIAL** connects its serial port, or stops with "The
  device has no serial port". One of each gives both at once, and each is
  remembered and reconnected as before.
- **KEYBOARD** is for a Classic keyboard whose Class of Device does not say
  it is one. On a device that is not a keyboard the connection is refused
  and `BLUETOOTH CONNECT` reports an error.
- `SPEAKER` and `SERIAL` take a PIN as before. A BLE device cannot be a
  speaker, and BLE keyboards pair by themselves, without
  `BLUETOOTH CONNECT`; both are reported. Without a word in front of the
  name, `BLUETOOTH CONNECT` works exactly as before. A string variable
  called `serial$` or `speaker$` is still a name.
- Tested with a speaker and a Bluetooth 3.0 keyboard. `SERIAL` opening a
  real serial port has not been tested yet.

## Changed since RC0: Bluetooth speakers, car radios and PINs

Three changes on the PicoMiteRP2350BTH and PicoMiteHDMIBTH, for the
tester's Milwaukee M12 site radio and car radios. None has been tried on
those devices yet, so please report how they behave.

- **The stream to a speaker starts as soon as it connects**, whatever

## New since RC0: the PicoMitePC3

A version of the firmware built for the Pico Computer 3 alone, which puts
everything the PC3's hardware can do in one image: the PicoMiteHDMIUSB's HDMI
video (the full set of resolutions and modes, USB keyboards, mice and game
controllers, the OV7670 camera), the PicoMiteHDMIWEB's WiFi (TCP, UDP, TLS,
MQTT, NTP, TFTP, the web server) and the PicoMiteHDMIBTH's Bluetooth
(keyboards, mice and game controllers, speakers and headphones, serial
devices on `COM7`). It needs the PC3's PSRAM and is not for other boards.

- **Program memory is 256K**, against 180K on the PicoMiteHDMIBTH and 156K on
  the PicoMiteHDMIWEB. The editor, `LOAD`, `AUTOSAVE`, `LIBRARY` and the
  XModem, YModem and ZModem program transfers take their buffers from the
  PSRAM, so a 250K program can be edited and saved. With the PSRAM disabled
  (`OPTION PSRAM PIN DISABLE`) only a program that fits in the internal
  memory can be loaded.
- **The PSRAM reserve is 2.5 MB** rather than 2 MB, for the bigger context
  area and RAM program slots that the 256K program needs; `MM.INFO(PSRAM
  SIZE)` reads 5767168 on an 8 MB part.
- **WiFi and a Bluetooth speaker share one radio.** While a speaker is
  playing, the radio gives the sound priority (otherwise it broke up as soon
  as WiFi was merely associated); a WiFi transfer slows to a crawl until the
  sound stops and recovers the moment it does. A speaker that is connected
  but silent costs WiFi nothing.
- **It is as fast as the PicoMiteHDMIBTH**, within 2% on solar_eclipse and
  the game benchmarks, and 7 to 9% behind the PicoMiteHDMIWEB; the
  difference is the Bluetooth host's polling, which every Bluetooth host
  build pays. Running the heap in PSRAM costs about 1%.
- No PWM, MCP48n2 or VS1053 audio (sound goes through the PC3's I2S DAC or a
  Bluetooth speaker), no YModem on the USB console (the console is a serial
  port on the PC3; XModem and ZModem work as on every build), and no PS/2 or
  I2C keyboard, the same as the PicoMiteHDMIBTH.
- `MM.DEVICE$` reads `PicoMitePC3 RP2350B` and the sign-on is `PicoMitePC3`.
  Loading it over another version resets the options and wipes A:; the PC3
  configures itself again at the next boot (`OPTION RESET PICO COMPUTER 3`
  applies the preset by hand).

## New in RC0: ZMODEM

`ZMODEM` moves a program or a file between the board and your computer over
the console, the USB console or a serial one. It takes the same forms as
`XMODEM` and `YMODEM`, on every build:

```
ZMODEM SEND                  ' the program in memory
ZMODEM SEND "B:/data.csv"    ' a file on A:, B: or C:
ZMODEM RECEIVE               ' a program into program memory
ZMODEM RECEIVE "B:/data.csv" ' a file
ZMODEM RECEIVE "B:/dl/*"     ' any number of files, under the sender's names
ZMODEM CRUNCH                ' a program, without comments, blank lines and spaces
```

- **It recovers instead of failing.** Every block carries a CRC-32 and its
  place in the file. When a block is lost or damaged the receiver asks for
  the data again from that point, so a poor connection slows a transfer
  down rather than stopping it. That matters most on a serial console,
  where nothing holds the sender back.
- **It is fast.** Over the USB console with Tera Term a 512 KB file takes
  about 2 seconds on an RP2350 and 3 seconds on an RP2040. Over a serial
  console it depends on the baud rate: through a PicoComputer 3's CH340 at
  750000 baud, about 70 KB a second. Some adapters, the CH340 among them,
  lose data on the way to the computer at 921600 baud; ZMODEM recovers, but
  750000 is faster.
- **At the other end** use Tera Term on Windows (File > Transfer > ZMODEM >
  Send or Receive), or `sz` and `rz` from the lrzsz package on Linux and
  macOS. The board waits 60 seconds for the other end to start, and a
  transfer cancelled there stops with `Cancelled by remote`.
- **Names.** `ZMODEM SEND` gives the computer the name of the file the
  program was loaded from, or `FILE.DAT`; `ZMODEM SEND file$` gives the
  file's name without its drive or directory. `ZMODEM RECEIVE file$` saves
  under `file$` whatever name the sender gives, and of a batch of files
  keeps only the first.
- **Many files at once.** `ZMODEM RECEIVE "*"` takes every file the sender
  offers and saves each one in the current directory under the sender's
  name (without any directory it sends), overwriting a file of that name.
  Put a directory in front of the `*` to receive into it, as in
  `ZMODEM RECEIVE "B:/dl/*"`. In Tera Term select all the files in the
  ZMODEM Send dialog; with lrzsz list them, as in `sz *.bas`. At the end it
  prints `Received 3 files, 221000 bytes`. If an error stops it part way,
  the files before it are complete and the error says how many there were,
  as in `The path name format is invalid (files received: 1)`.
- **Programs and files.** The file forms also work inside a program; the
  program forms are for the command prompt. A program too large for the
  receive buffer stops with `Not enough memory`, and the program in memory
  is left as it was. `SEND`, `RECEIVE` and `CRUNCH` can be shortened to
  `S`, `R` and `C`.

Four builds have moved their flash region up 16 KB to make room for ZMODEM
(the reset described at the top, and *Memory and flash layout*).

## New in RC0: Bluetooth serial devices on COM7

On the PicoMiteRP2350BTH and the PicoMiteHDMIBTH a Bluetooth serial device
can be the serial port `COM7`, much as a USB serial device is `COM3` to
`COM6`. It can be a Bluetooth Classic device with a serial port (the Serial
Port Profile), such as a Bluetooth GPS receiver, or a Bluetooth LE device
with a serial service: the Nordic UART Service (many modules, and the
console of a PicoMiteRP2350BT), an HM-10 module's `FFE0`, or Microchip's
Transparent UART.

- **Finding it.** `BLUETOOTH SCAN` lists a Bluetooth LE serial device as
  `BLE serial`; a Classic one is listed without a type. The type column is
  two characters wider.
- **Connecting.** `BLUETOOTH CONNECT "name"` (or the address) connects it:
  `Connected to serial device 00:19:01:2D:DC:BF (RFCOMM channel 1) as
  COM7`. A Classic device is paired as it connects, answering a PIN request
  with `0000`; a Bluetooth LE one is used without pairing unless it asks.
  The device is remembered, one at a time, and is connected alongside a
  BLE keyboard, a Classic keyboard and a speaker.
- **Using it.** `OPEN "COM7:" AS #1` or `OPEN "COM7:" AS GPS`, then as any
  serial port: a buffer size, an interrupt and its level work as for
  `COM1`, a baud rate is accepted and ignored, and `PRINT #` ends lines with
  CR and LF. With `AS GPS` the `GPS()` functions decode it, every sentence
  of every second included.
- **Staying connected.** While `COM7` is open the device is reconnected
  whenever it is not connected: when the port is opened, after it is
  switched off and on, and when it comes back into range. `CLOSE` leaves
  the link up. `BLUETOOTH DISCONNECT SERIAL` lets it go until `COM7` is next
  opened or the next `BLUETOOTH CONNECT`; `BLUETOOTH FORGET` forgets it.
- **Checking it.** `BLUETOOTH STATUS` has a `Serial:` line with the bytes
  received and sent, and `MM.INFO$(BLUETOOTH SERIAL)` gives the connected
  device's address, or an empty string, so a program can wait for it.
- **Tested** with a Dual XGPS150 GPS receiver (Classic) and a
  PicoMiteRP2350BT's console (BLE).
- **Good to know.** Some GPS receivers have a switch for use with an iPhone
  or iPad that hides their serial port: set it for other devices (on the
  Dual XGPS150, towards the USB connector). An older GPS can report a date
  1024 weeks too early, a fault in its own firmware (the GPS week
  rollover).
- **What it costs.** A fourth Bluetooth connection, RFCOMM and a second
  Bluetooth LE client: both builds' flash regions have moved up (the reset
  described at the top), and the PicoMiteHDMIBTH's heap is 4 KB smaller,
  220 KB.

The chapter *Bluetooth Versions* in the manual and `PicoMiteBT.pdf` describe
it in full.

## Fixed since beta 8

- Every build: `FLASH LOAD n` with another command after it on the same
  line, such as `FLASH LOAD 1:EDIT` typed at the prompt or held in an
  `OPTION F9` key, left that command looking at the names of the program
  that had been in memory before. `EDIT` and `LIST` showed the names as
  `?`, or the board hung or crashed, most often when the earlier program

  command after the load now sees the program just loaded. In beta 8, put
  the two commands on separate lines.

  and the PicoMiteRP2350BT): the console could lock up for good. USB
  stopped, the heartbeat stopped, and only a reset or a power cycle brought
  the board back. It took characters arriving one per USB packet, as when a
  PicoMite USB host prints to another PicoMite on its COM3 or a PC program
  writes byte by byte, and then happened within seconds; RP2040 boards did

  byte at a time over five minutes without a hitch.
- USB host builds: `OPEN "COM3:..."` to a USB serial device that refused
  the baud rate or the DTR/RTS setting still opened, and then nothing went
  either way, with no error at either end. It now stops with

  PicoMite at the other end only reads and writes its USB console while DTR
  is set.
- USB host builds: a serial adapter with a Prolific PL2303 chip was
  ignored. It now opens as COM3 to COM6, like FTDI, CP210x and CH34x
  adapters.
- WebMites (WebMiteRP2040, WebMiteRP2350, PicoMiteHDMIWEB): a TFTP request
  for `B:/name` was read from or written to the current drive instead of B:
  after an error, after leaving `EDIT` or an `XMODEM` transfer, or after a
  command with no arguments such as `CLS`. The drive in the request is now
  always the one used.
- WebMites: a TFTP transfer that failed, such as a request for a missing
  file or a missing directory, left the computer waiting until it timed
  out, set `MM.ERRNO`, and stopped a running program with an error it had
  not caused (`Could not find the file`); the next transfer was then
  refused. The computer now gets a TFTP error at once, the console shows
  `TFTP error:` and the reason, and a running program carries on.
- Every build: until the GPS sent a sentence with the date, `GPS(TIME)` and
  `GPS(DATE)` returned 48 characters of whatever was in memory. They now
  return `00:00:00` and `00-00-2000`.
- PicoMiteRP2350BT: the Bluetooth LE scan response no longer carried the
  Nordic UART Service's identifier, so anything that looks for the console
  by its service (a PC scanning with bleak, or the BTH builds'
  `BLUETOOTH SCAN`) did not see it. Phone terminal apps connect by name and

- Manual: `OPTION KEYBOARD` was said to ignore everything after the layout
  for USB and Bluetooth keyboards. Its caps lock, num lock and repeat

  manual on GitHub was replaced with this correction after the release.)

## New in beta 8: Bluetooth Classic keyboards

On the PicoMiteRP2350BTH and the PicoMiteHDMIBTH a Bluetooth keyboard no
longer has to be a BLE one. An older Bluetooth Classic keyboard, and the
touchpad or mouse built into one, now works alongside a BLE keyboard and a
Bluetooth speaker, all three connected at once.

- **Finding it.** Put the keyboard in pairing mode and run `BLUETOOTH SCAN`.
  It is listed as a `Keyboard`, as speakers are listed as `Audio`.
- **Pairing it.** `BLUETOOTH CONNECT "name"` (the name SCAN showed, or the
  address) pairs it. If the keyboard asks for a code, the console shows
  `Bluetooth keyboard pairing: type NNNNNN on the keyboard being paired, then
  Enter`, as it does for a BLE keyboard. After that the keyboard reconnects by itself
  whenever it wakes up or is switched on, also after the board restarts.
- **Keys and touchpad.** The keys go through `OPTION KEYBOARD` like a USB or
  BLE keyboard's: the layouts, the lock keys, auto-repeat and `KEYDOWN()` all
  work. A touchpad or mouse is `DEVICE(MOUSE 2, ...)`, the same as a BLE mouse.
- **Tablet keyboards.** Many low-cost keyboards sold for tablets have an
  operating-system mode, chosen with an Fn key combination or a switch (see
  the keyboard's instructions). Use its Windows or PC mode: in its iOS mode
  such a keyboard sends Cmd+arrow for Home and End and iPad shortcuts instead
  of F1 to F12, and its touchpad changes too.
- **`BLUETOOTH STATUS`** has a `Classic keyboard:` line: the keyboard's
  address, whether it is connected, and which of its reports carry the keys,
  the pointer and the media keys. `MM.INFO(BLUETOOTH KEYBOARD)` gives its
  address when no BLE keyboard is connected, and `BLUETOOTH FORGET` forgets
  it.
- **What it costs.** A third Bluetooth link and the HID code: the flash
  region has moved up 16 KB (the reset described at the top), and the MMBasic
  heap is 4 KB smaller, 320 KB on the PicoMiteRP2350BTH and 224 KB on the
  PicoMiteHDMIBTH.

## New in beta 8: Bluetooth speakers that work better

A tester tried beta 7's Bluetooth audio with four devices: a generic
receiver, a Milwaukee M12 site radio, a generic transmitter/receiver and a
car stereo. Only the receiver worked properly. These changes, on the
PicoMiteRP2350BTH and the PicoMiteHDMIBTH, are for the other three and for
speakers like them.

- **Speakers that pair, then refuse the sound** (`BLUETOOTH CONNECT` stops
  with `Bluetooth error 0x66`). Some devices agree a shorter encryption key
  than the board insisted on. It now accepts any length the Bluetooth
  specification allows, 7 to 16 bytes. The tester's transmitter/receiver,
  which gave these errors in beta 7, now works.
- **Speakers that connect but stay silent.** The board could put more sound
  in one packet than the packet's header can count, and it offered only
  stereo, which a speaker that plays only mono cannot take. Packets now hold
  at most 15 frames, and mono is offered too (stereo is still chosen
  whenever the speaker can play it).
- **A speaker that plays only if the sound starts as it connects.** The M12
  played if `PLAY` was already running when it connected, but stayed silent
  if it connected first. When a speaker closes the board's audio stream, or
  does not start it when asked, the board now connects to it again when
  `PLAY` next needs it. The sound waits for up to 8 seconds meanwhile, so it
  starts late (by 1.5 to 5.5 seconds in our tests) rather than being lost. If
  that does not help, the next try waits 20 seconds, then longer. We have
  not had an M12 to try this with. `OPTION AUDIO BLUETOOTH 0`, which keeps
  the stream running from the moment a speaker connects, is another thing
  to try with such a speaker.
- **Short gaps every few seconds** (the car stereo). The sound always went
  at the highest quality the speaker accepted, about 330 kbit/s. Over a link
  that could not carry that, the board fell behind until it had to drop a
  quarter of a second of sound. It now lowers the quality (the SBC bitpool)
  a step at a time while the link falls behind, and raises it again after
  ten seconds without trouble.
- **`BLUETOOTH STATUS` tells you much more about the speaker:** its packet
  size (`MTU`) and the frames in each packet, the quality in use (`bitpool
  41 (of 53)`) and how often it was lowered, packets the radio refused, how
  often the stream started, paused (and how many of the pauses the speaker
  made), was closed by the speaker, could not be started, and was reopened.
  If a speaker still misbehaves, a `BLUETOOTH STATUS` listing taken while it
  plays, or straight after a dropout, shows which of these it is. Please
  send us one.

**Other changes in beta 8:**

- **`OPTION CYW43 PINS`: modules that wire the wireless chip differently.**
  The WiFi and Bluetooth builds expected the radio on the Pico 2 W's pins,
  GP23 (power on), GP24 (data), GP25 (chip select) and GP29 (clock).
  `OPTION CYW43 PINS wl_on, wl_d, wl_cs, wl_clk` sets others. Waveshare's
  RP2350B Pico WiFi, for example, needs `OPTION CYW43 PINS GP36, GP37, GP38,
  GP39`, and connects to WiFi with it. The pins given are reserved, and
  GP23, GP24, GP25 and GP29 become normal I/O pins. `OPTION CYW43 PINS
  DEFAULT`, or `OPTION RESET`, goes back to the standard pins. An I2S DAC
  shares a PIO block with the radio, so its pins and the radio's data and
  clock pins must all be within GP0 to GP31 or all within GP16 to GP47. If
  the radio does not answer on the pins set, the board says `CYW43 radio
  failed to start on GP36,GP37,GP38,GP39 (OPTION CYW43 PINS)` (with the pins
  set) as it starts and carries on without WiFi or Bluetooth; the `WEB`
  commands then report `WiFi radio not running`. This is in the five
  RP2350 wireless builds: the WebMiteRP2350, PicoMiteRP2350BT,
  PicoMiteRP2350BTH, PicoMiteHDMIWEB and PicoMiteHDMIBTH. The
  WebMiteRP2040's pins stay fixed.
- **PNG images of any size, cropped, or part of one (RP2350).** The PNG
  decoder now works a line at a time, so a PNG needs about 40 KB of memory
  whatever its size, where it needed room for the whole file and the whole
  image (2.7 MB for an 800x500 picture), and it loads faster: that picture
  takes 1 second on a 320x240 screen instead of 3. `LOAD PNG` crops an image
  larger than the screen, as `LOAD BMP` and `LOAD JPG` do, instead of
  stopping with `Image too large`, and takes two more optional parameters,
  the first column and row of the image to show: `LOAD PNG fname$ [, x] [,
  y] [, transparent] [, alphacut] [, ximage] [, yimage]`. `SPRITE LOADPNG`
  takes `x_offset, y_offset, width, height` after `cutoff` to load part of
  an image, as `SPRITE LOADBMP` does: `SPRITE LOADPNG #n, filename$ [,
  transparent] [, cutoff] [, x_offset] [, y_offset] [, width] [, height]`.
- **RP2350 with 16 MB of flash: the A: drive stays where it is.** Every
  RP2350 build now lays out a 16 MB flash the same way: the firmware and its
  areas below 3 MB, a 1 MB MOD buffer, and a 12 MB A: drive from 4 MB to the
  end (see *Memory and flash layout*). Flashing a different build, `OPTION
  RESET` and the `OPTION RESET` presets keep the A: drive and its files; the
  options are reset as before. `OPTION MODBUFF` is not used on these boards
  (it says `The MOD buffer is fixed at 1024K with 16M of flash`): the 1 MB
  buffer is always there for `PLAY MODFILE` and `FLASH MODBUFF LOAD`, and the
  presets no longer ask before erasing everything. Boards with less flash
  are unchanged. The first boot of beta 8 reformats a 16 MB board's A: drive
  once (see the top).
- **The flash size is measured.** `OPTION FLASH SIZE` (`MM.INFO(OPTION
  FLASH SIZE)`) was the size the flash chip reports in its ID, which not
  every maker encodes the same way. That figure is now checked by reading
  past the end of the chip, as the PSRAM's size already was, and the size
  is measured at every boot.
- **The A: drive's file system is littlefs 2.11.3** (it was 2.5.1), which
  brings three years of littlefs fixes. A write cut short by a power failure
  is now caught by a checksum of the flash it went into, where before it
  could be read back as good data. On a drive more than half full, the first
  two blocks, which describe the drive, were rewritten so often that they
  could wear out first. A power failure could leave an "orphaned" file or
  directory, and tidying it up could loop for ever. `SEEK` to near the end
  of a 4 KB block could read back old data, and a file open twice, written
  through one number and read through the other, could read corrupted data.
  Names still ignore case. An A: drive written by an earlier version is
  kept, but the first write to it converts it to littlefs's newer format,
  which earlier firmware cannot read: going back to beta 7 or earlier
  reformats the A: drive, so copy anything you need first. The new littlefs
  is about 1.4 KB larger, which took the PicoMiteRP2040's flash region up
  16 KB, so that build resets on its first boot of beta 8 (see the top).
- **PicoMiteRP2350BT: a serial console beside the Bluetooth one.** This
  build has no USB, so a board whose Bluetooth link could not be used had no
  console at all. After a fresh install or any `OPTION RESET` the console
  now also runs on GP8 (TX) and GP9 (RX), UART1 at the console baud rate;
  on a PicoComputer 3 these pins go to the board's own USB-serial bridge.
  `OPTION LIST` shows it as `OPTION SERIAL CONSOLE COM2,GP8,GP9,BOTH`. A
  board upgraded from beta 7 keeps its options, so give it the console with
  `OPTION SERIAL CONSOLE GP8, GP9, B`. Keep the `B`: on this build it means
  Bluetooth and serial, and without it the Bluetooth console goes silent.
- **I2S audio shares the radio's PIO block on the wireless builds** (PIO2,
  or PIO1 on the WebMiteRP2040). That block is not available to your own
  PIO programs on these builds, and on the WebMiteRP2350, PicoMiteHDMIWEB and
  PicoMiteHDMIBTH PIO1 is now free for them. `OPTION AUDIO I2S` refuses pins
  the shared block cannot reach.
- **USB host: TinyUSB brought up to date.** The USB host builds now use
  TinyUSB's current development version instead of release 0.21.0. When a
  keyboard, mouse, game controller or flash drive behind a hub does not
  answer while it is being set up, TinyUSB now resets it and sets it up
  again. With four devices behind a PicoComputer 3's hub, all four came up
  after every restart, reset and power-on. Every other build uses the same
  TinyUSB for its USB console. Please tell us about any USB device that
  worked with beta 7 and does not now.
- **A new companion manual, `MMBasic_Performance_Guide.pdf`,** answers the
  common "how do I make it faster" questions with measurements on an RP2040
  PicoMiteVGA and an RP2350 PicoMiteHDMIWEB, interpreted and compiled:
  statements per line, `FOR` against `DO`, constants against variables,
  `CALL` by name, long names, and when the `MATH`, `ARRAY`, `SORT` and
  `MEMORY` commands pay. It is in the supplementary manuals zip with the
  others.
- **`PicoMiteBT.pdf`**, now titled *PicoMite Bluetooth Versions*, covers the
  two Bluetooth host builds as well as the PicoMiteRP2350BT: keyboards, mice
  and game controllers, speakers and headphones, pairings and `BLUETOOTH
  STATUS`.

## Fixed since beta 7

- Every build: sound played with `PLAY` (WAV, FLAC, MP3, MIDI, MOD, tones,
  sounds and arrays, and on the Bluetooth builds a speaker) stalled while
  `LOAD BMP`, `LOAD IMAGE`, `LOAD JPG` or `LOAD PNG` decoded a picture, and
  while `SPRITE LOADBMP`, `BLIT LOADBMP` or `SPRITE LOADPNG` read one. The
  decoders now keep the sound fed as they go. `FLASH LOAD IMAGE` into a
  flash slot still stops the sound: the flash is being written.
- RP2350: an interlaced PNG, or a damaged one, could crash `LOAD PNG` or
  `SPRITE LOADPNG`. They now stop with `Interlaced PNG not supported` or
  `Invalid or damaged PNG file`.
- RP2350: `LOAD PNG` did not refresh a buffered display (one with `OPTION
  REFRESH`), as `LOAD BMP` and `LOAD JPG` do.
- Every build: a `DIR$()` loop that `KILL`s or renames the files it finds on
  A: missed some of them (24 of 40 in a test), because `DIR$()` carried on
  reading a directory it had already closed. The directory now stays open,
  and up to date, until `DIR$()` returns an empty string.
- Every build: Ctrl-C at `KILL`'s `(Y/N)` question, or an error part way
  through `FILES`, or through `KILL` or `COPY` with a wildcard, left an A:
  directory open, and the next of these commands, or `CHDIR`, could then
  hang the board at its next write to A:. A directory left open this way
  is now closed before it is used again.
- PicoMiteRP2350BT, PicoMiteRP2350BTH and PicoMiteHDMIBTH: the radio was
  serviced from an interrupt that could fire 30,000 to 80,000 times a second
  and take 40 to 100% of the processor. I2S tones warbled and played on past
  their length, and the PicoMiteRP2350BT's heartbeat stopped. The radio is
  now polled from the main loop, as on the WiFi builds.
- PicoMiteRP2350BTH and PicoMiteHDMIBTH: when another device used the
  board's Bluetooth LE services, `BLUETOOTH STATUS` could report a keyboard
  pairing as failed (`status 0x13`) that never happened, and the board could
  disconnect the keyboard. Only the keyboard's own link counts now. A
  keyboard that drops its link while pairing or reconnecting is reported as
  "interrupted"; a sleeping keyboard does this as it is retried, which is
  normal.
- PicoMiteRP2350BTH and PicoMiteHDMIBTH: a Logitech Pebble Keys 2 K380s
  paired and connected but never typed. Its key report is 7 bytes, not the
  usual 8, and was ignored; the board now reads each keyboard's report
  layout from the keyboard itself. And while another Bluetooth LE keyboard
  was paired with the board, a keyboard that starts the pairing itself (the
  K380s again) could not pair at all: `BLUETOOTH STATUS` counted it as
  "interrupted" about once a second. It now pairs. `BLUETOOTH STATUS`'s
  `Last pairing` line gives the keyboard's address when a pairing fails,
  and the pairing prompt now says to type the number "on the keyboard being
  paired".
- PicoMiteRP2350BTH and PicoMiteHDMIBTH: a Bluetooth keyboard's Caps Lock
  LED came on for a moment and went out again, although Caps Lock stayed on:
  a keyboard waits for the computer to set its lock LEDs, and only USB
  keyboards were sent them. Bluetooth keyboards now are, for Caps, Num and
  Scroll Lock. On the PicoMiteHDMIBTH a Bluetooth keyboard's lock keys also
  sent the LED report to whichever USB device was plugged in first.
- PicoMiteRP2350BTH and PicoMiteHDMIBTH: while a speaker that had been
  switched off still counted as connected (the link takes up to 20 seconds
  to time out), the sound quality was lowered step by step for nothing, and
  `BLUETOOTH STATUS` could then report it lowered several times but its
  lowest value as the full one. A link that sends nothing at all is no
  longer taken for a slow one, and the lowest value counts since the last
  `BLUETOOTH STATUS`, like the number of times.
- PicoMiteHDMIBTH: a `RESOLUTION` change to another clock speed did not
  retune the radio's link, so at 378 MHz it ran at 63 MHz.
- Wireless builds: a clock change (`CPU SPEED`, or `RESOLUTION` on the HDMI
  builds) retuned every state machine on the radio's PIO block, so I2S audio
  on that block could then play at the wrong speed. Only the radio's state
  machine is retuned now.
- PicoMiteRP2350BT, PicoMiteRP2350BTH and PicoMiteHDMIBTH: I2S on GP32 or
  above could not work, because the radio had already fixed the PIO block's
  range of pins.
- Every build: a program that stopped with `Not enough memory` could leave
  the board printing the same error at the prompt for ever, until a hardware
  reset. It now stops once and gives the `>` prompt.
- Every build: after the reset button or a brown-out, `MM.INFO(BOOT)` said
  `Restart` if the board had last been restarted by `CPU RESTART` or an
  `OPTION` command, and the sign-on banner did not appear. It now gives the
  real cause, such as `Reset Switch`.
- WebMiteRP2040 (Pico W): `OPTION POWER` drives GP23, which on the Pico W is
  the radio's power-on pin, so `OPTION POWER PFM` switched the radio off. It
  now refuses with `GP23 is the wireless chip's power-on pin`.

## New in beta 7: Bluetooth speakers and headphones, and the PicoMiteHDMIBTH

The PicoMiteRP2350BTH can now play through a Bluetooth speaker or headphones
as well as take a Bluetooth keyboard. The manual covers it under *Sound
Output* (*Bluetooth Speakers and Headphones*) and in the Bluetooth Versions
chapter (*PicoMiteBTH - Bluetooth Speakers and Headphones*).

**A new build: PicoMiteHDMIBTH.** This is the PicoMiteHDMIUSB (HDMI display
and USB host) with the PicoMiteRP2350BTH's Bluetooth added: Bluetooth LE
keyboards and mice and Bluetooth speakers, with everything below. Like the
PicoMiteHDMIWEB it needs an RP2350 board with the Raspberry Pi wireless chip
(a Pico 2 W or similar). It takes programs of up to 180 KB and has a 228 KB
heap. The manual does not name it yet: what it says about Bluetooth on the
PicoMiteRP2350BTH applies to the PicoMiteHDMIBTH, and what it says about the
display and USB on the PicoMiteHDMIUSB applies too.

- **`OPTION AUDIO BLUETOOTH [idle]`** makes Bluetooth the board's audio
  output. Everything `PLAY` does (tones, `PLAY SOUND`, WAV, FLAC, MP3 and MOD
  files) goes to the speaker. With no speaker connected the sound is thrown
  away at the speed it would have played, so a program runs as it does with
  a wired output and nothing plugged in.
- **`idle`** (0 to 250 seconds, default 60) is how long the stream to the
  speaker stays open after the last sound. After that the next sound waits
  about half a second while it opens again. `0` keeps it open for as long as
  a speaker is connected.
- **`BLUETOOTH SCAN`** lists the devices in range, **`BLUETOOTH CONNECT
  name$`** pairs with one and connects to it by the name the scan showed (in
  any case) or by its address, **`BLUETOOTH DISCONNECT`** lets it go and
  **`BLUETOOTH STATUS`** reports the connection.
- **The board remembers the last speaker it played through.** With `OPTION
  AUDIO BLUETOOTH` set it connects to it again by itself a few seconds after
  a reset, and whenever it comes back in range, until `BLUETOOTH DISCONNECT`.
- **`BLUETOOTH FORGET`** deletes every stored pairing, keyboards and speakers;
  `BLUETOOTH FORGET addr$` deletes one device's.
- **`MM.INFO$(BLUETOOTH SPEAKER)`** and **`MM.INFO$(BLUETOOTH KEYBOARD)`** give
  the connected device's address, or an empty string.
- Encoding the sound for the speaker takes 12 to 14% of the processor at 200
  MHz while the stream is open.

Bluetooth keyboards also do better on both builds. A paired keyboard connects
again after a reset with a key press, without its pairing button, and when it
wakes up it uses its pairing instead of pairing afresh each time. A keyboard
that asks for a passkey when it pairs could not pair before; the board now
shows the six-digit code on the console to be typed on the keyboard, which
should let it pair. We have not had such a keyboard to try, so please tell
us how it goes if you have one.

**What the Bluetooth builds give up.** To make room the PicoMiteRP2350BTH no
longer has PWM audio (`OPTION AUDIO pin, pin`), the SPI DAC (`OPTION AUDIO
SPI`) or the VS1053 (`OPTION AUDIO VS1053` and the `PLAY` commands that need
it, such as `PLAY MIDI` and `PLAY STREAM`), and the PicoMiteHDMIBTH has none
of them either. Their audio outputs are I2S and Bluetooth. A PWM or SPI audio
option set by an earlier firmware is ignored: set `OPTION AUDIO I2S` or
`OPTION AUDIO BLUETOOTH` instead. The PicoMiteRP2350BTH's heap is 324 KB, 12
KB less than in beta 6; its program size and flash layout do not change.

## Faster in beta 7

- **`CALL` by name.** `CALL name$, arguments` calls a SUB whose name is held
  in a string, BASIC's answer to a C function pointer. It no longer spells
  out the statement's names before every call. On a PicoComputer 3 (315 MHz)
  a call takes 28.8 us instead of 40.0 interpreted, and 27.4 us instead of
  47.8 compiled, so a program that calls its SUBs through a table of names
  is no longer slower compiled than interpreted.
- **Compiled `PIXEL` and `COLOUR`.** The compiler runs these commands through
  two small routines that, after beta 6 made the compiler smaller, had come to
  share places in the processor's flash cache. They now sit together. A
  compiled loop that plots with `PIXEL` took 2.19 s in beta 6 and takes 1.95 s
  now (-11%); the chess bench and solar_eclipse are unchanged.

## Fixed since beta 6

- PicoMiteRP2350BT and PicoMiteRP2350BTH: at boot Bluetooth set up its
  pairing store in the last 12 KB of flash, which is the end of the A:
  drive, and erased a 4 KB sector there to do it, which could damage a file
  stored there. The pairings now live with the options, as the keyboard's
  already did, and Bluetooth writes nothing to the A: drive.
- PicoMiteRP2350BTH: a Bluetooth keyboard pairing or waking up while sound
  played could pause the sound and make an SD card read fail with `SDcard
  Removed`, because every save of its pairing held everything up for about
  160 ms. The pairings are now saved once the keyboard has finished, from
  the main loop.
- `OPTION AUDIO`: with `OPTION AUDIO I2S` set, the PWM, SPI and VS1053 forms
  were accepted too, leaving their pins reserved but silent and `OPTION
  LIST` showing only one output. They now give `Audio already configured`.

## New in beta 6: compiled programs run faster (RP2350)

Beta 6 compiles the same statements as beta 5 and every program behaves as
before; the compiled code runs faster. On a PicoComputer 3 (PicoMiteHDMIWEB,
315 MHz, `OPTION COMPILE ON`):

| Program | Beta 5 | Beta 6 | |
|---|---|---|---|
| TSCP chess bench, depth 3 | 58.9 s | 37.5 s | -36% |
| Exile's player physics | 15.7 s | 11.7 s | -25% |
| Elite's demo, 600 frames | 6.9 s | 6.1 s | -12% |
| solar_eclipse | 6.9 s | 6.0 s | -13% |

What made the difference:

- **Compiled code carries on compiled after a SUB or FUNCTION call.** In beta
  5 a flag that every return left set sent each following statement through
  the interpreter's own bookkeeping until a string was next freed, so a
  program that uses no strings, like the chess engine, paid for it on nearly
  every statement. This alone took 15% off the chess bench.
- **Loops and jumps.** `NEXT` and `LOOP` go straight back to the first
  statement of their loop, and the jump at an `ELSE`, a `CASE`, an `ELSEIF`
  and an `IF` that is false goes straight to its target, instead of finding
  that statement each time.
- **`LOCAL`.** The types in a `LOCAL` (`INTEGER`, `FLOAT`, `STRING`, a name's
  own `AS` type) are read once, when the program is compiled, instead of on
  every call. A `LOCAL` with no type still takes `OPTION DEFAULT`'s type when
  it runs.
- **Parameters and locals.** A SUB's or FUNCTION's integer and float
  parameters, a FUNCTION's result and its `LOCAL` integers and floats are
  made without searching for their names (on the RP2350, compiled or not).
- **Arrays of two and three dimensions.** An element such as `board(x, y)`
  or `c(1, k, j)` is found directly rather than through the general loop:
  about 80 processor cycles less for two indices and 110 for three.

The compiler is also built smaller, which gives every RP2350 build 10 to 11
KB more room in flash for what comes next. No flash region moves, so the A:
drives stay as they are.

## Fixed since beta 5

- WebMite, WebMiteRP2350 and PicoMiteHDMIWEB: the first WiFi join after a

**What has changed.** We compiled every program we have, about 650 that run

- **`LOCAL` in all its forms, and `STATIC`.** A type after the name

## New in beta 4: SUBs, labels and line numbers found faster, and more memory

**What has changed.**

- **One index for every SUB, FUNCTION, CSUB and label.** When a program is
  made ready to run, MMBasic now builds a small index of the SUB, FUNCTION,
  CSUB and label names in the program and the library, the same way on every
  board. A name stored as a symbol was already found quickly; the index makes
  that true when a name has to be found by its spelling: a command typed at
  the prompt, `EXECUTE`, `CALL`, `ON ... GOTO`, `RESTORE`, a program run with
  `OPTION SYMBOLS OFF`. On the RP2040 such a lookup used to search through the
  program for a label, or through the SUBs one by one; on the RP2350 a fixed
  18 KB table held the names, where the index takes only what the program
  needs, a few hundred bytes for most programs.
- **Line numbers used as targets are indexed too.** The numbers after `GOTO`,
  `GOSUB` and `RESTORE`, after `THEN` or `ELSE` or `GOTO` in an `IF`, and in an
  `ON ... GOTO` or `ON ... GOSUB` list go in the same index, so jumping to a
  numbered line no longer searches the program from the start. Only the
  numbers a program jumps to are indexed, so a long program with line numbers
  takes no more memory than it needs. A target worked out while the program
  runs (`GOTO 100 + n`) is searched for as before.
- **The RP2040 PicoMiteVGA, PicoMiteVGAUSB and WebMite are quicker.** These
  builds keep much of MMBasic in flash, whose speed depends on where each
  routine happens to sit. Finding a variable, calling a SUB or FUNCTION and
  `IF` now run from RAM, and on every RP2040 build so does double-precision
  arithmetic.
- **More memory.** The 18 KB table has been given to the heap, and so has
  most of the RAM freed by moving the rarely used complex-number arithmetic
  into flash: every RP2350 build has 20 or 24 KB more heap than in beta 3, and
  the RP2040 PicoMite, PicoMiteUSB and PicoMiteMIN 4 KB more. The
  PicoMiteHDMI, PicoMiteHDMIUSB and PicoMiteHDMIWEB also take programs 4 KB
  larger (see *Memory and flash layout*).
- **SUBs and FUNCTIONs with parameters use less memory.** A program that calls
  40 SUBs of two parameters each needs about 3 KB for their parameter lists
  instead of 11 KB.
- **`AUTOSAVE` keeps the symbols of a large program on the RP2040.** A program
  of about 500 names sent with `AUTOSAVE` was stored without its symbols, and
  ran slower than the same program loaded from a file; now it has them.

**What you gain.** Measured at 315 MHz:

| | beta 3 | beta 4 | |
|---|---|---|---|
| RP2040 PicoMiteVGA: Solar eclipse | 27.1 s | 25.2 s | 7% less |
| RP2040 PicoMiteVGA: PETSCII Robots, time to update a frame | 59.3 ms | 56.3 ms | 5% less |
| RP2040 PicoMiteVGA: `GOSUB` to a numbered line at the end of a 100-line program, per loop | 77 us | 58 us | 24% less |
| RP2040, a name found by its spelling: `GOTO` a label 300 lines away | 60 us | 6 us | |
| RP2040, a name found by its spelling: calling a SUB in a program of 200 | 28 us | 15 us | |
| PicoComputer 3: Solar eclipse | 16.0 s | 15.6 s | 3% less |

The RP2040 measurements above were taken before `SUB` and `FUNCTION` calls,

**What to know.**

- **A label belongs to the library and the program together.** The same label
  in both is now an error, `Duplicate label`, reported when the program is
  run, and so is the same label twice in one program (until now the second
  was silently ignored). Rename one of them.
- **Labels no longer count towards the limit on SUBs and FUNCTIONs.** On the
  RP2350 the limit is now 512 SUBs, FUNCTIONs and CSUBs (it was 511 SUBs,
  FUNCTIONs and labels together); the RP2040 keeps 256. Labels are limited
  only by memory.
- **`FM` clears memory when it starts**, as `EDIT` does: the variables of the
  program that ran last are cleared, so the file manager always has the
  memory it needs.
- **`EDIT FILE` and the editor in `FM` switch off `IR` and `KEYPAD`** if a
  program left them running, because the editor uses the memory they write
  to. The program's variables are kept, as before.

## New in beta 3: more memory for your programs

**What has changed.** Until now MMBasic set aside a fixed block of memory for
variables when the board started: room for every variable a program could
ever have, whether it used five or five hundred. That block was 27 KB on the
RP2040 builds and up to 49 KB on the RP2350, and nothing else could use it.
In beta 3 a variable takes its memory from the same pool as strings and
arrays (the heap), and only when the program creates it. The memory comes
in small groups of 32 variables, and the block that used to be reserved has
been added to the heap.

**What you gain.**

- **More memory on every board.** The heap is 20 to 24 KB larger on the
  RP2040 builds and 40 to 56 KB larger on the RP2350: for example 120 KB
  instead of 100 KB on the RP2040 PicoMiteVGA, and 344 KB instead of 300 KB on
  the RP2350 PicoMite. That is room for bigger arrays, more strings, sound
  buffers and framebuffers. *Memory and flash layout* lists every build.
- **A program pays only for the variables it has.** A program with 40
  variables uses memory for about 40, not for 500 empty places. `MEMORY`
  shows the variables' share as it grows.
- **Faster programs that were short of memory.** V7 is quicker because it
  remembers where every name's variable is (*symbols*), and those tables need
  memory. In beta 2 a program that was already short of memory had to switch
  them off with `OPTION SYMBOLS OFF`. Now most such programs have room for
  them. The logic analyser that prompted `OPTION SYMBOLS OFF` now runs with
  its symbols on an RP2040 PicoMiteVGA, and its main loop takes 81 ms
  instead of 110 ms: more than a third faster.
- **Nothing to change in your programs.** The number of variables you can
  have is the same as before, `OPTION LOCAL VARIABLES` works as it did, and
  local variables only use memory while a SUB or FUNCTION is running them.
  The PicoMiteHDMIWEB also takes programs of up to 152 KB instead of 144 KB.

**What to know.**

- Making a variable can now fail with `Not enough memory` if the program has
  used up all the heap, just as `DIM` of an array always could. Room for the
  first 32 global and 32 local variables is set aside when the program
  starts, so small programs never meet this.
- On the RP2040 a program runs one to two per cent slower than it would have
  with the old fixed block, if it gains nothing from the extra memory. The
  RP2350 is no slower.
- `PEEK(VARTBL, n)` and `POKE VARTBL` have gone, because there is no longer
  one table to look into. They stop with an error that points to
  `PEEK(VARHEADER var)`, which still gives a variable's details.

## Faster on every board

**Names are stored as symbols.** When a program is saved, every variable, SUB,
FUNCTION and label name becomes a two or three byte symbol, and the
interpreter finds what a symbol refers to directly instead of searching for
the name each time. `LIST` and `EDIT` show every name exactly as you typed it,
and a program saved to a file is plain text as before. The tables that link
the symbols to what they name take a few KB of memory; if a program written
for an earlier version now runs out of memory, see *Programs that need all
their memory* below.

**Local variables live on a stack.** A SUB or FUNCTION's parameters and
`LOCAL` variables are made on entry and dropped on exit without searching or
tidying a table, and each SUB's parameter list is read once rather than on
every call. Calling a SUB or FUNCTION costs much less than it did: loops of
calls are 12% to 39% quicker on a PicoComputer 3 and 17% to 55% on an RP2040.

**`LOCAL` strings and arrays are made faster when the heap is full**: finding
room for them no longer walks past every block already in use.

Measured on an RP2040 PicoMiteVGA at 378 MHz, compared with V6.03.01:

| program | V6.03.01 | V7.0.00b1 | |
|---|---|---|---|
| PETSCII Robots, time to update a frame | 64.7 ms | 54.6 ms | 16% less |
| Solar eclipse | 28 s | just under 23 s | about 18% less |

## Programs that need all their memory: `OPTION SYMBOLS OFF`

**Why it is needed.** The speed that symbols bring comes from tables that V7
builds every time a program is run. For every name in the program they record
where its variable, SUB, FUNCTION or label is, so the interpreter never has to
search for it. The tables live in the same memory as the program's variables,
strings and arrays and take about 20 bytes for each name plus a fixed part:
typically 3 to 5 KB. On an RP2350 with PSRAM most of that is put in the PSRAM,
but on an RP2040, or an RP2350 without PSRAM, it comes out of the memory the
program has for itself (100 KB on the RP2040 PicoMiteVGA). A program written
for 6.04 or earlier that used nearly all of that memory, with a framebuffer,
large arrays, a PIO ring buffer or sound buffers, can now stop with
`Not enough memory`. A logic analyser sent in by a beta tester did exactly
that on an RP2040 PicoMiteVGA. (Beta 3 gives every build 20 to 56 KB more
memory, so most programs that needed `OPTION SYMBOLS OFF` no longer do: see
*New in beta 3*. Try your program without it first.)

**Using it.** Put

```
OPTION SYMBOLS OFF
```

on a line of its own at the top of the program. Only blank lines, comment
lines and a `LIBRARY LOAD` may come before it, and a `LIBRARY LOAD` can equally
come after it. When the program is run the tables are not built, and the
memory they would have taken is the program's. Only that program is affected:
nothing is saved in the options, and every other program still gets the
tables. The program itself does not change (it is still stored with symbols,
and `LIST`, `EDIT` and `SAVE` behave as before), so the line can be added or
removed at any time. It cannot be typed at the command prompt
(`Invalid at command prompt`), and lower down in a program it stops with
`Must be at the top of the program`.

**When to use it.** Only for a program that runs out of memory, and you do not
have to guess. When a program runs out of memory for a request no larger than
the tables, the error message says so:

```
Error : Not enough memory for 1920 bytes: put OPTION SYMBOLS OFF first
```

With the line added, the logic analyser starts with 44800 bytes free instead
of 39936 and runs normally.

**What it costs.** Speed. Without the tables every name is found as in earlier
versions, and a little more slowly because it is stored as a symbol. The
interpreter's micro benchmarks (36 kinds of statement, each timed on its own)
on an RP2040 PicoMiteVGA at 315 MHz took, added together:

| | time per statement, all 36 added | compared with 6.04.00 |
|---|---|---|
| 6.04.00 | 844 us | |
| V7, tables built | 666 us | 21% less |
| V7 with `OPTION SYMBOLS OFF` | 880 us | 4% more |

The largest differences are in calls to a SUB or FUNCTION with parameters (a
SUB with six parameters and four `LOCAL`s takes 89 us with the tables, 138 us
without them and 122 us in 6.04.00), in `GOSUB` (4.5 us against 39 us) and in
long names. On an RP2350 a program with the line is not compiled:
`MM.INFO(COMPILE)` reports `TEXT: OPTION SYMBOLS OFF`.

Type it at the command prompt; it takes effect at the next `RUN`, and it is
saved with the other options, so it stays in force after a restart until you
change it. `OPTION LIST` shows it when it is `ON` or `SHADOW`, and `OPTION DISK
SAVE` and `OPTION DISK LOAD` carry it.

At `RUN` the firmware compiles the program, and its library if there is one,
into a *stream* of native operations held apart from the program. It compiles
only when the program or library has changed since the last compile, so the
first `RUN` after an edit takes a moment longer (about 0.3 s for a 110 KB
program on a PicoComputer 3) and later runs start as quickly as the
interpreter. Statements the compiler cannot take stay in the stream as
references to your text and run on the interpreter, interleaved with the
compiled ones, so a program never has to be entirely compilable to benefit.
Nothing about the program changes: `LIST`, `EDIT`, `SAVE`, error messages and
line numbers, `TRACE`, `ON ERROR`, interrupts, `CHAIN` and libraries all
behave as before.

A program runs entirely as text when:

- it starts with `OPTION SYMBOLS OFF`:
  `MM.INFO(COMPILE)` says `TEXT: OPTION SYMBOLS OFF`;
- it was saved without symbols: `TEXT: saved without symbols`;
- its stream would not fit the space kept for it:
  `TEXT: too big for the slot (n of m bytes)`. A stream is typically 1.4 to 3
  times the size of the program (Exile 1.44, PETSCII Robots 1.72, the
  reference benchmark 1.85, Elite 2.87), and the space kept is three times
  the maximum program size, so every program that fits in memory should
  compile.

### Checking a program with SHADOW

`OPTION COMPILE SHADOW` runs the program compiled, and wherever the compiler
has worked out a value - the right-hand side of an assignment, an `IF` or
`ELSEIF` condition, a `DO` or `LOOP` condition, a `BOX`/`LINE`/`PIXEL`/`COLOUR`
argument - it works it out again with the interpreter and compares the two.
If they differ in any bit the program stops at that line:

```
[120] y = a * Sin(t) + b
Error : SHADOW: compiled 3.5, text 3.25
```

It is slower than `ON`, since every checked value is worked out twice, and
switching between `ON` and `SHADOW` recompiles at the next `RUN`. A statement
that calls a user FUNCTION or uses `RND`, `TIMER`, `INKEY$`, `KEYDOWN(`,
`MATH(RAND)` or `MM.INFO(` is not checked, because the interpreter would make
the call again or get another value. If a
program behaves differently under `OPTION COMPILE ON`, running it under
`SHADOW` is the quickest way to find where.

### Known differences from the interpreter

- If a FUNCTION `ERASE`s a variable that the statement calling it goes on to
  use after the call, the interpreter quietly makes the variable again; a
  compiled statement stops with `A FUNCTION changed a variable of this
  statement`. A FUNCTION that erases or creates other variables is fine.
- If a FUNCTION changes `OPTION DEFAULT` while another untyped FUNCTION is
  still to be called in the same statement, the statement stops with `OPTION
  DEFAULT changed by a FUNCTION in this statement`.
- Programs run faster, so a program that relies on how long its statements
  take (a delay loop rather than `PAUSE`) will run differently.

### Speed

Times as text and compiled on the same board and firmware (PicoComputer 3,
RP2350 at 378 MHz; the first two with the HDMIUSB build, the rest with
HDMIWEB):

| program | interpreted | compiled | |
|---|---|---|---|
| landscape (untyped FUNCTION in the inner loop) | 78.5 s | 21 s | 3.7x |
| torus (nested loops, `IF` and `PIXEL`) | 40.5 s | 7.8 s | 5.2x |
| galaxy (SIN/COS per point), per point | 255 us | 80 us | 3.2x |
| reference benchmark | 15.4 s | 7.1 s | 2.2x |
| Elite, per frame | 22.6 ms | 11.0 ms | 2.1x |
| Prince of Persia port, per frame | 9.7 ms | 6.7 ms | 1.4x |
| PETSCII Robots, frame update | 36.0 ms | 23.4 ms | 1.5x |

Where the gain is smaller, the time goes on work the compiler cannot make
faster: the maths library (a `SIN` or a `^` costs the same compiled or not),
the drawing itself, and statements that are not compiled yet. In the galaxy
program, once compiled, about a quarter of the time is in `SIN`, `COS`, `LOG`
and `^`, and a fifth in `PIXEL`.

### Where the stream is kept, and memory

- **With PSRAM** the stream is kept in the part of PSRAM the firmware already
  reserves, above the five RAM slots. None of your PSRAM heap or RAM slots is
  used, and it is lost at power-off (the next `RUN` compiles again).
- **Without PSRAM** it is kept in a hidden area of flash straight after the
  program, three program sizes long. It is rewritten only when the program
  has changed since its last compile, so an edit-and-run costs one erase of
  it, as saving the program already does. This area is why the A: drive is
  smaller on the RP2350 builds (see *Memory and flash layout*).
- The compiler borrows some temporary memory while it compiles and returns it
  before the program starts; while the program runs it uses none of the
  heap. It does not reduce how deeply SUBs and FUNCTIONs can recurse:
  compiled code recurses as deep as the interpreter or deeper.

## What compiles

Anything not listed here runs on the interpreter exactly as before. A
statement that the compiler cannot take in full runs as text as a whole; the
statements around it are still compiled.

### Statements

| statement | compiled when | runs as text |
|---|---|---|
| assignment (`LET`, or `name = ...`) | the target is a numeric or string variable or a numeric array element, and the right-hand side is an expression the compiler takes (below) | a string array element, a structure member, a whole-array assignment |
| `IF ... THEN ... [ELSE ...] ENDIF`, `ELSEIF` | multi-line, with any number of `ELSEIF` arms | |
| single-line `IF ... THEN ... [ELSE ...]` | the parts after `THEN` and `ELSE` are assignments; or, with no `ELSE`, the part after `THEN` is any statement (which then runs compiled or not on its own merits) | `IF ... THEN GOTO`, `THEN` followed by a line number, an `ELSE` whose parts are not assignments |
| `FOR ... TO ... [STEP ...]`, `NEXT` | the loop variable is a numeric variable | a user FUNCTION call in the start, limit or step |
| `DO [WHILE / UNTIL ...]`, `LOOP [WHILE / UNTIL ...]` | | a user FUNCTION call in the condition |

### Expressions

- **Operators:** `+ - * /`, `\`, `MOD`, `^` (when the left operand is a
  float), `= <> < > <= >=`, `AND OR XOR`, `NOT`, `INV`, `<<`, `>>`, unary `-`
  and `+`; `+` and the comparisons on strings. An integer `^` runs as text.
- **Literals:** decimal numbers, hexadecimal, octal and binary numbers
  (`&HFF`, `&O17`, `&B101`), and strings of up to 64 characters with no
  backslash.
- **Variables:** integer, float and string variables, global or local,
  including parameters, `STATIC` variables and constants; numeric array
  elements of any number of dimensions, with any expression as the index;
  dotted names (`R.running`) in a program that defines no `TYPE`. Not string
  arrays or structure members.
- **Built-in functions:** `SIN COS TAN ATN SQR EXP LOG DEG RAD INT FIX ABS SGN
  PI RND`; `ASIN ACOS ATAN2 CINT MAX MIN`; `LEN ASC CHR$ MID$ STR$ SPACE$
  LEFT$ RIGHT$ UCASE$ LCASE$ HEX$ OCT$ BIN$`; `INSTR` with two strings or a
  start position and two strings; `TRIM$` with one or two arguments;
  `RGB(r, g, b)` and `RGB(name)`; `MAP(n)`; `PIXEL(x, y)`; `KEYDOWN(n)`;
  `TIMER`, `INKEY$`, `DATE$`, `TIME$` and the other functions with no
  argument; the integer `MM.` values (`MM.HRES`, `MM.VRES`, `MM.FONTWIDTH`,
  `MM.FONTHEIGHT`, `MM.HPOS`, `MM.VPOS`, `MM.ERRNO`, `MM.ERRLINE` and the
  rest); `PEEK(BYTE|WORD|SHORT|INTEGER|FLOAT address)` and `PEEK(VAR name,
  offset)`; `MATH(RAND)`; `CHOICE(condition, a, b)` when `a` and `b` have
  one type; `MM.INFO(...)` with `FONTWIDTH`, `FONTHEIGHT`, `FONT`, `FCOLOUR`,
  `BCOLOUR`, `HEAP`, `HPOS`, `VPOS`, `WRITEBUFF`, `STACK`, `UPTIME`, `PATH`,
  `SOUND`, `CPUSPEED`, `ERRNO`, `ERRMSG`, `LCDPANEL`, `SYSTEM I2C`, `FLASH
  ADDRESS n`, `FILESIZE f$`, `PINNO pin`, `DISK SIZE`, `FREE SPACE`, `PS2`
  (on a build without a USB keyboard) and, on a WebMite, `IP ADDRESS`, `MAX
  CONNECTIONS` and `TCPIP STATUS`;
  `VAL(s$)` as the whole right-hand side of an assignment. These follow
  `OPTION ANGLE` and give the same errors as the interpreter. An argument
  may not call a user FUNCTION or be left empty.
  Not compiled: `VAL` anywhere else, `STRING$`, `PIN`, `EVAL`, `MM.INFO` with
  other keywords, `PEEK`'s other forms and the rest.
- **User FUNCTIONs:** any number of calls in an assignment, an `IF` or
  `ELSEIF` condition or an `INC` value, including calls inside another
  call's arguments. The FUNCTION must return a number: typed (`As Integer`,
  `As Float`, or a suffix) or untyped, when it takes the type `OPTION DEFAULT`
  gives it (float unless the program sets another). Arguments as for a SUB
  call. Not a FUNCTION returning a string or an array.

### New variables

A variable that does not exist yet is made by the interpreter, as always: the
first time a statement that makes it runs, that statement runs as text, and it
is compiled from then on. A single-line `IF` is not held back by a variable
that only its `THEN` or `ELSE` part uses: `IF k$ = "q" THEN quit = 1` runs
compiled on every pass, and only the pass that first sets `quit` runs as text.

## Seeing how much of a program runs compiled

**`MM.INFO(COMPILE)`** says what the last `RUN` did. Print it at the end of
the program, or type `PRINT MM.INFO(COMPILE)` at the prompt afterwards:

```
COMPILED 3 REUSED 1 STMTS 3227 RAN 714382 MISS 25707 CODE 680945 SIZE 132348 OF 966656
```

| field | meaning |
|---|---|
| `COMPILED n` / `REUSED n` | how many compiles, and how many runs that found the stream already compiled, since power-on. At the prompt the word is `NONE` instead of `COMPILED`. |
| `STMTS n` | statements in the stream |
| `RAN n` | statements the last run executed through the stream |
| `CODE n` | how many of those ran as compiled code |
| `MISS n` | internal: lookups of where to go next |
| `SIZE n OF m` | bytes of stream, of the space kept for it |

`CODE` divided by `RAN` is the share of the work done compiled: 680945 of
714382 is 95% here. It can also say `OFF`, or `TEXT:` and a reason (above).

**`OPTION PROFILING ON`** shows which statements ran as text. Put it as the
program's first line (it must be in the program: `RUN` clears it), make sure
the program finishes with `END` (the report is printed by `END`, not when a
program runs off its last line or is stopped with Ctrl-C), and run it with
`OPTION COMPILE ON`:

```
[PERF] elapsed=61247333 us  statements=772063  findvar=...  user_subs=46912  local_peak=19/192
[PERF] top commands by dispatch count:
      325725  Static
      323875  Loop
       56082  Blit Memory
        2172  FRAMEBUFFER
[PERF] top SUBs by exclusive (self) time:
       self_us    incl_us     calls   self_us/call  name
       7444555    7444555       719         10354  writeworld_n
```

With the compiler on, `statements` and the `top commands` list count only
the statements that ran as text, so the list is exactly what is left
uncompiled, command by command, busiest first. The SUB table shows where the
time goes, so you can tell whether what is left is in a busy SUB or in
start-up code. `local_peak` is the most local variables alive at once, of the
number available.

**`OPTION PROFILING ON, SAMPLE`** also samples where the processor is, and
`END` adds the busiest lines:

```
[PCSLINE] 29 4011
[PCSLINE] 23 3318
```

The first number is the line number, as the editor and error messages show it
(-1 for a line in the library); the second is how many samples landed on it. Together
with the command list this points at the lines worth changing, or worth
telling us about.

A typical session:

```
> OPTION COMPILE ON
> RUN
... the program, which starts with OPTION PROFILING ON and ends with END ...
> PRINT MM.INFO(COMPILE)
```

## A warning when the stack runs low

When a program has taken the stack to within 1 KB of its limit, the next
command prompt shows

```
Warning: the stack came within 536 bytes of its limit, at depth 12
```

where the depth is how many SUBs and FUNCTIONs were running. Deep recursion is
the usual cause: a simple recursive FUNCTION reaches about 13 levels on an
RP2350 and 9 on an RP2040 before `Stack overflow`, much as in 6.04.00. None of
the programs we test with (the reference programs, Exile, Elite, the Prince of
Persia port, PETSCII Robots and a corpus of 224 test programs) comes near it;
if one of yours shows the warning, please send it to us.

## Fixed since beta 2

- Commands that go on using a variable after the statement has finished
  (`IR`, `KEYPAD`, `PLAY STREAM`, `PLAY ARRAY`, `PLAY SAMPLE`, `PLAY LOAD
  SOUND`, `WEB TCP CLIENT STREAM` and its request string, `PIO DMA RX` and
  `TX`, `ADC RUN`, `ADC START` with an interrupt, `MATH PID INIT` and `GUI
  LISTBOX`) now refuse a `LOCAL` with `Must be a global variable`. A local is
  freed when its SUB returns, and the command went on writing or reading
  memory that by then belonged to something else. A global passed down to a
  SUB, and a `STATIC`, still work. The manual says so for each command.
- `WEB UDP INTERRUPT 0` switches the interrupt off; it gave `Line number`.
- After an `ERASE` had left every global slot used or blocked, looking for a
  name that was not there could hang at the top level, and inside a SUB gave
  `Too many global variables` although a slot was free.
- The count of variables (`MM.INFO(VARCNT)`, and the count a CSUB reads) could
  stay one too high after an error making a variable (`Not enough Global
  variable memory`, `Dimensions`, a `DIM` that ran out of memory), so a later
  `DIM` was refused with room to spare. `ERASE` and returning from a SUB now
  keep it right.
- Variable names, labels and SUB and FUNCTION names are at most 31 characters,
  as the manual has always said; 32 was accepted, and `LIST VARIABLES` then
  printed rubbish after the name.
- `MATH(CROSSING ...)` returns its index with `OPTION BASE` applied, so it
  agrees with the array's numbering under `OPTION BASE 1`.

## Fixed since beta 1

- `TEXT x, y, s$, C` and the other justifications written without quotes
  (`CM`, `RB` and so on) work in a program again, as they do at the command
  prompt; beta 1 stored the letters as a name and the text came out
  unjustified. `GUI CAPTION` had the same problem.
- A font defined with `DefineFont` in a program was not found when the program
  ran (`FONT #10` gave an error).
- `PIO MAKE RING BUFFER` in a program could fail with `Not enough aligned
  memory` on an RP2040 PicoMiteVGA although the memory was free: the search for
  an aligned block now tries every boundary, and the heap now starts on a
  256-byte boundary at the start of RAM.
- `PLAY WAV` with a file that is not 16-bit PCM (8-bit, 24-bit, floating point,
  A-law or mu-law) took 4 KB of free memory for every refill of its buffers, so
  with little memory left it stopped with `Not enough memory for 4096 bytes`,
  or the sound stopped part way through the file with no error. It now takes
  512 bytes, with no audible difference.
- A program containing a statement that is just a one-letter name (a call to
  `SUB a`, say) could not be saved when names were stored as text, and the board
  then stopped responding. It now saves and runs. (The same fix is on the 6.04 branch.)
- More generally, an error while a program was being written to flash left the
  board unresponsive part way through printing the message, while the display
  kept running. The message is now printed and the prompt returns. (The same
  fix is on the 6.04 branch.)
- When a program runs out of memory for a request that the symbol tables could
  have covered, the error message now says how to get it back:
  `Not enough memory for 1920 bytes: put OPTION SYMBOLS OFF first`.
- The manual's command list was missing `DO UNTIL condition ... LOOP` and
  `LOOP WHILE`; both have always worked.

A program that uses the same name for a variable and a SUB or FUNCTION stops
with `A sub/fun has the same name` on an RP2040, as it always has on the RP2350
and on the original MMBasic. This came in 6.04.00 RC2: before that the check
never fired on the RP2040, so such a program may have run there. Rename one of
the two.

## Fixed since 6.04.00 RC2

- RP2350 with PSRAM (a PicoComputer 3, for example): the board could stop with
  a hard fault, usually at the command prompt, after a program used `WS2812`
  or `BITSTREAM`, or after anything that writes flash (saving a program,
  writing a file on A:, changing an option). Before each of these the firmware
  tidied the processor's cache in a way that the RP2350's erratum E11 turns
  into wrong reads of the firmware's own code. On a PicoComputer 3 a short
  `WS2812` test faulted about one run in three; with the fix it ran 240 times
  without one.
- RP2350 with PSRAM: writing or closing a file on A: could throw away data a
  program had just stored in PSRAM (a large array or string could lose its
  most recent changes).
- `OPTION LOCAL VARIABLES` stayed in force after the program that set it had
  ended, so the next program ran with its split and could run out of global
  variables. `RUN`, `NEW` and `LOAD` put it back to the default; `CHAIN` keeps
  it for the chained program.
- An expression passed to a `BYVAL` parameter (`Inner 5, x()`) could be refused
  with `Array as BYVAL not allowed` when an unrelated local array happened to
  occupy the first slot of the variable table. Passing a whole array `BYVAL`
  is still refused, and an array element is still accepted.
- A float subtraction that overflows (`1e308 - (-1e308)`) stops with the same
  error as addition and multiplication, instead of giving `INF`.
- `LIBRARY LOAD` refuses a library too big for its flash slot. The size check
  could never fire, so a library whose text outgrew the slot would have been
  written over program memory.

**Program size.** Five RP2350 builds now take programs of up to 208 KB
rather than their heap size: the PSRAM reserve has to hold the five RAM
slots and three program sizes of stream. Every build's maximum program size
is now fixed, so the flash layout and the A: drive no longer move when the
heap grows. The PicoMiteHDMI and PicoMiteHDMIUSB are back to RC2's 160 and
152 KB, and the PicoMiteHDMIWEB rose from 144 to 156 KB; on these three each
4 KB of program takes 28 KB from A: (the program area, three flash slots and
three program sizes of stream).

**More heap: the variables live in it.** The variable table's fixed array (27
KB on the RP2040, up to 49 KB on the RP2350) is gone: a variable's record now
comes from the heap in chunks of 32 (1.75 KB on the RP2040, 2 KB on the
RP2350), and locals' chunks are kept for the run. The heap took the table's
RAM, leaving about 4 KB for the stack (see *New in beta 3*). For CSUB writers,
call-table entry 0x60 is now `g_slotrec`, the record of each variable number,
in place of the table itself (see `PicoCFunctions.h` and docs/armcfgen.md).

**Local variables.** Since locals live on a stack, the local region only
needs to hold the most locals alive at once, not a hash table's slack. Real
programs use far fewer than the space kept: the most we have measured is 125
(the reference benchmark); Exile 56, Elite and the Prince of Persia port about
44, PETSCII Robots 19. The RP2350 builds keep 192 local entries and have 64
more globals than before, so the total is the same or larger. The RP2040
builds keep RC2's 240 locals, except the WebMite, which has the RAM for 192.
`OPTION LOCAL VARIABLES` moves the split as before, and now returns to the
default at `RUN`, `NEW` and `LOAD` rather than staying in force for the next
program (`CHAIN` keeps it). `local_peak` in the `OPTION PROFILING` report
shows what a program actually uses.

## Everything in 6.04.00 RC2

V7 includes all of 6.04.00 RC2. Its release notes follow as they were
published, for anyone coming from an earlier version.

**Release candidate.** V6.04.00 gathers everything since V6.03.00: the V6.03.01
release, the twelve 6.03.02 betas (b0 to b12, of which b8 and b10 were never
published) and the fixes since b12. It is a major release because of the amount
that has changed rather than any one feature: arrays, libraries, image slots in
PSRAM, a sprite compositor for VGA and HDMI, a BASIC-to-CSUB compiler, a new USB
host stack and BBC Micro sound have all arrived in this cycle. Please try it on
programs you already have and report anything that behaves differently.

> **Every board is reset when it first boots this release. Back up first.**
> The option magic key has changed on every variant, deliberately, so that a
> board coming from any earlier firmware starts clean: the options return to
> their defaults, saved variables and the three flash slots are erased, program
> memory is cleared and **the A: drive is reformatted**. Copy anything on A: to
> an SD card or your PC, and save your settings so you can put them back:
>
> ```
> OPTION DISK SAVE "B:/myoptions.txt"
> ```
>
> then after upgrading, `OPTION DISK LOAD "B:/myoptions.txt"`. Save it to B:,
> not A:. A PicoComputer 3 configures itself again at the first boot, but its
> CPU speed and any options you set by hand need re-issuing.

### Changed since RC1

RC2 is RC1 with the changes below. **Coming from RC1, your board keeps its
settings** unless it runs `PicoMiteRP2040`, `PicoMiteRP2040MIN` or
`WebMiteRP2350`: their flash regions have moved (see *Memory and flash
layout*), so they do the full reset described above and reformat A:. Coming
from RC0, only `PicoMiteRP2040MIN` and `WebMiteRP2350` reset, because
`PicoMiteRP2040` returns to RC0's layout. Coming from b12 or earlier, the reset
applies to every board, as before. `MM.VER` reads `6.040052`.

#### The trace cache is gone; mmb2csub replaces it

`OPTION TRACECACHE`, `OPTION CACHE DEBUG` and `OPTION CACHE SUB` have been
removed. The statement cache rarely paid for itself and could make programs
slower. A program that still uses one of these options stops at that line with
`Invalid Option`: delete the line. For real speed, the mmb2csub tool compiles
a whole SUB or FUNCTION to machine code, typically 10 to 35 times faster (see
`mmb2csub.pdf`). The cache's one generally useful part, the `DO` loop fast
path, is kept and is now on every build: a `DO WHILE i% < 100000` loop on the
RP2040 VGA went from 1.50 s to 0.60 s. `OPTION PROFILING`'s per-SUB times are
unchanged.

#### Less work per statement

- **Interrupts.** With an interrupt armed (a `SETTICK`, a pin, a COM port...)
  the interpreter used to scan every source after every statement. Each source
  now signals when it is ready, so an armed but quiet interrupt costs almost
  nothing: a statement loop with `SETTICK` armed takes about 30% less time on
  the PC3 and the RP2040 VGA.
- **WebMite.** Network housekeeping no longer runs after every statement when
  WiFi is not connected, and runs once a millisecond when it is: about 1.5%
  faster. `WEB SCAN` finds networks when WiFi is not connected.

#### Fixed

Program flow and variables:

- A `FOR`, `DO` or `GOSUB` whose line ends in `: ' comment` left the loop after
  one pass, or returned past the next line. This was in every release since
  6.03.00.
- Calling a one-letter SUB alone on a line skipped the next line.
- A `STATIC` could attach its variable to the wrong SUB: the one called most
  recently rather than the one running.
- `OPTION LOCAL VARIABLES` above the default corrupted memory, and a deep
  recursion could leave the local variable table unusable ("Too many local
  variables" with most of it free).
- RP2350: at most 511 SUBs, FUNCTIONs and labels, where 512 made a search for
  a missing name hang. `GOTO`, `GOSUB` and `RESTORE` to a label with the same
  name as a SUB work, and a FUNCTION called as a command, or a SUB used in an
  expression, is reported at the call, as on the RP2040.
- RP2040: a variable with the same name as a SUB or FUNCTION is refused, as on
  the RP2350.
- A line that tokenises to more than 255 bytes (say, a long line of short
  assignments) is refused with `Line is too long` instead of overwriting
  memory, which could restart or hang an RP2040.
- Under `ON ERROR SKIP` or `ON ERROR IGNORE`, an error in a SUB or FUNCTION's
  arguments no longer leaks memory: about 2.8 KB per error on the RP2040, so a
  program could run out after a few dozen.
- An error in an `ELSEIF` condition names the `ELSEIF`'s line.
- A program that ends with its own font selected no longer breaks the next
  `LOAD`.

Numbers:

- `MAX` and `MIN` no longer clamp at +-3.4e38, and `ABS` and `SGN` accept
  floats beyond 9.2e18.
- Minus infinity prints as `-INF` and NaN as `NAN`; printing minus infinity
  used to print garbage, and hung the RP2040. Converting NaN, infinity or
  anything beyond +-2^63 to an integer raises `Number too large`, including
  through `INT` and `FIX`, which used to return +-9223372036854775807.
- An integer `^` takes at most 64 steps: `1^4000000000` used to lock the board
  for minutes, and `CTRL-C` could not stop it.
- An integer array subscript beyond 32 bits is `Index out of bounds`; with
  `DIM a(3)`, `a(4294967297)` used to read `a(1)`.
- RP2040: a bare `RANDOMIZE` reported `Number out of bounds` whenever the board
  had been up for between 36 and 72 minutes (and in alternate spells after
  that).
- RP2040: `SIN`, `COS` and `TAN` in degrees read the wrong argument when it
  contained a function: `SIN(SQR(2.5))` gave sin(2.5 degrees).
- `MATH M_INVERSE` of a 1x1 matrix works, and determinants no longer leak heap.
- The `DO` fast path (on the builds that had the trace cache) no longer
  truncates a fractional limit: `LOOP WHILE i% < 2.5` stopped at 2.

Interrupts and timing:

- `MATH PID START` waits a full sample time for the first callback; it came
  1000 times too early.
- `ON KEY k` works on a UART serial console; `SETTICK` refuses a period of -1;
  `ONESHOT` no longer shares its callback bit with the PS/2 mouse; an I2C slave
  interrupt no longer loses a ready bit; a PIO TX interrupt uses each state
  machine's own FIFO depth.
- `OPTION PROFILING` charged time to the wrong SUB after an interrupt SUB or an
  `ON ... GOSUB`; interrupt SUBs now appear in the report under their own name.
- `MM.INFO(VARCNT)` falls again after `ERASE` and when a SUB's locals are
  freed.

Graphics and sound:

- `MAP MAXIMITE` no longer stripes every second column in HDMI `MODE 2`.
- `BLIT FRAMEBUFFER` on VGA refuses a source rectangle off the buffer.
- `PLAY SOUND` reports an invalid type given as a string.

Stepper (RP2350):

- **`RUN`, `NEW`, `LOAD` and `CHAIN` now stop the stepper subsystem** (as do
  `FILES`, `EDIT FILE` and `RAM FILE LOAD` run from inside a program). It used
  to keep running over the old program's memory, so a queued job could execute
  garbage, and the next program could not `STEPPER INIT` without a `STEPPER
  CLOSE` that itself freed stale memory. A program now simply starts with
  `STEPPER INIT`.
- `STEPPER ESTOP` during an arc no longer leaks the arc's buffer, and the
  stepper interrupt no longer frees heap memory itself.

WebMite:

- A timed-out `WEB TCP CLIENT REQUEST` no longer writes into the program's
  array after the error, which restarted the board a few seconds later.
- `RUN` closes an open TCP client connection, as it already did MQTT.

Documentation:

- The CSUB manual (armcfgen) now says which CSUBs are tied to one chip: those
  that read the variable table or the `Option` structure, whose layouts differ.
  Everything else, including all mmb2csub output, runs on every board.

*Memory and flash layout*. Coming from b12 or anything earlier, the reset
described above applies exactly as it did for RC0.

- **`DIM` of a user-defined `TYPE` could fail with `Not enough memory for 0
  bytes`**, reported against a line that was perfectly correct, and adding an
  unrelated statement elsewhere in the program made it come and go. The
  `IF`/`END IF` jump table and the table of `TYPE` definitions both live in the
  BASIC heap, and clearing that heap did not tell either of them, so the jump
  table went on to release memory that by then held a `TYPE` definition and was
  rebuilt over the top of it. Found from a report by G@bor. It is not new to
  this release - it needed a particular arrangement of memory to show itself.
- **The first flash write after a power-on now waits a second for the supply to
  settle.** The boot counter is written to `A:` early in start-up, and on a
  board whose 3.3 V rail sits close to the flash chip's minimum that write
  could reach the wrong sector, leaving a board that booted once more and then
  not at all. Only a cold start waits; a reset button or `CPU RESTART` does
  not.
- **`MM.VER` tells release candidates apart.** RC1 reads `6.040051` and RC0
  reads `6.040050`. Every `RCn` used to read a bare `6.04`, so a board you had
  just reflashed looked identical to one you had not.
- **`PLAY BBC SOUND` queues 16 notes per channel** instead of 8, and
  `MM.INFO(BBC BUFFER [channel])` reports how many more notes a channel will
  take without waiting. With no channel it answers for the emptiest of the
  four, which is the figure that is safe whichever channel comes next.
- **Out of memory now names the size**, as in `Not enough memory for 16000008
  bytes`. The three earlier messages - `Not enough PSRAM memory`, `Not enough
  Heap memory` and `Not enough System Heap memory` - have become this one.
- `LIBRARY LOAD` says a source file **is empty** rather than reporting it as
  missing.
- A drive format requested during start-up is no longer **repeated** by an
  unrelated `OPTION PLATFORM` change afterwards.
- On the WiFi builds, a full connection table no longer writes past the end of
  the connection arrays.
- Writes to the `A:` drive are bounded at run time, so a bad block number can
  no longer become an erase at a computed address.

### Arrays

**A dimension can hold exactly one element.** `DIM a(0)` under `OPTION BASE 0`
and `DIM a(1)` under `OPTION BASE 1` used to raise `Dimensions`, which made a
row vector, a column vector or a 1x1 result impossible to declare:

```basic
Option base 0
Dim rowv(2,0), colv(0,2), dot(0,0)
Math M_MULT rowv(), colv(), dot()    ' a dot product
```

It works everywhere an array does: every type, any dimension of a
multi-dimensional array, `LOCAL`, `STATIC`, arrays passed as `arr()`, `REDIM`,
structure member arrays, `VAR SAVE`/`VAR RESTORE` and the `MATH` functions.
One consequence: `BOUND()` now raises an error for a dimension the array does
not have, or on a variable that is not an array, where it used to return 0. A
program that tested rank with `If Bound(a(), 2) = 0` needs changing.

**Whole-array assignment.** `b%() = a%()` copies one array into another in a
single memory move. Same type (and `LENGTH` for strings, structure type for
structures), same total number of elements; the shapes may differ.

**Functions can return arrays.** `Function f(n%) As Integer(5)` (integer and
float only) sets its result by assigning to elements of its own name and is
consumed by a whole-array assignment, `m%() = f(3)`. It cannot appear anywhere
else in an expression, and reading an element of the function's name inside
the function is a recursive call, so build the result in a `LOCAL` array if
intermediate values must be read back.

### Libraries

**`LIBRARY LOAD file$ [, O] [, RAM]` lets a program install its own library.**
It must be the program's first statement, it asks before replacing a library
that is already there unless `O` is given, and it is idempotent: a hash of the
source is kept, so a run that finds the same library already in flash touches
nothing. Up to eight files can be named and are joined in order into one
library, so a library can be kept as separate sources and assembled on the
board:

```basic
LIBRARY LOAD "graphics.bas", "sound.bas", "maths.bas"
```

Nothing is written until every file has been read. Not on `PicoMiteRP2040MIN`.

**A library in RAM, alongside the one in flash** (RP2350 with PSRAM). With the
`RAM` keyword the library goes into RAM slot 5 and takes the place of the flash
library, which is left exactly as it was, until `END` or the next `RUN`. A
program can bring a large library of its own without disturbing the routines
you keep in flash. Without PSRAM the keyword is ignored.

**A CSUB costs the library its binary only.** `LIBRARY LOAD` no longer stores
the hex text of a CSUB, which had cost about 3.4 times the code.

**`READ` falls through to `DATA` in the library** when the program's `DATA`
runs out or it has none, and a library routine can read its own `DATA`.

**`FLASH ERASE` works from inside a running program**, so a program can
manage its own slots.

**A corrupt library can no longer lock a board out.** The boot-time walks of
the library are bounded to the slot and the image is checked before anything
reads it; one that fails is erased with the message `Library was corrupt and
has been discarded`. Previously a damaged image hung the interpreter before
the prompt, and reflashing did not help because a .uf2 leaves the library
where it is.

### Image slots in PSRAM (RP2350)

On an RP2350 with PSRAM, **image slots 4 to 8 are the RAM slots 1 to 5**, and
`FLASH LOAD IMAGE`, `BLIT FLASH`, `TILEMAP` and `MM.INFO(FLASH ADDRESS)` take
them by number:

```basic
FLASH LOAD IMAGE 4, "tiles.bmp", O        ' RAM slot 1, every start
TILEMAP CREATE mapdata, 1, 4, 16, 16, 16, 20, 15
BLIT FLASH 4, F, 0, 0, 100, 40, 32, 32, 0
```

A RAM image loads in milliseconds, costs no flash wear and leaves the three
flash slots free. `RAM LIST` and `FLASH LIST` report `image w x h` for a slot
holding an image, `RAM SAVE` refuses one, and both loaders reject a bad or
oversize file before anything is erased. Odd-width images, which were stored
one byte short per row and drew skewed, are now packed the way `BLIT FLASH`
reads them.

### Sprites over a background on VGA and HDMI

**`FRAMEBUFFER MERGE [colour] [, B]`** composites framebuffer 2 over the main
framebuffer into the display in one pass, without the tearing that drawing
into the live layer produces:

```basic
FRAMEBUFFER CREATE          ' the background, F
FRAMEBUFFER CREATE 2        ' the moving things, 2
FRAMEBUFFER MERGE 0, B      ' 2 over F into the display, at vertical blank
```

A full mode 3 merge takes about 11 ms, one frame at 75 Hz. `FRAMEBUFFER CREATE
2` shares the video memory the layer would otherwise use, and `BLIT FLASH`,
`BLIT FRAMEBUFFER` and `TILEMAP DRAW` accept buffer 2. RP2350 only, as `CREATE
2` is. The background merge on LCD panels no longer overflows core 1's stack on
wide displays.

### A BASIC routine compiled to a CSUB, without writing C

**mmb2csub** (in the attached zip) takes one SUB or FUNCTION out of your
program, compiles it to machine code and puts it back as a CSUB. Your call
sites do not change. Loops, arithmetic and array work run 10 to 35 times
faster; the Julia set demo renders in 5.9 s instead of 119 s on an RP2040. The
generated code calls the firmware's own routines through the CallTable, so
`SIN`, `MID$` or `RGB` inside a CSUB mean exactly what they mean in BASIC, and
one converted program, the same bytes, runs on the RP2040 and the RP2350 and
on every variant. `--list` reports what every routine in a program would gain
before anything is written; anything unsupported is refused by name.

With it the CSUB interface has grown: 64-bit arithmetic, `memcpy`/`memset`/
`memmove` and the string routines are in the CallTable, `PIN(n)` and
`PIN(n) = v` work from a CSUB (20,000 write-then-read passes in 83 ms rather
than 654 ms), a CSUB may take sixteen arguments on the RP2350, and the same
CSUB now runs on both chips, unless it reads the variable table or `Option`,
whose layouts differ. `docs/armcfgen.md` and the mmb2csub manual cover
it; `PicoCFunctions.h` no longer declares the wrong variable-table layout for
the RP2040.

### PicoCFunctions.h: the CSUB header has been updated

Anyone compiling a CSUB in C or assembler should take the `PicoCFunctions.h`
from this release (it is in the repository and inside the mmb2csub zip) and
rebuild. It is now at v2.3.0 and differs from the 6.03.00 header in these
ways:

- **The variable-table layout for the RP2040 was wrong.** A CSUB built from
  the old header against an RP2040 build read every variable's value from the
  wrong offset. `MAXDIM` is now 5 on the RP2350 and 6 on the RP2040, the
  `rp2350` define is set so the option struct's padding resolves, and the
  struct matches the firmware's 896-byte `Option`, including the new
  `LIBRARY_HASH` field.
- **New CallTable vectors, all appended so existing CSUBs keep working:**
  64-bit integer helpers `LMul`, `LDiv`, `LMod`, `LShl`, `LAsr`, `LLsr`
  (0x140-0x154); `memcpy`, `memset`, `memmove` (0x158-0x160); the MMBasic
  string routines `MtoC`, `CtoM`, `Mstrcpy`, `Mstrcat`, `Mstrcmp`
  (0x164-0x174) and `StrRight`, `StrCase`, `StrMid`, `StrChar`, `StrFill`
  (0x178-0x18C); `INSTR`, `STR$`, `TIMER`, `RND`, `log`, `tan`, `VAL` and
  `TIMER = n` (0x190-0x1AC); the current `COLOUR` foreground and background
  (0x1B0-0x1B4); and `PinVal` and `PinPut`, which read and drive a pin as
  `PIN(n)` and `PIN(n) = v` do (0x1B8-0x1BC).
- **A CSUB may take sixteen arguments on the RP2350**, ten on the RP2040 as
  before.

The CallTable is found at run time through the VTOR register, so one compiled
CSUB runs on the RP2040 and the RP2350 and on every variant; a CSUB built with
the new header needs this release or later. The exception is a CSUB that reads
the variable table (its `dims[]` are five `int`s on the RP2350 and six `short`s
on the RP2040) or the `Option` structure (laid out per variant): that must
still be built for the chip, or variant, it runs on. `docs/armcfgen.md` lists every
vector with its signature.

### USB host

The USB host stack is now **TinyUSB 0.21** with PicoMite's patches on top.

- **Reads from a USB flash drive (C:) run at several hundred KB/s** instead of
  about 64 KB/s, faster than the SD card on the same board, so `PLAY MP3
  "C:/track.mp3"` streams without underruns.
- **Several devices behind a hub enumerate reliably** on every kind of reset.
  The connect chime plays once, after enumeration, instead of from inside it.
- **Plugging in one device no longer silently kills another**: a recycled
  endpoint slot could capture a live endpoint's completions.
- **RP2040 keyboards no longer fault on plug-in**: control transfers are
  double-buffered again on RP2040, where single buffering walked into erratum
  E4. RP2350 keeps its single-buffered fix.
- **Recoverable USB conditions recover and report** (`[USB DATA_SEQ 3 @181]`)
  instead of taking the interpreter down with a bare `*** FAULT`. The counts
  are readable with `PEEK`.
- **`UPDATE FIRMWARE` is in every build**, so the USB host variants can reach
  the bootloader without the BOOTSEL button.
- **GPS on a USB serial port**: `OPEN "COM3:" AS GPS` through `COM6:` now
  starts the parser, as the UARTs always did.
- **Mouse reports are decoded from the mouse's own HID descriptor** when
  `OPTION MOUSE SENSITIVITY` is set, so mice with extra buttons, padding,
  report IDs or wide movement fields work.

### Sound

**`PLAY BBC SOUND channel, amplitude, pitch, duration`** and **`PLAY BBC
ENVELOPE`** are the BBC Micro's `SOUND` and `ENVELOPE` statements with the same
parameters, units and behaviour, on every variant including the RP2040: three
square-wave channels and a noise channel, eight-deep queues per channel, sync
marks for chords, `&H10` to flush, sixteen envelopes with three-section pitch
envelopes and ADSR amplitude at the authentic 100 Hz, and all eight of the
BBC's noises including the two clocked by channel 1's pitch.

```basic
FOR p = 53 TO 101 STEP 4 : PLAY BBC SOUND 1, -15, p, 5 : NEXT p
```

Also: the VS1053 `PLAY SOUND` right-channel sawtooth and silent-channel DC
offset are fixed, and the computed square and sawtooth waveforms are
band-limited. `PLAY SOUND` type N takes a dwell rather than a pitch.

### Cameras (RP2350)

**OV5640 support**: `CAMERA OPEN OV5640` with QVGA RGB565 preview, motion
detection (`CAMERA CHANGE`) and JPEG capture at VGA to 5MP in three qualities.
White balance is frozen at the preview's converged setting for stills, and the
pixel clock follows the CPU speed. `CAMERA OPEN` no longer needs a display for
JPEG capture and motion detection; a misconfigured or disconnected camera
reports which signal stalled instead of freezing; capture no longer disturbs
the PSRAM/flash controller; the capture inner loops are faster.

### New commands and functions

- **`LOAD file$ [, C] [, R]`** crunches a program as it loads, as `AUTOSAVE C`
  and `XMODEM C` already could, so a program too big for memory can come off a
  disk rather than being pasted up the console. The suffix letters are now
  matched in full, so `LOAD "p.bas", RUN` is a syntax error rather than `,R`.
- **`TILEMAP LOAD file$, id, slot, tileW, tileH, tilesPerRow`** reads a tile map
  from a text file (`.map` by default) so a large map need not live in `DATA`.
- **`MATH CLAMP in(), lo, hi, out()`** limits every element to a range, integer
  or float, strided; 16 elements in 14 us.
- **`BASE$(base, number [, chars])`** for bases 2 to 36.
- **`MM.ERRLINE`** is the line of the last error, beside `MM.ERRNO` and
  `MM.ERRMSG$`.
- **`MM.INFO(TELNET)`** (WiFi builds) is 1 while a Telnet client is attached.
- **`MM.INFO$(BOOT)`** reports a brown-out reset distinctly on the RP2350.
- **`WEB PING address$ [, count] [, timeout_ms] [, avgvar]`** (WiFi builds).
- **`TURTLE`** colour commands accept `COLOR` as well as `COLOUR`.
- **`KEYDOWN()` works on the PicoCalc's built-in keyboard**, and Ctrl+C typed
  quickly on a PicoCalc no longer produces a literal `c`.
- **SHIFT with the left and up arrows** now has key codes of its own, `LEFTSEL`
  (&HA2) and `UPSEL` (&HA4), beside the existing down and right codes.
- **`MAX3D` is 32**, up from 8, so a scene can hold 32 `DRAW3D` objects.
- **PicoComputer 3 configures itself at boot** on the RP2350 builds.

### Boot robustness

- The library check above.
- **The PSRAM bring-up can no longer hang the boot.** Its two QMI handshake
  waits had no timeout and run inside the boot watchdog window, so a PSRAM
  that did not answer rebooted the board into the same wait: a silent boot
  loop that also rewrote the option sector every cycle. The waits are now
  bounded; a chip that does not answer is reported as `PSRAM not responding`
  once the console is up and the option is kept for the next boot.
- **A magic key mismatch is a full clean**, A: drive included (see the box at
  the top). A firmware version change of the same variant resets nothing.
- **RP2040 boot loop fixed**: littlefs's lookahead buffer lost its alignment
  when `FileIO.c` was compiled for size and the boot-time mount of A: faulted.
- **`SAVE IMAGE` writes the colours the screen is showing**, including after
  `MAP SET`.

### Fixed

Two of these have been in the firmware for a long time and are worth calling
out. Both were found while chasing a Game*Mite report on PicoMiteRP2040MIN,
and both were proved on hardware before and after the fix:

- **SD-card access straight after a background framebuffer copy failed** on
  any board where the card shares the system SPI with the display, which is
  every Pico-ResTouch and Game*Mite. The only workaround was a `PAUSE` tuned
  to the CPU speed. Details under *Files and drives*.
- **Reading the screen after a framebuffer session rebooted the board** on an
  SPI panel that cannot be read back, such as the ILI9488W on the ResTouch
  3.5: `SAVE IMAGE`, `BLIT READ` or `PIXEL()` after `FRAMEBUFFER WRITE N`
  went through a null pointer. Details under *Graphics*.

Files and drives

- **A file operation straight after a background `FRAMEBUFFER COPY ,B`
  (or `MERGE ,B` / `BLIT ,B`) no longer fails with an I/O error** when the SD
  card shares the system SPI with the display. The copy runs on core 1 after
  the statement has returned, and the next `PLAY MODFILE`, `LOAD BMP` or file
  read used to drive the same bus at the same time; the only cure was a
  `PAUSE` tuned to the CPU speed. The SD driver now waits for the burst to
  finish before touching the card. The continuous background `MERGE` is
  unchanged: it restarts itself, and a program still has to keep file
  access away from it.
- Reading part of a file after `SEEK` on an SD card started up to 512 bytes
  late (`MEMORY INPUT`, `LONGSTRING LOAD`, structure `LOAD`); `LOC()` could be
  wrong after a seek; `EOF()` could say there was more after a seek to or past
  the end, on SD and on flash.
- The file manager froze or faulted copying directories from a USB drive: its
  5.8 KB stack frame overflowed core 0's 8 KB stack. `EDIT` from the file
  manager could then run out of heap; fixed as well.
- The HDMIUSB build crashed launching a program from the file manager.
- `OPTION DISK SAVE` dropped the platform name and the telnet console mode.
- `RAM FILE LOAD` left the running program without its subroutines, wrote 1 KB
  past the PSRAM allocation map, and `RAM ERASE ALL` cleared 128 KB beyond the
  end of the PSRAM and into the heap.

Graphics

- **`SAVE IMAGE`, `BLIT READ` or `PIXEL()` after a framebuffer session
  hard-faulted on an SPI panel that cannot be read back** (ILI9488W,
  ST7789, ILI9481, GC9A01, the ST7735s and others). `FRAMEBUFFER WRITE N`
  restored the panel's drawing routines but left the read routines bound to
  the framebuffer reader with no framebuffer selected, so the next read went
  through a null pointer and the board rebooted. They now report "not
  available on this display" as they do before any framebuffer is created.
  On these panels `SAVE IMAGE` reads the framebuffer while `FRAMEBUFFER
  WRITE F` or `L` is in force and is refused for `N`; on panels with read-back
  it reads the screen for `N`.
- `FRAMEBUFFER CLOSE L` and `CLOSE T` were transposed and a selective close
  discarded the other buffers; the mode 5 layer and the mode 2 and 5 top layers
  were never freed.
- `FRAMEBUFFER LAYER` drew behind the display on the HDMI builds in modes 2
  and 5 when no `LAYER TOP` existed.
- `DRAW3D()` never returned a value; `CLOSE ALL` left the last object; `LIGHT`,
  `SET FLAGS` and `RESET` faulted on a missing object.
- The mouse cursor could leave a block of corruption behind on GUI and
  on-screen keyboard redraws; OSK keys could not be clicked with a mouse under
  `OPTION GUI CONTROLS 0`; the GUI TEXTBOX pop-up keyboard could not produce
  lower case.
- `CIRCLE` with an aspect greater than 1 and a one-pixel line left gaps; font
  7's percent sign was mirrored; the brownian demo left sprite trails.
- The editor mis-placed a mouse click or tap on a horizontally scrolled line
  and did not refresh its status line after a terminal click.

Interpreter and maths

- `REDIM` recreated arrays as the default type, losing INTEGER and STRING data.
- `MATH CHI` indexed past its table above about 8x8 and had wrong degrees of
  freedom under `OPTION BASE 1`; `MATH M_INVERSE` leaked a row per call;
  `MATH CRC12` masking, the CRC `reverseOut` argument and `Q_CREATE` angle units
  were wrong; assorted argument checks in the MATH array helpers.
- `JSON$` could read 8 bytes past its source array under `OPTION BASE 1`.
- Regular expressions: `{n}` matched n or more times.
- `MM.VER` read past the end of the version string on a release build.
- The console emitted the autowrap escape before every input line; it is now
  sent once at reset and once when the editor exits.
- `PIO SYNC` wrote the wrong PIO's CTRL register and PIO DMA completion
  disabled the wrong state machine on PIO 2.
- dr_wav's 4 KB scratch buffers come from the heap, not the stack.
- The interpreter had become about 7% slower in b2 because newlib's `strlen`
  and `strchr` moved to flash; both are RAM-resident on every variant, and the
  reference benchmark is faster than before.

Network

- `WEB TCP CLIENT REQUEST/READ/STREAM` could write 8 bytes past the
  destination array; `WEB SCAN` and the receive commands reject an array too
  small for any payload; the CRLF terminating a transmitted HTTP body was in
  the wrong order.
- The GPS monitor could overflow the stack when printing to a display console.
- `MM.DEVICE$` said `WebMite` on PicoMiteHDMIWEB; `RAM FILE LOAD` wiped the sub
  table on that build.
- Bluetooth console and keyboard fixes.

### Memory and flash layout

- The MMBasic heap is smaller on the USB host builds to give the new USB
  host stack the C heap it needs: `PicoMiteRP2040USB` 124 KB,
  `PicoMiteRP2040VGAUSB` 96 KB, `PicoMiteRP2350USB` 296 KB and
  `PicoMiteRP2350VGAUSB` 160 KB. The maximum program size follows the heap
  on the RP2350 builds and on the VGA builds; the plain RP2040 builds keep
  their 120 KB program size (116 KB on `PicoMiteRP2040MIN` from RC2).
- Several variants moved their flash region during the beta cycle. That no
  longer matters for upgrading: every board is reset by this release anyway.
- **`PicoMiteRP2040` moved again in RC1**, 912 KB to 928 KB, **and back to
  912 KB in RC2**, now that the trace cache is gone; its heap also grows from
  120 KB to 128 KB. Flash moves only in 16 KB steps, and every move resets the
  board and reformats A: when it first boots the new version.
- **RC2 also moves `PicoMiteRP2040MIN`** (688 KB to 704 KB, with its program
  size 120 KB to 116 KB, so its A: drive keeps its place and size but the board
  still resets) **and `WebMiteRP2350`** (1456 KB to 1472 KB; its A: drive is
  16 KB smaller). No other variant moved.

### For anyone building from source

- The firmware builds with **pico-sdk 2.3.1**. The USB host is **TinyUSB
  0.21.0** in a sibling `../tinyusb-0.21` tree with PicoMite's patches; run
  `tinyusb-patches/setup-tinyusb` once and it fetches the release and applies
  them. The README build instructions are written around this.
- `buildpicomite.bat` takes the version from `Version.h`, pins a Release build,
  stops on the first variant that fails its flash/RAM/heap/alignment fit
  checks, and runs those checks before copying the .uf2 into `uf2/`.
- `tools/release_preflight.py` gates a release: binaries present and named for
  the version, fresher than the last firmware commit (by commit time, never
  mtime), manual PDF byte-identical to the master, tree committed and pushed.
- `misc/FileIO.c` compiles at `-Os`. `strlen` and `strchr` are RAM-resident.
- `SaveProgramToFlash` takes the flash region to write; `ImageSlotAddress()` is
  the one place a slot number becomes an address; `LibPresent()` means "a
  library is active"; `PrepareProgramExt()` bounds its walks to
  `MAX_PROG_SIZE`; `LibraryImageValid()` is the boot check.
- `Option` gains `LIBRARY_HASH` in its last four bytes with the struct still
  exactly 896 bytes, asserted at compile time. `MAXIMAGESLOTS` is 3 on the
  RP2040 and 8 on the RP2350. `PSMAPWORDS` in Memory.h sizes the PSRAM map
  once; static asserts guard the RAM slot reserve and the context save.
- The CallTable has grown by appending; existing CSUBs are unaffected.
  `armcfgen` compiles with `-fno-jump-tables`.
- Board tests in `Testfiles/`: `ArrayCopyTest`, `ArrayCopyStructTest`,
  `ArrayFuncTest`, `ErrLineTest`, `TilemapLoadTest`, `RamImageSlotTest`,
  `RamLibraryTest`, `FramebufferMergeTest`, `MultiFileLibraryTest`,
  `SeekBulkReadTest`, `SdCopyBTest` (needs the SD card on the system SPI,
  e.g. a Pico-ResTouch-LCD-3.5), `single_element_matrix_demo`.
- `MM.VER` distinguishes the release candidates from RC1 onwards: the fourth
  field is read as n+50, so RC2 reports `6.040052`, RC1 `6.040051` and RC0
  `6.040050`. The
  offset is 50 rather than 100 because that field owns only two digits, which
  puts the practical ceiling at RC49. Every `RCn` used to report a bare
  `6.04`, so a board just reflashed could not be told from a stale one.
