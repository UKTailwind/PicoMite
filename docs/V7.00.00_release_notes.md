**Beta 1 (V7.0.00b1).** Version 7 makes MMBasic faster on every board, and on
the RP2350 it adds a compiler that runs most of a program as native code
while leaving it exactly as you wrote it. You do not change your program to
use it: switch it on, type `RUN`, and whatever the compiler can take runs
compiled while the rest runs as before. Please run your own programs on this
beta, first as they are and then (on an RP2350) compiled, and report anything
that behaves differently, anything that fails, and anything that is slower
than you expected. `MM.VER` reads `7.000001`.

V7 also carries everything in 6.04.00 RC2, whose notes are included at the end,
and the fixes listed under *Fixed since 6.04.00 RC2*.

> **Most boards are reset when they first boot this beta. Back up first.**
> Every build except `PicoMiteRP2040` has moved its flash region (see
> *Memory and flash layout*). On the first boot the options return to their
> defaults, saved variables and the three flash slots are erased, program
> memory is cleared and **the A: drive is reformatted**. Copy anything on A:
> to an SD card or your PC, and save your settings so you can put them back:
>
> ```
> OPTION DISK SAVE "B:/myoptions.txt"
> ```
>
> then after upgrading, `OPTION DISK LOAD "B:/myoptions.txt"`. Save it to B:,
> not A:. A PicoComputer 3 configures itself again at the first boot, but its
> CPU speed and any options you set by hand need re-issuing. A board using a
> preset (`OPTION RESET name`) can simply be given the preset again.
> `PicoMiteRP2040` coming from 6.04.00 RC2 keeps its settings and its A: drive.

## What to test

1. **Your programs, as they are.** The interpreter has changed underneath on
   every board (names are now stored as symbols, and local variables live on a
   stack), so run what you have and tell us about any difference in output,
   any error that was not there before, and any program that has become
   slower.
2. **On an RP2350: the same programs compiled.** Type `OPTION COMPILE ON` at
   the command prompt and `RUN`. The output must be exactly what the
   interpreter gives. Tell us about any difference, and about programs whose
   speed-up seems poor: *Seeing how much of a program runs compiled* below
   shows how to find out why, and the answer tells us what to compile next.
3. **If you can, once with `OPTION COMPILE SHADOW`.** It runs the program
   compiled and checks every compiled value against the interpreter, stopping
   at the first line where they disagree. That line is exactly what we need.

When you report, please give the build (the banner line or `MM.DEVICE$`), what
`OPTION COMPILE` was set to, what `PRINT MM.INFO(COMPILE)` says after the run,
and if possible the program.

A note for timing comparisons: on the RP2350, `RND` reseeds itself from the
hardware random number generator every 100 draws, so `RANDOMIZE n` does not
repeat a sequence (this is not new). A program whose amount of work depends
on `RND` does a different amount each run, so compare the time per unit of
work (per frame, per point drawn) rather than the time for a whole run.

## Faster on every board

**Names are stored as symbols.** When a program is saved, every variable, SUB,
FUNCTION and label name becomes a two or three byte symbol, and the
interpreter finds what a symbol refers to directly instead of searching for
the name each time. `LIST` and `EDIT` show every name exactly as you typed it,
and a program saved to a file is plain text as before. The tables that link
the symbols to what they name take a few KB of memory; if a program written
for an earlier version now runs out of memory, see *Programs that need all
their memory* below.

**Local variables live on a stack.** A SUB or FUNCTION's parameters and
`LOCAL` variables are made on entry and dropped on exit without searching or
tidying a table, and each SUB's parameter list is read once rather than on
every call. Calling a SUB or FUNCTION costs much less than it did: loops of
calls are 12% to 39% quicker on a PicoComputer 3 and 17% to 55% on an RP2040.

**`LOCAL` strings and arrays are made faster when the heap is full**: finding
room for them no longer walks past every block already in use.

Measured on an RP2040 PicoMiteVGA at 378 MHz, compared with V6.03.01:

| program | V6.03.01 | V7.0.00b1 | |
|---|---|---|---|
| PETSCII Robots, time to update a frame | 64.7 ms | 54.6 ms | 16% less |
| Solar eclipse | 28 s | just under 23 s | about 18% less |

## Programs that need all their memory: `OPTION SYMBOLS OFF`

**Why it is needed.** The speed that symbols bring comes from tables that V7
builds every time a program is run. For every name in the program they record
where its variable, SUB, FUNCTION or label is, so the interpreter never has to
search for it. The tables live in the same memory as the program's variables,
strings and arrays and take about 20 bytes for each name plus a fixed part:
typically 3 to 5 KB. On an RP2350 with PSRAM most of that is put in the PSRAM,
but on an RP2040, or an RP2350 without PSRAM, it comes out of the memory the
program has for itself (100 KB on the RP2040 PicoMiteVGA). A program written
for 6.04 or earlier that used nearly all of that memory, with a framebuffer,
large arrays, a PIO ring buffer or sound buffers, can now stop with
`Not enough memory`. A logic analyser sent in by a beta tester did exactly
that on an RP2040 PicoMiteVGA.

**Using it.** Put

```
OPTION SYMBOLS OFF
```

on a line of its own at the top of the program. Only blank lines, comment
lines and a `LIBRARY LOAD` may come before it, and a `LIBRARY LOAD` can equally
come after it. When the program is run the tables are not built, and the
memory they would have taken is the program's. Only that program is affected:
nothing is saved in the options, and every other program still gets the
tables. The program itself does not change (it is still stored with symbols,
and `LIST`, `EDIT` and `SAVE` behave as before), so the line can be added or
removed at any time. It cannot be typed at the command prompt
(`Invalid at command prompt`), and lower down in a program it stops with
`Must be at the top of the program`.

**When to use it.** Only for a program that runs out of memory, and you do not
have to guess. When a program runs out of memory for a request no larger than
the tables, the error message says so:

```
Error : Not enough memory for 1920 bytes: put OPTION SYMBOLS OFF first
```

With the line added, the logic analyser starts with 44800 bytes free instead
of 39936 and runs normally.

**What it costs.** Speed. Without the tables every name is found as in earlier
versions, and a little more slowly because it is stored as a symbol. The
interpreter's micro benchmarks (36 kinds of statement, each timed on its own)
on an RP2040 PicoMiteVGA at 315 MHz took, added together:

| | time per statement, all 36 added | compared with 6.04.00 |
|---|---|---|
| 6.04.00 | 844 us | |
| V7, tables built | 666 us | 21% less |
| V7 with `OPTION SYMBOLS OFF` | 880 us | 4% more |

The largest differences are in calls to a SUB or FUNCTION with parameters (a
SUB with six parameters and four `LOCAL`s takes 89 us with the tables, 138 us
without them and 122 us in 6.04.00), in `GOSUB` (4.5 us against 39 us) and in
long names. On an RP2350 a program with the line is not compiled:
`MM.INFO(COMPILE)` reports `TEXT: OPTION SYMBOLS OFF`.

## The compiler (RP2350)

### Using it

```
OPTION COMPILE ON        ' compile at the next RUN
OPTION COMPILE SHADOW    ' compile, and check every compiled value against the interpreter
OPTION COMPILE OFF       ' interpret only (the default)
```

Type it at the command prompt; it takes effect at the next `RUN`, and it is
saved with the other options, so it stays in force after a restart until you
change it. `OPTION LIST` shows it when it is `ON` or `SHADOW`, and `OPTION DISK
SAVE` and `OPTION DISK LOAD` carry it.

At `RUN` the firmware compiles the program, and its library if there is one,
into a *stream* of native operations held apart from the program. It compiles
only when the program or library has changed since the last compile, so the
first `RUN` after an edit takes a moment longer (about 0.3 s for a 110 KB
program on a PicoComputer 3) and later runs start as quickly as the
interpreter. Statements the compiler cannot take stay in the stream as
references to your text and run on the interpreter, interleaved with the
compiled ones, so a program never has to be entirely compilable to benefit.
Nothing about the program changes: `LIST`, `EDIT`, `SAVE`, error messages and
line numbers, `TRACE`, `ON ERROR`, interrupts, `CHAIN` and libraries all
behave as before.

A program runs entirely as text when:

- it starts with `OPTION SYMBOLS OFF`:
  `MM.INFO(COMPILE)` says `TEXT: OPTION SYMBOLS OFF`;
- it was saved without symbols: `TEXT: saved without symbols`;
- its stream would not fit the space kept for it:
  `TEXT: too big for the slot (n of m bytes)`. A stream is typically 1.4 to 3
  times the size of the program (Exile 1.44, PETSCII Robots 1.72, the
  reference benchmark 1.85, Elite 2.87), and the space kept is three times
  the maximum program size, so every program that fits in memory should
  compile.

### Checking a program with SHADOW

`OPTION COMPILE SHADOW` runs the program compiled, and wherever the compiler
has worked out a value - the right-hand side of an assignment, an `IF` or
`ELSEIF` condition, a `DO` or `LOOP` condition, a `BOX`/`LINE`/`PIXEL`/`COLOUR`
argument - it works it out again with the interpreter and compares the two.
If they differ in any bit the program stops at that line:

```
[120] y = a * Sin(t) + b
Error : SHADOW: compiled 3.5, text 3.25
```

It is slower than `ON`, since every checked value is worked out twice, and
switching between `ON` and `SHADOW` recompiles at the next `RUN`. A statement
that calls a user FUNCTION or uses `RND` is not checked, because the
interpreter would make the call again or draw another random number. If a
program behaves differently under `OPTION COMPILE ON`, running it under
`SHADOW` is the quickest way to find where.

### Known differences from the interpreter

- If a FUNCTION `ERASE`s a variable that the statement calling it goes on to
  use after the call, the interpreter quietly makes the variable again; a
  compiled statement stops with `A FUNCTION changed a variable of this
  statement`. A FUNCTION that erases or creates other variables is fine.
- If a FUNCTION changes `OPTION DEFAULT` while another untyped FUNCTION is
  still to be called in the same statement, the statement stops with `OPTION
  DEFAULT changed by a FUNCTION in this statement`.
- Programs run faster, so a program that relies on how long its statements
  take (a delay loop rather than `PAUSE`) will run differently.

### Speed

Times as text and compiled on the same board and firmware (PicoComputer 3,
RP2350 at 378 MHz; the first two with the HDMIUSB build, the rest with
HDMIWEB):

| program | interpreted | compiled | |
|---|---|---|---|
| landscape (untyped FUNCTION in the inner loop) | 78.5 s | 21 s | 3.7x |
| torus (nested loops, `IF` and `PIXEL`) | 40.5 s | 7.8 s | 5.2x |
| galaxy (SIN/COS per point), per point | 255 us | 80 us | 3.2x |
| reference benchmark | 15.4 s | 7.1 s | 2.2x |
| Elite, per frame | 22.6 ms | 11.0 ms | 2.1x |
| Prince of Persia port, per frame | 9.7 ms | 6.7 ms | 1.4x |
| PETSCII Robots, frame update | 36.0 ms | 23.4 ms | 1.5x |

Where the gain is smaller, the time goes on work the compiler cannot make
faster: the maths library (a `SIN` or a `^` costs the same compiled or not),
the drawing itself, and statements that are not compiled yet. In the galaxy
program, once compiled, about a quarter of the time is in `SIN`, `COS`, `LOG`
and `^`, and a fifth in `PIXEL`.

### Where the stream is kept, and memory

- **With PSRAM** the stream is kept in the part of PSRAM the firmware already
  reserves, above the five RAM slots. None of your PSRAM heap or RAM slots is
  used, and it is lost at power-off (the next `RUN` compiles again).
- **Without PSRAM** it is kept in a hidden area of flash straight after the
  program, three program sizes long. It is rewritten only when the program
  has changed since its last compile, so an edit-and-run costs one erase of
  it, as saving the program already does. This area is why the A: drive is
  smaller on the RP2350 builds (see *Memory and flash layout*).
- The compiler borrows some temporary memory while it compiles and returns it
  before the program starts; while the program runs it uses none of the
  heap. It does not reduce how deeply SUBs and FUNCTIONs can recurse:
  compiled code recurses as deep as the interpreter or deeper.

## What compiles

Anything not listed here runs on the interpreter exactly as before. A
statement that the compiler cannot take in full runs as text as a whole; the
statements around it are still compiled.

### Statements

| statement | compiled when | runs as text |
|---|---|---|
| assignment (`LET`, or `name = ...`) | the target is a numeric or string variable or a numeric array element, and the right-hand side is an expression the compiler takes (below) | a string array element, a structure member, a whole-array assignment |
| `IF ... THEN ... [ELSE ...] ENDIF`, `ELSEIF` | multi-line, with any number of `ELSEIF` arms | |
| single-line `IF ... THEN ... [ELSE ...]` | the parts after `THEN` and `ELSE` are assignments; or, with no `ELSE`, the part after `THEN` is any statement (which then runs compiled or not on its own merits) | `IF ... THEN GOTO`, `THEN` followed by a line number, an `ELSE` whose parts are not assignments |
| `FOR ... TO ... [STEP ...]`, `NEXT` | the loop variable is a numeric variable | a user FUNCTION call in the start, limit or step |
| `DO [WHILE / UNTIL ...]`, `LOOP [WHILE / UNTIL ...]` | | a user FUNCTION call in the condition |
| `SELECT CASE`, `CASE`, `CASE ELSE`, `END SELECT` | the selector is numeric; `CASE` values, ranges (`a TO b`) and `IS` comparisons | a string selector |
| `EXIT FOR`, `EXIT DO`, `CONTINUE FOR` | | `CONTINUE DO` |
| calling a SUB | up to 16 parameters; each argument a numeric expression or a variable (passed by reference) | a CSUB, a string, array or structure argument, an array element or a FUNCTION call as an argument, `BYREF` with an expression |
| `RETURN`, `END SUB`, `EXIT SUB`, `END FUNCTION`, `EXIT FUNCTION` | | |
| `LOCAL [AS type] name [, name ...]` | | an initial value, an array, `LENGTH` |
| `INC var [, value]` | a numeric variable or array element, or a string variable | a string array element |
| `BOX`, `LINE`, `PIXEL`, `COLOUR` (`COLOR`) | every argument is an expression the compiler takes | `LINE PLOT`, `LINE GRAPH`, `LINE AA`; a user FUNCTION call in an argument; `LINE` and `PIXEL` under `OPTION LEGACY` |
| `ENDIF`, `END SELECT`, `DATA`, comments, labels | (passed over) | |

Not compiled, among others: `PRINT`, `INPUT`, `GOTO`, `GOSUB`, `ON ... GOTO`,
`DIM`, `STATIC`, `CONST`, `READ`, `ERASE`, `TEXT`, `CIRCLE`, `CLS`, `BLIT`,
`SPRITE`, `PAUSE`, file and pin commands. The variables they create are used
by compiled statements like any others.

### Expressions

- **Operators:** `+ - * /`, `\`, `MOD`, `^` (when the left operand is a
  float), `= <> < > <= >=`, `AND OR XOR`, `NOT`, `INV`, `<<`, `>>`, unary `-`
  and `+`; `+` and the comparisons on strings. An integer `^` runs as text.
- **Literals:** decimal numbers, hexadecimal, octal and binary numbers
  (`&HFF`, `&O17`, `&B101`), and strings of up to 64 characters with no
  backslash.
- **Variables:** integer, float and string variables, global or local,
  including parameters, `STATIC` variables and constants; numeric array
  elements of any number of dimensions, with any expression as the index.
  Not string arrays or structure members.
- **Built-in functions:** `SIN COS TAN ATN SQR EXP LOG DEG RAD INT FIX ABS SGN
  PI RND`; `LEN ASC CHR$ MID$ STR$ SPACE$ LEFT$ RIGHT$ UCASE$ LCASE$ HEX$ OCT$
  BIN$`; `INSTR` with two strings or a start position and two strings;
  `TRIM$` with one or two arguments; `RGB(r, g, b)` and `RGB(name)`;
  `MAP(n)`. These follow `OPTION ANGLE` and give the same errors as the
  interpreter. An argument may not call a user FUNCTION or be left empty.
  Not compiled: `VAL`, `STRING$`, `MIN`, `MAX`, `CINT`, `ACOS`, `ASIN`,
  `ATAN2`, `TIMER`, `INKEY$`, `PEEK`, `PIN`, `MM.` values and the rest.
- **User FUNCTIONs:** any number of calls in an assignment, an `IF` or
  `ELSEIF` condition or an `INC` value, including calls inside another
  call's arguments. The FUNCTION must return a number: typed (`As Integer`,
  `As Float`, or a suffix) or untyped, when it takes the type `OPTION DEFAULT`
  gives it (float unless the program sets another). Arguments as for a SUB
  call. Not a FUNCTION returning a string or an array.

### New variables

A variable that does not exist yet is made by the interpreter, as always: the
first time a statement that makes it runs, that statement runs as text, and it
is compiled from then on. A single-line `IF` is not held back by a variable
that only its `THEN` or `ELSE` part uses: `IF k$ = "q" THEN quit = 1` runs
compiled on every pass, and only the pass that first sets `quit` runs as text.

## Seeing how much of a program runs compiled

**`MM.INFO(COMPILE)`** says what the last `RUN` did. Print it at the end of
the program, or type `PRINT MM.INFO(COMPILE)` at the prompt afterwards:

```
COMPILED 3 REUSED 1 STMTS 3227 RAN 714382 MISS 25707 CODE 680945 SIZE 132348 OF 966656
```

| field | meaning |
|---|---|
| `COMPILED n` / `REUSED n` | how many compiles, and how many runs that found the stream already compiled, since power-on. At the prompt the word is `NONE` instead of `COMPILED`. |
| `STMTS n` | statements in the stream |
| `RAN n` | statements the last run executed through the stream |
| `CODE n` | how many of those ran as compiled code |
| `MISS n` | internal: lookups of where to go next |
| `SIZE n OF m` | bytes of stream, of the space kept for it |

`CODE` divided by `RAN` is the share of the work done compiled: 680945 of
714382 is 95% here. It can also say `OFF`, or `TEXT:` and a reason (above).

**`OPTION PROFILING ON`** shows which statements ran as text. Put it as the
program's first line (it must be in the program: `RUN` clears it), make sure
the program finishes with `END` (the report is printed by `END`, not when a
program runs off its last line or is stopped with Ctrl-C), and run it with
`OPTION COMPILE ON`:

```
[PERF] elapsed=61247333 us  statements=772063  findvar=...  user_subs=46912  local_peak=19/192
[PERF] top commands by dispatch count:
      325725  Static
      323875  Loop
       56082  Blit Memory
        2172  FRAMEBUFFER
[PERF] top SUBs by exclusive (self) time:
       self_us    incl_us     calls   self_us/call  name
       7444555    7444555       719         10354  writeworld_n
```

With the compiler on, `statements` and the `top commands` list count only
the statements that ran as text, so the list is exactly what is left
uncompiled, command by command, busiest first. The SUB table shows where the
time goes, so you can tell whether what is left is in a busy SUB or in
start-up code. `local_peak` is the most local variables alive at once, of the
number available.

**`OPTION PROFILING ON, SAMPLE`** also samples where the processor is, and
`END` adds the busiest lines:

```
[PCSLINE] 29 4011
[PCSLINE] 23 3318
```

The first number is the line number, as the editor and error messages show it
(-1 for a line in the library); the second is how many samples landed on it. Together
with the command list this points at the lines worth changing, or worth
telling us about.

A typical session:

```
> OPTION COMPILE ON
> RUN
... the program, which starts with OPTION PROFILING ON and ends with END ...
> PRINT MM.INFO(COMPILE)
```

## A warning when the stack runs low

When a program has taken the stack to within 1 KB of its limit, the next
command prompt shows

```
Warning: the stack came within 536 bytes of its limit, at depth 12
```

where the depth is how many SUBs and FUNCTIONs were running. Deep recursion is
the usual cause: a simple recursive FUNCTION reaches about 13 levels on an
RP2350 and 9 on an RP2040 before `Stack overflow`, much as in 6.04.00. None of
the programs we test with (the reference programs, Exile, Elite, the Prince of
Persia port, PETSCII Robots and a corpus of 224 test programs) comes near it;
if one of yours shows the warning, please send it to us.

## Fixed since 6.04.00 RC2

- RP2350 with PSRAM (a PicoComputer 3, for example): the board could stop with
  a hard fault, usually at the command prompt, after a program used `WS2812`
  or `BITSTREAM`, or after anything that writes flash (saving a program,
  writing a file on A:, changing an option). Before each of these the firmware
  tidied the processor's cache in a way that the RP2350's erratum E11 turns
  into wrong reads of the firmware's own code. On a PicoComputer 3 a short
  `WS2812` test faulted about one run in three; with the fix it ran 240 times
  without one.
- RP2350 with PSRAM: writing or closing a file on A: could throw away data a
  program had just stored in PSRAM (a large array or string could lose its
  most recent changes).
- `OPTION LOCAL VARIABLES` stayed in force after the program that set it had
  ended, so the next program ran with its split and could run out of global
  variables. `RUN`, `NEW` and `LOAD` put it back to the default; `CHAIN` keeps
  it for the chained program.
- An expression passed to a `BYVAL` parameter (`Inner 5, x()`) could be refused
  with `Array as BYVAL not allowed` when an unrelated local array happened to
  occupy the first slot of the variable table. Passing a whole array `BYVAL`
  is still refused, and an array element is still accepted.
- A float subtraction that overflows (`1e308 - (-1e308)`) stops with the same
  error as addition and multiplication, instead of giving `INF`.
- `LIBRARY LOAD` refuses a library too big for its flash slot. The size check
  could never fire, so a library whose text outgrew the slot would have been
  written over program memory.

## Memory and flash layout

**Flash.** Every build except `PicoMiteRP2040` has moved its flash region
since 6.04.00 RC2, so the first boot is the full reset described at the top.
On the RP2350 builds the A: drive is smaller, mostly because of the stream's
flash area (three program sizes, needed on boards without PSRAM); on a 4 MB
board it keeps between 1.1 and 1.9 MB. The RP2040 builds lose 16 KB of A: or
nothing.

| build | flash region | maximum program | MMBasic heap | A: drive | locals / globals |
|---|---|---|---|---|---|
| PicoMiteRP2040 | unchanged | 120 KB | 128 KB | unchanged | 240 / 256 |
| PicoMiteRP2040USB | moved | 120 KB | 124 KB | 16 KB smaller | 240 / 256 |
| PicoMiteRP2040MIN | moved | 112 KB (was 116) | 128 KB | same place and size | 240 / 256 |
| PicoMiteRP2040VGA | moved | 100 KB | 100 KB | 16 KB smaller | 240 / 240 |
| PicoMiteRP2040VGAUSB | moved | 96 KB | 96 KB | 16 KB smaller | 240 / 240 |
| WebMiteRP2040 | moved | 88 KB | 88 KB | 16 KB smaller | 192 / 240 (was 240 / 240) |
| PicoMiteRP2350 | moved | 208 KB (was 300) | 300 KB | 288 KB smaller | 192 / 576 |
| PicoMiteRP2350USB | moved | 208 KB (was 296) | 296 KB | 320 KB smaller | 192 / 576 |
| PicoMiteRP2350BT | moved | 208 KB (was 272) | 272 KB | 416 KB smaller | 192 / 576 |
| PicoMiteRP2350BTH | moved | 208 KB (was 256) | 256 KB | 480 KB smaller | 192 / 576 |
| WebMiteRP2350 | moved | 208 KB (was 256) | 248 KB (was 256) | 480 KB smaller | 192 / 576 |
| PicoMiteRP2350VGA | moved | 168 KB | 168 KB | 552 KB smaller | 192 / 544 |
| PicoMiteRP2350VGAUSB | moved | 160 KB | 160 KB | 512 KB smaller | 192 / 544 |
| PicoMiteHDMI | moved | 156 KB (was 160) | 156 KB (was 160) | 500 KB smaller | 192 / 544 |
| PicoMiteHDMIUSB | moved | 148 KB (was 152) | 148 KB (was 152) | 460 KB smaller | 192 / 544 |
| PicoMiteHDMIWEB | moved | 144 KB | 144 KB | 480 KB smaller | 192 / 544 |

**Program size.** Five RP2350 builds now take programs of up to 208 KB
rather than their heap size: the PSRAM reserve has to hold the five RAM
slots and three program sizes of stream. The heap itself is unchanged except
where the table says. On the HDMI and HDMIUSB builds, 4 KB of heap went to
the variable table below, and the maximum program size follows the heap
there.

**Local variables.** Since locals live on a stack, the local region only
needs to hold the most locals alive at once, not a hash table's slack. Real
programs use far fewer than the space kept: the most we have measured is 125
(the reference benchmark); Exile 56, Elite and the Prince of Persia port about
44, PETSCII Robots 19. The RP2350 builds keep 192 local entries and have 64
more globals than before, so the total is the same or larger. The RP2040
builds keep RC2's 240 locals, except the WebMite, which has the RAM for 192.
`OPTION LOCAL VARIABLES` moves the split as before, and now returns to the
default at `RUN`, `NEW` and `LOAD` rather than staying in force for the next
program (`CHAIN` keeps it). `local_peak` in the `OPTION PROFILING` report
shows what a program actually uses.

## For anyone building from source

- The V7 work is on the `development` branch. `buildpicomite.bat` builds the
  checked-out branch; `PicoMiteRP2040MIN` is back in its list.
- The compiler is `core/Stream.c`, RP2350 only (`Stream.h` provides stubs on
  the RP2040). Its design, with the measurements behind each step, is
  `docs/Interpreter_RouteB_Design.html`.
- A stream is tied to the firmware that wrote it (the build's date and the
  image's size are in its stamp), so a new firmware always recompiles.
- `#define SYMBOLS_TEST_SWITCH` in `configuration.h` (off in the release
  builds) makes `OPTION SYMBOLS ON|OFF` at the command prompt a testing switch
  that saves programs with or without symbols, for comparing the two; the
  scripts in `Bas/bench/` that do so (`stdset.py`, `symab.py`, `rtlist.py`,
  `rbstamp.py`) need it.
- Board tests for the compiler are in `Bas/bench/`: the `rbp*.py` scripts run
  each of their programs with `OPTION COMPILE OFF`, `ON` and `SHADOW` and
  require the same output; `rbf2.py` checks local variables and SUB calls
  against recorded references, `rbcache.py` the compiled statements' cached
  bindings, and `rbdepth.py` the recursion depth.

programs you already have and report anything that behaves differently.

> **Every board is reset when it first boots this release. Back up first.**
> The option magic key has changed on every variant, deliberately, so that a
> board coming from any earlier firmware starts clean: the options return to
> their defaults, saved variables and the three flash slots are erased, program
> memory is cleared and **the A: drive is reformatted**. Copy anything on A: to
> an SD card or your PC, and save your settings so you can put them back:
>
> ```
> OPTION DISK SAVE "B:/myoptions.txt"
> ```
>
> then after upgrading, `OPTION DISK LOAD "B:/myoptions.txt"`. Save it to B:,
> not A:. A PicoComputer 3 configures itself again at the first boot, but its
> CPU speed and any options you set by hand need re-issuing.

### Changed since RC1

RC2 is RC1 with the changes below. **Coming from RC1, your board keeps its
settings** unless it runs `PicoMiteRP2040`, `PicoMiteRP2040MIN` or
`WebMiteRP2350`: their flash regions have moved (see *Memory and flash
layout*), so they do the full reset described above and reformat A:. Coming
from RC0, only `PicoMiteRP2040MIN` and `WebMiteRP2350` reset, because
`PicoMiteRP2040` returns to RC0's layout. Coming from b12 or earlier, the reset
applies to every board, as before. `MM.VER` reads `6.040052`.

#### The trace cache is gone; mmb2csub replaces it

`OPTION TRACECACHE`, `OPTION CACHE DEBUG` and `OPTION CACHE SUB` have been
removed. The statement cache rarely paid for itself and could make programs
slower. A program that still uses one of these options stops at that line with
`Invalid Option`: delete the line. For real speed, the mmb2csub tool compiles
a whole SUB or FUNCTION to machine code, typically 10 to 35 times faster (see
`mmb2csub.pdf`). The cache's one generally useful part, the `DO` loop fast
path, is kept and is now on every build: a `DO WHILE i% < 100000` loop on the
RP2040 VGA went from 1.50 s to 0.60 s. `OPTION PROFILING`'s per-SUB times are
unchanged.

#### Less work per statement

- **Interrupts.** With an interrupt armed (a `SETTICK`, a pin, a COM port...)
  the interpreter used to scan every source after every statement. Each source
  now signals when it is ready, so an armed but quiet interrupt costs almost
  nothing: a statement loop with `SETTICK` armed takes about 30% less time on
  the PC3 and the RP2040 VGA.
- **WebMite.** Network housekeeping no longer runs after every statement when
  WiFi is not connected, and runs once a millisecond when it is: about 1.5%
  faster. `WEB SCAN` finds networks when WiFi is not connected.

#### Fixed

Program flow and variables:

- A `FOR`, `DO` or `GOSUB` whose line ends in `: ' comment` left the loop after
  one pass, or returned past the next line. This was in every release since
  6.03.00.
- Calling a one-letter SUB alone on a line skipped the next line.
- A `STATIC` could attach its variable to the wrong SUB: the one called most
  recently rather than the one running.
- `OPTION LOCAL VARIABLES` above the default corrupted memory, and a deep
  recursion could leave the local variable table unusable ("Too many local
  variables" with most of it free).
- RP2350: at most 511 SUBs, FUNCTIONs and labels, where 512 made a search for
  a missing name hang. `GOTO`, `GOSUB` and `RESTORE` to a label with the same
  name as a SUB work, and a FUNCTION called as a command, or a SUB used in an
  expression, is reported at the call, as on the RP2040.
- RP2040: a variable with the same name as a SUB or FUNCTION is refused, as on
  the RP2350.
- A line that tokenises to more than 255 bytes (say, a long line of short
  assignments) is refused with `Line is too long` instead of overwriting
  memory, which could restart or hang an RP2040.
- Under `ON ERROR SKIP` or `ON ERROR IGNORE`, an error in a SUB or FUNCTION's
  arguments no longer leaks memory: about 2.8 KB per error on the RP2040, so a
  program could run out after a few dozen.
- An error in an `ELSEIF` condition names the `ELSEIF`'s line.
- A program that ends with its own font selected no longer breaks the next
  `LOAD`.

Numbers:

- `MAX` and `MIN` no longer clamp at +-3.4e38, and `ABS` and `SGN` accept
  floats beyond 9.2e18.
- Minus infinity prints as `-INF` and NaN as `NAN`; printing minus infinity
  used to print garbage, and hung the RP2040. Converting NaN, infinity or
  anything beyond +-2^63 to an integer raises `Number too large`, including
  through `INT` and `FIX`, which used to return +-9223372036854775807.
- An integer `^` takes at most 64 steps: `1^4000000000` used to lock the board
  for minutes, and `CTRL-C` could not stop it.
- An integer array subscript beyond 32 bits is `Index out of bounds`; with
  `DIM a(3)`, `a(4294967297)` used to read `a(1)`.
- RP2040: a bare `RANDOMIZE` reported `Number out of bounds` whenever the board
  had been up for between 36 and 72 minutes (and in alternate spells after
  that).
- RP2040: `SIN`, `COS` and `TAN` in degrees read the wrong argument when it
  contained a function: `SIN(SQR(2.5))` gave sin(2.5 degrees).
- `MATH M_INVERSE` of a 1x1 matrix works, and determinants no longer leak heap.
- The `DO` fast path (on the builds that had the trace cache) no longer
  truncates a fractional limit: `LOOP WHILE i% < 2.5` stopped at 2.

Interrupts and timing:

- `MATH PID START` waits a full sample time for the first callback; it came
  1000 times too early.
- `ON KEY k` works on a UART serial console; `SETTICK` refuses a period of -1;
  `ONESHOT` no longer shares its callback bit with the PS/2 mouse; an I2C slave
  interrupt no longer loses a ready bit; a PIO TX interrupt uses each state
  machine's own FIFO depth.
- `OPTION PROFILING` charged time to the wrong SUB after an interrupt SUB or an
  `ON ... GOSUB`; interrupt SUBs now appear in the report under their own name.
- `MM.INFO(VARCNT)` falls again after `ERASE` and when a SUB's locals are
  freed.

Graphics and sound:

- `MAP MAXIMITE` no longer stripes every second column in HDMI `MODE 2`.
- `BLIT FRAMEBUFFER` on VGA refuses a source rectangle off the buffer.
- `PLAY SOUND` reports an invalid type given as a string.

Stepper (RP2350):

- **`RUN`, `NEW`, `LOAD` and `CHAIN` now stop the stepper subsystem** (as do
  `FILES`, `EDIT FILE` and `RAM FILE LOAD` run from inside a program). It used
  to keep running over the old program's memory, so a queued job could execute
  garbage, and the next program could not `STEPPER INIT` without a `STEPPER
  CLOSE` that itself freed stale memory. A program now simply starts with
  `STEPPER INIT`.
- `STEPPER ESTOP` during an arc no longer leaks the arc's buffer, and the
  stepper interrupt no longer frees heap memory itself.

WebMite:

- A timed-out `WEB TCP CLIENT REQUEST` no longer writes into the program's
  array after the error, which restarted the board a few seconds later.
- `RUN` closes an open TCP client connection, as it already did MQTT.

Documentation:

- The CSUB manual (armcfgen) now says which CSUBs are tied to one chip: those
  that read the variable table or the `Option` structure, whose layouts differ.
  Everything else, including all mmb2csub output, runs on every board.

### Changed since RC0

RC1 is RC0 with the fixes below. **Coming from RC0 your board keeps its
settings**, unless you run `PicoMiteRP2040`, whose flash region has moved - see
*Memory and flash layout*. Coming from b12 or anything earlier, the reset
described above applies exactly as it did for RC0.

- **`DIM` of a user-defined `TYPE` could fail with `Not enough memory for 0
  bytes`**, reported against a line that was perfectly correct, and adding an
  unrelated statement elsewhere in the program made it come and go. The
  `IF`/`END IF` jump table and the table of `TYPE` definitions both live in the
  BASIC heap, and clearing that heap did not tell either of them, so the jump
  table went on to release memory that by then held a `TYPE` definition and was
  rebuilt over the top of it. Found from a report by G@bor. It is not new to
  this release - it needed a particular arrangement of memory to show itself.
- **The first flash write after a power-on now waits a second for the supply to
  settle.** The boot counter is written to `A:` early in start-up, and on a
  board whose 3.3 V rail sits close to the flash chip's minimum that write
  could reach the wrong sector, leaving a board that booted once more and then
  not at all. Only a cold start waits; a reset button or `CPU RESTART` does
  not.
- **`MM.VER` tells release candidates apart.** RC1 reads `6.040051` and RC0
  reads `6.040050`. Every `RCn` used to read a bare `6.04`, so a board you had
  just reflashed looked identical to one you had not.
- **`PLAY BBC SOUND` queues 16 notes per channel** instead of 8, and
  `MM.INFO(BBC BUFFER [channel])` reports how many more notes a channel will
  take without waiting. With no channel it answers for the emptiest of the
  four, which is the figure that is safe whichever channel comes next.
- **Out of memory now names the size**, as in `Not enough memory for 16000008
  bytes`. The three earlier messages - `Not enough PSRAM memory`, `Not enough
  Heap memory` and `Not enough System Heap memory` - have become this one.
- `LIBRARY LOAD` says a source file **is empty** rather than reporting it as
  missing.
- A drive format requested during start-up is no longer **repeated** by an
  unrelated `OPTION PLATFORM` change afterwards.
- On the WiFi builds, a full connection table no longer writes past the end of
  the connection arrays.
- Writes to the `A:` drive are bounded at run time, so a bad block number can
  no longer become an erase at a computed address.

### Arrays

**A dimension can hold exactly one element.** `DIM a(0)` under `OPTION BASE 0`
and `DIM a(1)` under `OPTION BASE 1` used to raise `Dimensions`, which made a
row vector, a column vector or a 1x1 result impossible to declare:

```basic
Option base 0
Dim rowv(2,0), colv(0,2), dot(0,0)
Math M_MULT rowv(), colv(), dot()    ' a dot product
```

It works everywhere an array does: every type, any dimension of a
multi-dimensional array, `LOCAL`, `STATIC`, arrays passed as `arr()`, `REDIM`,
structure member arrays, `VAR SAVE`/`VAR RESTORE` and the `MATH` functions.
One consequence: `BOUND()` now raises an error for a dimension the array does
not have, or on a variable that is not an array, where it used to return 0. A
program that tested rank with `If Bound(a(), 2) = 0` needs changing.

**Whole-array assignment.** `b%() = a%()` copies one array into another in a
single memory move. Same type (and `LENGTH` for strings, structure type for
structures), same total number of elements; the shapes may differ.

**Functions can return arrays.** `Function f(n%) As Integer(5)` (integer and
float only) sets its result by assigning to elements of its own name and is
consumed by a whole-array assignment, `m%() = f(3)`. It cannot appear anywhere
else in an expression, and reading an element of the function's name inside
the function is a recursive call, so build the result in a `LOCAL` array if
intermediate values must be read back.

### Libraries

**`LIBRARY LOAD file$ [, O] [, RAM]` lets a program install its own library.**
It must be the program's first statement, it asks before replacing a library
that is already there unless `O` is given, and it is idempotent: a hash of the
source is kept, so a run that finds the same library already in flash touches
nothing. Up to eight files can be named and are joined in order into one
library, so a library can be kept as separate sources and assembled on the
board:

```basic
LIBRARY LOAD "graphics.bas", "sound.bas", "maths.bas"
```

Nothing is written until every file has been read. Not on `PicoMiteRP2040MIN`.

**A library in RAM, alongside the one in flash** (RP2350 with PSRAM). With the
`RAM` keyword the library goes into RAM slot 5 and takes the place of the flash
library, which is left exactly as it was, until `END` or the next `RUN`. A
program can bring a large library of its own without disturbing the routines
you keep in flash. Without PSRAM the keyword is ignored.

**A CSUB costs the library its binary only.** `LIBRARY LOAD` no longer stores
the hex text of a CSUB, which had cost about 3.4 times the code.

**`READ` falls through to `DATA` in the library** when the program's `DATA`
runs out or it has none, and a library routine can read its own `DATA`.

**`FLASH ERASE` works from inside a running program**, so a program can
manage its own slots.

**A corrupt library can no longer lock a board out.** The boot-time walks of
the library are bounded to the slot and the image is checked before anything
reads it; one that fails is erased with the message `Library was corrupt and
has been discarded`. Previously a damaged image hung the interpreter before
the prompt, and reflashing did not help because a .uf2 leaves the library
where it is.

### Image slots in PSRAM (RP2350)

On an RP2350 with PSRAM, **image slots 4 to 8 are the RAM slots 1 to 5**, and
`FLASH LOAD IMAGE`, `BLIT FLASH`, `TILEMAP` and `MM.INFO(FLASH ADDRESS)` take
them by number:

```basic
FLASH LOAD IMAGE 4, "tiles.bmp", O        ' RAM slot 1, every start
TILEMAP CREATE mapdata, 1, 4, 16, 16, 16, 20, 15
BLIT FLASH 4, F, 0, 0, 100, 40, 32, 32, 0
```

A RAM image loads in milliseconds, costs no flash wear and leaves the three
flash slots free. `RAM LIST` and `FLASH LIST` report `image w x h` for a slot
holding an image, `RAM SAVE` refuses one, and both loaders reject a bad or
oversize file before anything is erased. Odd-width images, which were stored
one byte short per row and drew skewed, are now packed the way `BLIT FLASH`
reads them.

### Sprites over a background on VGA and HDMI

**`FRAMEBUFFER MERGE [colour] [, B]`** composites framebuffer 2 over the main
framebuffer into the display in one pass, without the tearing that drawing
into the live layer produces:

```basic
FRAMEBUFFER CREATE          ' the background, F
FRAMEBUFFER CREATE 2        ' the moving things, 2
FRAMEBUFFER MERGE 0, B      ' 2 over F into the display, at vertical blank
```

A full mode 3 merge takes about 11 ms, one frame at 75 Hz. `FRAMEBUFFER CREATE
2` shares the video memory the layer would otherwise use, and `BLIT FLASH`,
`BLIT FRAMEBUFFER` and `TILEMAP DRAW` accept buffer 2. RP2350 only, as `CREATE
2` is. The background merge on LCD panels no longer overflows core 1's stack on
wide displays.

### A BASIC routine compiled to a CSUB, without writing C

**mmb2csub** (in the attached zip) takes one SUB or FUNCTION out of your
program, compiles it to machine code and puts it back as a CSUB. Your call
sites do not change. Loops, arithmetic and array work run 10 to 35 times
faster; the Julia set demo renders in 5.9 s instead of 119 s on an RP2040. The
generated code calls the firmware's own routines through the CallTable, so
`SIN`, `MID$` or `RGB` inside a CSUB mean exactly what they mean in BASIC, and
one converted program, the same bytes, runs on the RP2040 and the RP2350 and
on every variant. `--list` reports what every routine in a program would gain
before anything is written; anything unsupported is refused by name.

With it the CSUB interface has grown: 64-bit arithmetic, `memcpy`/`memset`/
`memmove` and the string routines are in the CallTable, `PIN(n)` and
`PIN(n) = v` work from a CSUB (20,000 write-then-read passes in 83 ms rather
than 654 ms), a CSUB may take sixteen arguments on the RP2350, and the same
CSUB now runs on both chips, unless it reads the variable table or `Option`,
whose layouts differ. `docs/armcfgen.md` and the mmb2csub manual cover
it; `PicoCFunctions.h` no longer declares the wrong variable-table layout for
the RP2040.

### PicoCFunctions.h: the CSUB header has been updated

Anyone compiling a CSUB in C or assembler should take the `PicoCFunctions.h`
from this release (it is in the repository and inside the mmb2csub zip) and
rebuild. It is now at v2.3.0 and differs from the 6.03.00 header in these
ways:

- **The variable-table layout for the RP2040 was wrong.** A CSUB built from
  the old header against an RP2040 build read every variable's value from the
  wrong offset. `MAXDIM` is now 5 on the RP2350 and 6 on the RP2040, the
  `rp2350` define is set so the option struct's padding resolves, and the
  struct matches the firmware's 896-byte `Option`, including the new
  `LIBRARY_HASH` field.
- **New CallTable vectors, all appended so existing CSUBs keep working:**
  64-bit integer helpers `LMul`, `LDiv`, `LMod`, `LShl`, `LAsr`, `LLsr`
  (0x140-0x154); `memcpy`, `memset`, `memmove` (0x158-0x160); the MMBasic
  string routines `MtoC`, `CtoM`, `Mstrcpy`, `Mstrcat`, `Mstrcmp`
  (0x164-0x174) and `StrRight`, `StrCase`, `StrMid`, `StrChar`, `StrFill`
  (0x178-0x18C); `INSTR`, `STR$`, `TIMER`, `RND`, `log`, `tan`, `VAL` and
  `TIMER = n` (0x190-0x1AC); the current `COLOUR` foreground and background
  (0x1B0-0x1B4); and `PinVal` and `PinPut`, which read and drive a pin as
  `PIN(n)` and `PIN(n) = v` do (0x1B8-0x1BC).
- **A CSUB may take sixteen arguments on the RP2350**, ten on the RP2040 as
  before.

The CallTable is found at run time through the VTOR register, so one compiled
CSUB runs on the RP2040 and the RP2350 and on every variant; a CSUB built with
the new header needs this release or later. The exception is a CSUB that reads
the variable table (its `dims[]` are five `int`s on the RP2350 and six `short`s
on the RP2040) or the `Option` structure (laid out per variant): that must
still be built for the chip, or variant, it runs on. `docs/armcfgen.md` lists every
vector with its signature.

### USB host

The USB host stack is now **TinyUSB 0.21** with PicoMite's patches on top.

- **Reads from a USB flash drive (C:) run at several hundred KB/s** instead of
  about 64 KB/s, faster than the SD card on the same board, so `PLAY MP3
  "C:/track.mp3"` streams without underruns.
- **Several devices behind a hub enumerate reliably** on every kind of reset.
  The connect chime plays once, after enumeration, instead of from inside it.
- **Plugging in one device no longer silently kills another**: a recycled
  endpoint slot could capture a live endpoint's completions.
- **RP2040 keyboards no longer fault on plug-in**: control transfers are
  double-buffered again on RP2040, where single buffering walked into erratum
  E4. RP2350 keeps its single-buffered fix.
- **Recoverable USB conditions recover and report** (`[USB DATA_SEQ 3 @181]`)
  instead of taking the interpreter down with a bare `*** FAULT`. The counts
  are readable with `PEEK`.
- **`UPDATE FIRMWARE` is in every build**, so the USB host variants can reach
  the bootloader without the BOOTSEL button.
- **GPS on a USB serial port**: `OPEN "COM3:" AS GPS` through `COM6:` now
  starts the parser, as the UARTs always did.
- **Mouse reports are decoded from the mouse's own HID descriptor** when
  `OPTION MOUSE SENSITIVITY` is set, so mice with extra buttons, padding,
  report IDs or wide movement fields work.

### Sound

**`PLAY BBC SOUND channel, amplitude, pitch, duration`** and **`PLAY BBC
ENVELOPE`** are the BBC Micro's `SOUND` and `ENVELOPE` statements with the same
parameters, units and behaviour, on every variant including the RP2040: three
square-wave channels and a noise channel, eight-deep queues per channel, sync
marks for chords, `&H10` to flush, sixteen envelopes with three-section pitch
envelopes and ADSR amplitude at the authentic 100 Hz, and all eight of the
BBC's noises including the two clocked by channel 1's pitch.

```basic
FOR p = 53 TO 101 STEP 4 : PLAY BBC SOUND 1, -15, p, 5 : NEXT p
```

Also: the VS1053 `PLAY SOUND` right-channel sawtooth and silent-channel DC
offset are fixed, and the computed square and sawtooth waveforms are
band-limited. `PLAY SOUND` type N takes a dwell rather than a pitch.

### Cameras (RP2350)

**OV5640 support**: `CAMERA OPEN OV5640` with QVGA RGB565 preview, motion
detection (`CAMERA CHANGE`) and JPEG capture at VGA to 5MP in three qualities.
White balance is frozen at the preview's converged setting for stills, and the
pixel clock follows the CPU speed. `CAMERA OPEN` no longer needs a display for
JPEG capture and motion detection; a misconfigured or disconnected camera
reports which signal stalled instead of freezing; capture no longer disturbs
the PSRAM/flash controller; the capture inner loops are faster.

### New commands and functions

- **`LOAD file$ [, C] [, R]`** crunches a program as it loads, as `AUTOSAVE C`
  and `XMODEM C` already could, so a program too big for memory can come off a
  disk rather than being pasted up the console. The suffix letters are now
  matched in full, so `LOAD "p.bas", RUN` is a syntax error rather than `,R`.
- **`TILEMAP LOAD file$, id, slot, tileW, tileH, tilesPerRow`** reads a tile map
  from a text file (`.map` by default) so a large map need not live in `DATA`.
- **`MATH CLAMP in(), lo, hi, out()`** limits every element to a range, integer
  or float, strided; 16 elements in 14 us.
- **`BASE$(base, number [, chars])`** for bases 2 to 36.
- **`MM.ERRLINE`** is the line of the last error, beside `MM.ERRNO` and
  `MM.ERRMSG$`.
- **`MM.INFO(TELNET)`** (WiFi builds) is 1 while a Telnet client is attached.
- **`MM.INFO$(BOOT)`** reports a brown-out reset distinctly on the RP2350.
- **`WEB PING address$ [, count] [, timeout_ms] [, avgvar]`** (WiFi builds).
- **`TURTLE`** colour commands accept `COLOR` as well as `COLOUR`.
- **`KEYDOWN()` works on the PicoCalc's built-in keyboard**, and Ctrl+C typed
  quickly on a PicoCalc no longer produces a literal `c`.
- **SHIFT with the left and up arrows** now has key codes of its own, `LEFTSEL`
  (&HA2) and `UPSEL` (&HA4), beside the existing down and right codes.
- **`MAX3D` is 32**, up from 8, so a scene can hold 32 `DRAW3D` objects.
- **PicoComputer 3 configures itself at boot** on the RP2350 builds.

### Boot robustness

- The library check above.
- **The PSRAM bring-up can no longer hang the boot.** Its two QMI handshake
  waits had no timeout and run inside the boot watchdog window, so a PSRAM
  that did not answer rebooted the board into the same wait: a silent boot
  loop that also rewrote the option sector every cycle. The waits are now
  bounded; a chip that does not answer is reported as `PSRAM not responding`
  once the console is up and the option is kept for the next boot.
- **A magic key mismatch is a full clean**, A: drive included (see the box at
  the top). A firmware version change of the same variant resets nothing.
- **RP2040 boot loop fixed**: littlefs's lookahead buffer lost its alignment
  when `FileIO.c` was compiled for size and the boot-time mount of A: faulted.
- **`SAVE IMAGE` writes the colours the screen is showing**, including after
  `MAP SET`.

### Fixed

Two of these have been in the firmware for a long time and are worth calling
out. Both were found while chasing a Game*Mite report on PicoMiteRP2040MIN,
and both were proved on hardware before and after the fix:

- **SD-card access straight after a background framebuffer copy failed** on
  any board where the card shares the system SPI with the display, which is
  every Pico-ResTouch and Game*Mite. The only workaround was a `PAUSE` tuned
  to the CPU speed. Details under *Files and drives*.
- **Reading the screen after a framebuffer session rebooted the board** on an
  SPI panel that cannot be read back, such as the ILI9488W on the ResTouch
  3.5: `SAVE IMAGE`, `BLIT READ` or `PIXEL()` after `FRAMEBUFFER WRITE N`
  went through a null pointer. Details under *Graphics*.

Files and drives

- **A file operation straight after a background `FRAMEBUFFER COPY ,B`
  (or `MERGE ,B` / `BLIT ,B`) no longer fails with an I/O error** when the SD
  card shares the system SPI with the display. The copy runs on core 1 after
  the statement has returned, and the next `PLAY MODFILE`, `LOAD BMP` or file
  read used to drive the same bus at the same time; the only cure was a
  `PAUSE` tuned to the CPU speed. The SD driver now waits for the burst to
  finish before touching the card. The continuous background `MERGE` is
  unchanged: it restarts itself, and a program still has to keep file
  access away from it.
- Reading part of a file after `SEEK` on an SD card started up to 512 bytes
  late (`MEMORY INPUT`, `LONGSTRING LOAD`, structure `LOAD`); `LOC()` could be
  wrong after a seek; `EOF()` could say there was more after a seek to or past
  the end, on SD and on flash.
- The file manager froze or faulted copying directories from a USB drive: its
  5.8 KB stack frame overflowed core 0's 8 KB stack. `EDIT` from the file
  manager could then run out of heap; fixed as well.
- The HDMIUSB build crashed launching a program from the file manager.
- `OPTION DISK SAVE` dropped the platform name and the telnet console mode.
- `RAM FILE LOAD` left the running program without its subroutines, wrote 1 KB
  past the PSRAM allocation map, and `RAM ERASE ALL` cleared 128 KB beyond the
  end of the PSRAM and into the heap.

Graphics

- **`SAVE IMAGE`, `BLIT READ` or `PIXEL()` after a framebuffer session
  hard-faulted on an SPI panel that cannot be read back** (ILI9488W,
  ST7789, ILI9481, GC9A01, the ST7735s and others). `FRAMEBUFFER WRITE N`
  restored the panel's drawing routines but left the read routines bound to
  the framebuffer reader with no framebuffer selected, so the next read went
  through a null pointer and the board rebooted. They now report "not
  available on this display" as they do before any framebuffer is created.
  On these panels `SAVE IMAGE` reads the framebuffer while `FRAMEBUFFER
  WRITE F` or `L` is in force and is refused for `N`; on panels with read-back
  it reads the screen for `N`.
- `FRAMEBUFFER CLOSE L` and `CLOSE T` were transposed and a selective close
  discarded the other buffers; the mode 5 layer and the mode 2 and 5 top layers
  were never freed.
- `FRAMEBUFFER LAYER` drew behind the display on the HDMI builds in modes 2
  and 5 when no `LAYER TOP` existed.
- `DRAW3D()` never returned a value; `CLOSE ALL` left the last object; `LIGHT`,
  `SET FLAGS` and `RESET` faulted on a missing object.
- The mouse cursor could leave a block of corruption behind on GUI and
  on-screen keyboard redraws; OSK keys could not be clicked with a mouse under
  `OPTION GUI CONTROLS 0`; the GUI TEXTBOX pop-up keyboard could not produce
  lower case.
- `CIRCLE` with an aspect greater than 1 and a one-pixel line left gaps; font
  7's percent sign was mirrored; the brownian demo left sprite trails.
- The editor mis-placed a mouse click or tap on a horizontally scrolled line
  and did not refresh its status line after a terminal click.

Interpreter and maths

- `REDIM` recreated arrays as the default type, losing INTEGER and STRING data.
- `MATH CHI` indexed past its table above about 8x8 and had wrong degrees of
  freedom under `OPTION BASE 1`; `MATH M_INVERSE` leaked a row per call;
  `MATH CRC12` masking, the CRC `reverseOut` argument and `Q_CREATE` angle units
  were wrong; assorted argument checks in the MATH array helpers.
- `JSON$` could read 8 bytes past its source array under `OPTION BASE 1`.
- Regular expressions: `{n}` matched n or more times.
- `MM.VER` read past the end of the version string on a release build.
- The console emitted the autowrap escape before every input line; it is now
  sent once at reset and once when the editor exits.
- `PIO SYNC` wrote the wrong PIO's CTRL register and PIO DMA completion
  disabled the wrong state machine on PIO 2.
- dr_wav's 4 KB scratch buffers come from the heap, not the stack.
- The interpreter had become about 7% slower in b2 because newlib's `strlen`
  and `strchr` moved to flash; both are RAM-resident on every variant, and the
  reference benchmark is faster than before.

Network

- `WEB TCP CLIENT REQUEST/READ/STREAM` could write 8 bytes past the
  destination array; `WEB SCAN` and the receive commands reject an array too
  small for any payload; the CRLF terminating a transmitted HTTP body was in
  the wrong order.
- The GPS monitor could overflow the stack when printing to a display console.
- `MM.DEVICE$` said `WebMite` on PicoMiteHDMIWEB; `RAM FILE LOAD` wiped the sub
  table on that build.
- Bluetooth console and keyboard fixes.

### Memory and flash layout

- The MMBasic heap is smaller on the USB host builds to give the new USB
  host stack the C heap it needs: `PicoMiteRP2040USB` 124 KB,
  `PicoMiteRP2040VGAUSB` 96 KB, `PicoMiteRP2350USB` 296 KB and
  `PicoMiteRP2350VGAUSB` 160 KB. The maximum program size follows the heap
  on the RP2350 builds and on the VGA builds; the plain RP2040 builds keep
  their 120 KB program size (116 KB on `PicoMiteRP2040MIN` from RC2).
- Several variants moved their flash region during the beta cycle. That no
  longer matters for upgrading: every board is reset by this release anyway.
- **`PicoMiteRP2040` moved again in RC1**, 912 KB to 928 KB, **and back to
  912 KB in RC2**, now that the trace cache is gone; its heap also grows from
  120 KB to 128 KB. Flash moves only in 16 KB steps, and every move resets the
  board and reformats A: when it first boots the new version.
- **RC2 also moves `PicoMiteRP2040MIN`** (688 KB to 704 KB, with its program
  size 120 KB to 116 KB, so its A: drive keeps its place and size but the board
  still resets) **and `WebMiteRP2350`** (1456 KB to 1472 KB; its A: drive is
  16 KB smaller). No other variant moved.

### For anyone building from source

- The firmware builds with **pico-sdk 2.3.0**. The USB host is **TinyUSB
  0.21.0** in a sibling `../tinyusb-0.21` tree with PicoMite's patches; run
  `tinyusb-patches/setup-tinyusb` once and it fetches the release and applies
  them. The README build instructions are written around this.
- `buildpicomite.bat` takes the version from `Version.h`, pins a Release build,
  stops on the first variant that fails its flash/RAM/heap/alignment fit
  checks, and runs those checks before copying the .uf2 into `uf2/`.
- `tools/release_preflight.py` gates a release: binaries present and named for
  the version, fresher than the last firmware commit (by commit time, never
  mtime), manual PDF byte-identical to the master, tree committed and pushed.
- `misc/FileIO.c` compiles at `-Os`. `strlen` and `strchr` are RAM-resident.
- `SaveProgramToFlash` takes the flash region to write; `ImageSlotAddress()` is
  the one place a slot number becomes an address; `LibPresent()` means "a
  library is active"; `PrepareProgramExt()` bounds its walks to
  `MAX_PROG_SIZE`; `LibraryImageValid()` is the boot check.
- `Option` gains `LIBRARY_HASH` in its last four bytes with the struct still
  exactly 896 bytes, asserted at compile time. `MAXIMAGESLOTS` is 3 on the
  RP2040 and 8 on the RP2350. `PSMAPWORDS` in Memory.h sizes the PSRAM map
  once; static asserts guard the RAM slot reserve and the context save.
- The CallTable has grown by appending; existing CSUBs are unaffected.
  `armcfgen` compiles with `-fno-jump-tables`.
- Board tests in `Testfiles/`: `ArrayCopyTest`, `ArrayCopyStructTest`,
  `ArrayFuncTest`, `ErrLineTest`, `TilemapLoadTest`, `RamImageSlotTest`,
  `RamLibraryTest`, `FramebufferMergeTest`, `MultiFileLibraryTest`,
  `SeekBulkReadTest`, `SdCopyBTest` (needs the SD card on the system SPI,
  e.g. a Pico-ResTouch-LCD-3.5), `single_element_matrix_demo`.
- `MM.VER` distinguishes the release candidates from RC1 onwards: the fourth
  field is read as n+50, so RC2 reports `6.040052`, RC1 `6.040051` and RC0
  `6.040050`. The
  offset is 50 rather than 100 because that field owns only two digits, which
  puts the practical ceiling at RC49. Every `RCn` used to report a bare
  `6.04`, so a board just reflashed could not be told from a stale one.
