What the compiler leaves as text

Every program in the repository and on the PC3's SD card was compiled by the board's own compiler, and each statement it left as a text fallback was found, classified and weighted by whether it runs inside a loop. Headless workloads were then run under OPTION PROFILING to see which fallbacks actually execute. The result is the next set of statements for the compiler.

COM16: PicoMiteHDMIWEB V7.0.00b4 (development, SDK 2.3.1), RP2350B at 315 MHz, 6 MB PSRAM, OPTION COMPILE ON. The census is of the morning's build, V7.0.00b4 (stream format RB_VERSION 33). The updates re-measured the games, the benchmarks, walkr and the workloads during the day, last on V7.0.00b5 as released (RB_VERSION 37, the same firmware, at 315 MHz); the commits are in the summary.

  • Where this leaves it: diminishing returns for coverage. The measured workloads run 96.7% to 100% of their statements compiled, and what they still run as text is mostly commands whose own work dwarfs their parsing (MATH, DRAW3D, CLS, FRAMEBUFFER, TEXT of a string array element) and console I/O. Prince of Pico, 96.7% compiled, is only 1.4 times faster compiled than interpreted, because its time goes on drawing. And flash is now the limit: HDMIWEB has 200 bytes spare, PicoMiteRP2350VGA 740 and PicoMiteRP2350USB 756, so each further item is likely to move flash regions again, resetting those boards and shrinking their A: drive. What is still worth doing, in order:
    • IF ... GOTO, GOSUB and ON (item 10): the one measured workload well short of the rest, the Micromite benchmark at 76.7%, and the benchmark people compare boards with. Small to medium.
    • CONTINUE DO (item 11): small; the Exile kernel's last fallback.
    • String SELECT CASE and SELECT of more than 10 values (item 12): Prince of Pico's largest, about 7,500 samples. Medium.
    The broad items after these (strings through calls, string array elements, whole arrays as arguments, MATH) have the largest counts across the corpus, but each is medium effort and costs flash; time is better spent on the speed of what is compiled, and the flash margins need a decision first.
  • Deep recursion (section 7). The original TSCP chess reaches 21 BASIC call levels in its depth-5 search, and three limits applied:
    • NEXT closed the caller's loop: fixed in 5b90865.
    • The C stack: about 12.4 KB on HDMIWEB, which is 14 call levels as text and 19 compiled.
    • The local variable table: 192 entries on the RP2350, which OPTION LOCAL VARIABLES n raises.
    Peter's Bas/chess/chessiter.bas runs the same search as a loop, at most 7 call levels deep, and is the version measured here.

The next set of statements

Items 1, 3 and 4 are done, and item 2 for programs that define no TYPE, all committed on 3 October. The counts in the table are the morning census's, so for those four they show what each item has taken. The list is ordered by three things, in this order:

  1. the time the fallback took in the measured workloads (section 3);
  2. how many statements inside loops need it, and in how many programs;

half done Half done, committed 418892f: in a program that defines no TYPE, dotted names compile as the plain names they are (RBDotBlocked). That compiles only 38 in-loop statements in 9 programs. 400 in-loop statements in 32 programs (259 alone); games: 0. Effort: Small (no TYPEs) to medium (with TYPEs).

Today: Every name whose spelling has a dot is refused as a structure member: RBVarRefS, RBElement and RBCompileLocal test memchr(sp, '.', len). Many MMBasic programs use dots as namespaces on plain variables (Dim integer R.running, Dim Float srv.pCurr(17)). And when a program defines any TYPE, findvar does not bind a dotted symbol either (FINDVAR_DOTBLOCKS: g_structcnt > 0 and SYMC_DOT), so the text path looks it up by hashing every time.

To add: When the program defines no TYPE, findvar already binds dotted symbols, so the compiler only has to stop refusing them. When it does, a dotted name is a structure member only if the part before a dot names a TYPE instance. That can be settled once per name at PrepareProgram, where the TYPEs and their instances are known (a per-symbol flag beside SYMC_DOT), and then both findvar's binding and the compiler can treat the other dotted names as the plain names they are.

Evidence: It is the main reason walkr-robot gains under 5% (section 5): 306 of its 788 in-loop text statements need it, 216 need nothing else, and fixing it alone takes walkr's compiled share in loops from 33% to 51%. It is also the style of Petrobot, superclock and the solar_eclipse INPUT lines.

A bug, now fixed: IF and ELSE with two spaces after the command

The tokeniser skips one space after a command and keeps the rest; skipspace then steps over them, so cmdline - sizeof(CommandToken) is the command token only when there were none. Three places looked the IF table up there:

  • cmd_else, which then scanned for its ENDIF;
  • cmd_if, which then scanned for the next arm;
  • the compiler's ELSE (RBCompileExit), which then stayed text.

In the corpus, all 65 ELSEs with two or more spaces before a comment were fallbacks, 51 of them in Petrobot, and all 95 with one space compiled.

fixed and committed on development, 3 October (6497832). CmdTokenBefore() in Commands.c walks back over the spaces (a token's bytes are never spaces), and RBCompileExit is given the token. Measured with Bas/bench/elsespace.py, 2,000 passes over a 40-line block:

The census of the six programs with such ELSEs now compiles every one of them, and nothing else changed.

A cost, now removed: comment and empty lines inside compiled loops

A tester ran a compiled program 20,000 times a second as text and 37,000 compiled, and then 57,000 after MMEdit's crunch, which takes out comments, blank lines and indentation. The cause was the stream, not the interpreter:

  • each comment-only, empty or label-only line had a record of its own, a NOP;
  • a NOP is not compiled code, so the chain of compiled statements (RBRun) stopped at it and went back through RunStream, once per line per pass.

Measured on a two-statement compiled loop, 100,000 passes: no comment 237 ms, one comment line +18%, three comment lines +30%.

fixed and committed on development, 3 October (3071436, RB_VERSION 35). Such a line now has no record, only a map entry pointing at the next statement's record:

  • a GOTO, NEXT or LOOP that lands on it starts at the next statement, which is all the text loop does there;
  • the compiled chain runs straight past it;
  • a comment as a program's last line maps to the image's END record, which stops as the text loop does.

A fault found on the way: the end of a saved program

The test for item 8 faulted with OPTION COMPILE OFF, so in the interpreter itself, for one program length in 256. The program's last line was a false single-line IF with no ELSE:

  • cmd_if steps to the next line with skipline, which stops one byte past the line's terminator. On the last line that byte is the end marker's second zero.
  • ExecuteProgram stops only on two zeros. The writers padded with zeros to a block boundary (256 bytes in flash, 32 in RAM, a word for LIBRARY SAVE) before the FF FF FF FF that starts the binaries, so when the marker ended a block the next byte was FF.
  • The executor stepped onto FF FF and called command 16383 through a garbage pointer.

fixed and committed on development, 3 October (bc0c157), in the writers, not the runtime: SaveProgramToFlash, SaveProgramToRAM, LIBRARY LOAD's writer and LIBRARY SAVE now put a word of zeros after the marker. Every reader already skips any run of zeros before the FF, so the symbol table and the CSUB and font records are found where they are written:

  • Bas/savetest prints the same signature as before, by LOAD and by AUTOSAVE.
  • Padded so the marker ends a page, the binaries start a page later, and the CSUB's answers and the font are still right: in program memory by both routes, and in a library through LIBRARY SAVE, LIBRARY LOAD and LIBRARY LOAD …, RAM.

An image saved before the fix keeps its old ending until it is saved again.

A third bug: NEXT in a recursive SUB or FUNCTION

Found with TSCP chess (B:/basicchess/chessfaster.bas), whose search recurses with a FOR loop around each call. The fault was in the interpreter as well as in compiled code.

  • When a loop ended, NEXT also closed any other loop whose NEXT was at the same place, so that NEXT j, i closes both.
  • In a recursive SUB or FUNCTION every level's loop has the same NEXT, so the loop it found was the caller's. It stepped the caller's variable and ran the caller's loop body inside the callee.
  • A loop was lost at every return, until an EXIT FOR in quiesce left search's loop and the next NEXT failed with "Cannot find a matching FOR".

fixed in 5b90865: cmd_next and the compiled NEXT close another loop only at their own level. Bas/bench/fornextrec.py fails on the build before and passes after. main has the same code.

Deep recursion: the C stack and the local variables

With NEXT fixed, the chess program's depth-5 bench met two limits.

The C stack. On HDMIWEB it runs from 0x20082000 down to heapend: 8 KB of scratch RAM, plus 4.2 KB below it, about 12.4 KB in all.

  • A BASIC call costs about 900 bytes as text and 660 compiled, so "Stack overflow" came at 14 call levels as text and 19 compiled.
  • On a test build with 32 KB less user heap (about 45 KB of stack), the original TSCPChess bench, which stops after 30 s, needed 16.8 KB at 18 levels as text and 12.6 KB at 19 levels compiled. Compiled, it searched 4,864 nodes against 1,280 as text.
  • The frames on the call path are within about 40 bytes of what they were in 5.08. That release checked the stack only against a fixed HEAPTOP address, which allowed 10 to 14 KB. Below its stack lay core 1's scratch bank and the top of newlib's heap, which a non-VGA build seldom uses, so an overrun there did no visible damage.

The local variables. With enough stack, chessfaster's full depth-5 search reached ply 14 and 21 call levels, using 13.9 KB of stack. Then it stopped with "Not enough Local variable memory".

  • The RP2350 build has 192 local variable entries; search takes 14 a level and quiesce 8.
  • OPTION LOCAL VARIABLES n, at the top of the program, moves entries from the globals to the locals.

How much stack each call costs, and how many locals a build allows, are left for a later decision.

since Peter's Bas/chess/chessiter.bas (eaeab32) runs the same search as a loop, with each ply's alpha, beta, depth and move index in arrays, so a node no longer costs a BASIC call: the deepest call path is 7 levels at any ply. It is the version measured in sections 3 and 4. The original's recursion inside FOR loops is the form the manual documents as unreliable.

A fourth bug: Prince of Pico did not run on HDMIWEB V7.0.00b4

fixed in db2353e (4 October). The scenario harness (A:/gb/gbpop.bas, loaded with ,C) stopped at line 117, Dim INTEGER vPanelB, ..., with Error : Not enough memory for 2048 bytes: put OPTION SYMBOLS OFF first, compiled or not, after a CPU RESTART, without its profiling twin, and with OPTION SYMBOLS OFF too (the hint was wrong). MEMORY showed 192 variables in 197 KB and 6 MB of PSRAM free.

The cause was not the compiler. Since 509622a (1 October) the globals' records are in the heap, in chunks of 32 records (2 KB on the RP2350), taken from the SRAM heap only, as each chunk filled. The heap puts an array in SRAM first, so the game's arrays had taken all of it, and its 193rd variable could not get a seventh chunk. The locals' chunks, taken the first time the local stack is that deep, could fail the same way in the middle of a run.

  • At RUN the program and the library are scanned for the globals they declare (the names of every DIM and STATIC, and of a CONST outside a SUB or FUNCTION), and their records are taken from the SRAM heap before anything else: about 590 for Prince of Pico, 38 KB.
  • A record chunk needed after that (a global made without DIM or by EXECUTE, a deep local) comes from PSRAM when the SRAM heap is full.
  • SAVE CONTEXT and LOAD CONTEXT copy any chunk that is in PSRAM, because SAVE CONTEXT CLEAR and CHAIN hand the records out again.

Test: Bas/bench/varpsram.py, which fails on the build before with the same error. The harness now passes its 274 checks compiled and is measured in section 3: 96.6% of what it runs is compiled.

The same work found the RP2040 PICO image 4 bytes over its flash limit since 74ed383 (item 7 split two helpers out of cmd_dim for Route B). d53c5df inlines them back on the RP2040, where Route B does not exist: every RP2040 variant fits, PICO with 156 bytes to spare.

8 · Method

How the census was taken

  • Compiling without running. Each program was sent by TFTP to A:/cc/p.bas with one line, END, in front, then LOADed and RUN. PrepareProgram compiles the whole image at RUN, and the program stops at its first statement before it can set a mode, open a file or wait for a key.
    • Elite and the Exile game load their library as their first statement, so for them the library and the program were put in one file. This compiles the same statements under the same rules.
    • Programs too large to LOAD were retried without their comment-only and blank lines.
  • Reading the stream. At the prompt, two command lines walked the stream's map in PSRAM (&H11723000 on this build: PSRAMstream) and wrote each record's key, STMT word, op word and command token to A:/cc/d.bin, which came back by TFTP. A record is compiled when its STMT word has RB_COMPILED.
    • Records were matched to source lines by their RB_LINESTART flags; every line, blank or not, has at least one record. LOAD's '#file line and the END line were skipped.
    • From RB_VERSION 35 (the update) a comment, empty or label-only line has no record, only a map entry pointing at the next statement's record. A third command line therefore writes each record's own key to A:/cc/k.bin, and a map entry whose key differs from its record's is taken as such a line. The update's scripts are in cc2/.
    • Lines were split into statements at : as tokenise does. 1,978 THEN and ELSE parts of single-line IFs, which are records of their own (RB_PART), are counted as statements in their own right.
    • On the games every line matched exactly. Programs with more than 2% unmatched lines were left out (2 programs).
  • Why. The compiler does not say why it refused a statement. The reasons here come from the statement's text, read against Stream.c's rules: RBValue, RBFunction, RBFnSplice, RBArgs, RBParams, RBCompileLocal, RBCompileSplice and the block compilers. The SELECT CASE and ELSEIF size limit was calibrated on the corpus: compiled SELECTs reach 10 values and none with 11 or more compiles.
    • 125 in-loop fallbacks, 0.8%, have no reason found or an odd one: 42 multi-line IFs, 22 LETs (some calling CFUNCTIONs), 23 lines in OPTION LEGACY's LINE (x,y)-(x,y) form, and a few others.
  • In loops.
    • Inside a loop in its own unit: a statement inside FOR/NEXT, DO/LOOP or WHILE/WEND, or between a label and a backward GOTO to it.
    • In a hot unit: any statement of a SUB or FUNCTION called from such a place, or from a hot unit, or named by SETTICK, an interrupt or ON KEY.
    A game's main loop makes most of its units hot, which is what happens.
  • Not runnable. A program is left out when the board refuses it at LOAD or RUN, or when a statement calls a name that is neither a command of this build nor a SUB or FUNCTION of the program. Running such a statement would stop the program with an error. This removes the CMM2, CMM1 and older Micromite programs on the SD card. The CMM1, welcome and *cmm2* directories and pc3a (a backup of A:) were skipped altogether, and identical files were counted once, the repository's copy first.
  • Measured runs. [PERF] counts every statement that runs as text by command, through RBExec. MM.INFO(COMPILE) gives the stream's RAN and CODE counts. [PCSLINE] gives the 40 busiest lines, joined to the census of the same source. INPUT and PAUSE lines collect waiting time, and PRINT lines console time.
  • Files. The scripts are in the session scratchpad cc/:
    • ccboard.py drives the census;
    • ccmap.py matches records to statements;
    • ccreason.py gives the reasons;
    • analyze.py works out loop context;
    • items.py groups and ranks;
    • dyn.py, dynparse.py and dynjoin.py handle the measured runs;
    • report.py writes this page.
    The per-statement table is stmts.json (212,533 rows). Nothing was changed on the board except OPTION COMPILE ON (left on), the files in A:/cc, A:/dy and A:/gb (copied from B:/pc3a/gb), and one CPU RESTART.
