TinyUSB 0.21 · RP2040 / RP2350 host driver

RP2 USB Host Hardening

Making multi-device enumeration behind a hub reliable on the rp2 host driver. This is the approach that was validated on hardware — not the one that looked best on paper. The two that actually mattered: keep the mount callbacks light, and make the control path tolerant of a documented silicon race.

Validated on a PicoComputer 3 (RP2350B) 2 keyboards + touch + MSC behind one hub for the MicroPython rp2 port

This began as three control-path patches and a plan to adopt the upstream root-cause fix. Then all of it was run on real multi-device-behind-a-hub hardware, across software, hardware and power-on resets. The result reorders the advice: the tolerant workarounds plus keeping the mount callbacks light gave four devices on every boot, while the “proper” hcd rewrite — correct as its analysis is — enumerated fewer devices on this marginal hardware. Below is what held up, in the order it matters.

Two independent problems

What actually breaks enumeration

Two unrelated things each cost a device behind the hub. One is a silicon race in the host driver; the other is the application doing heavy work in the wrong context. Both have to be handled — fixing only one still drops devices.

The silicon

The shared handshake latch

The RP2040/RP2350 SIE keeps one set of handshake-result latches — ACK_REC, RX_TIMEOUT, DATA_SEQ_ERROR — shared across the EPX control/bulk endpoint and the interrupt-endpoint poller. When a control transfer completes on EPX and the SIE then polls an interrupt endpoint — a keyboard or touch panel behind the hub — that poll overwrites the EPX latch before the IRQ handler reads it. A transfer the device actually ACK'd is misread as RX_TIMEOUT, and enumeration fails. It only shows with interrupt endpoints present, which is why #2517 reports the same hub working with a flash drive alone and panicking the moment a keyboard is added. #3533 documents the mechanism in full.

There are two ways to live with this race — tolerate it above the driver, or remove it inside the driver. The validated recommendation, below, is tolerate: it proved markedly more robust on marginal hardware.

Validated · do this first application side

Keep the mount callbacks light

Symptom

With the driver otherwise fine, one device — the marginal one — still fails to enumerate on some boots. On our rig, disabling a single connect chime was the difference between random 1–3 devices and a stable count.

Root cause

tuh_mount_cb / tuh_hid_mount_cb run inside tuh_task(), between the enumeration steps of the other devices on the bus. Anything heavy there — a sound (heap alloc + audio-clock reconfig), a slow log line, a blocking allocation — stalls the bus long enough for a marginal device behind the hub to lose its enumeration. The MicroPython and Fuzix rp2 ports both defer mount-time notification for exactly this reason; our hardware confirmed why.

The rule

A mount callback should do almost nothing — set a flag, stash an id. Anything with real cost (notifications, allocation, device setup that can wait) belongs on the main loop, after tuh_task() returns. Never call it from inside the callback.

the pattern: callback sets a flag, the main loop acts on it

// in the mount / unmount callback — cheap, non-blocking:
usb_event_flag = +1;   // device arrived  (-1 = left)

// in the main loop, right after tuh_task():
tuh_task();
usb_event_service();          // off the enumeration path — safe to be heavy here
A nice side effect. Latch the flag for the duration of whatever the service does (e.g. a chime), so a burst of devices enumerating together collapses into one action instead of one per device. A device that arrives after it finishes simply starts a fresh one.
The driver · the validated choice

Make the control path tolerant

These three patches sit above the silicon and tolerate the shared-latch race and its fallout rather than removing it. On the PicoComputer 3 — two keyboards (one marginal), a touch panel and a flash drive behind one hub — this set enumerated all four devices on every software, hardware and power-on reset. Keep all three.

Validatedhcd_rp2040.c

Grace period for control-pipe RX timeouts

What it does

On RX_TIMEOUT for endpoint 0 only, within a bounded window, it does not fail the transfer — it leaves it armed for the SIE to retry, so a spurious latch-clobbered timeout is simply outlasted and the transfer reads back correctly. Bulk and interrupt keep the fast-fail (their slow-path flow control is NAK, which never raises RX_TIMEOUT).

Why it holds

It is forgiving of exactly the marginal, race-prone case that a strict driver drops. Close the window only on a control-pipe completion — resetting it on any completion lets hub/HID traffic re-arm it forever and wedge the pipe.

if (status & USB_INTS_ERROR_RX_TIMEOUT_BITS) {
  usb_hw_clear->sie_status = USB_SIE_STATUS_RX_TIMEOUT_BITS;
  bool in_grace = false;
  if (epx->state == EPSTATE_ACTIVE && tu_edpt_number(epx->ep_addr) == 0) {
    if (!rx_timing) { rx_timing = true; rx_start_us = time_us_32(); }
    in_grace = (time_us_32() - rx_start_us) < 1000000u;   // 1 s ceiling
  }
  if (!in_grace) {  /* original STOP_TRANS + fail-the-transfer body */  }
}
// clear rx_timing on any EP0 completion, in xfer_complete_isr()
Validatedusbh.c

Enumeration-exclusive control dispatch

What it does

While an enumeration is in progress, only transfers to address 0, to the address being enumerated, and to the hub in use may claim the single control slot. Application control traffic — a keyboard LED write, a touch handshake — waits in the pending FIFO. This restores 0.20's effectively-atomic enumeration and keeps the shared EPX state from being disturbed mid-bring-up.

static inline bool ctrl_blocked_by_enum(uint8_t daddr) {
  return (_usbh_data.enumerating_daddr != TUSB_INDEX_INVALID_8) &&
         (daddr != 0) &&
         (daddr != _usbh_data.enumerating_daddr) &&  // driver-open phase
         (daddr != _usbh_data.dev0_bus.hub_addr);
}
// gate both the slot claim in tuh_control_xfer() and the pending drain
Validatedusbh.c

Disable the hub port on a failed enumeration

What it does

In enum_full_complete(false), send CLEAR_FEATURE(PORT_ENABLE) to the abandoned device's hub port. 0.21 otherwise leaves it enabled at address 0; if it wakes later it answers address-0 traffic in parallel with the next device's bring-up — the mechanism behind “pulling one device reported another disconnecting.” The chime must use a non-NULL completion callback (a NULL one blocks and deadlocks inside tuh_task()).

hub_port_clear_feature(_usbh_data.dev0_bus.hub_addr,
                       _usbh_data.dev0_bus.hub_port,
                       HUB_FEATURE_PORT_ENABLE,
                       port_disable_complete, 0);   // no-op cb, not NULL
The other path

The #3533 hcd — cleaner, but validate it

#3533 ships a from-scratch rp2 host driver that removes the race at source — it suppresses interrupt-endpoint polling around each EPX transfer (suppress_int_polling()), clears stale latches before every start (epx_prepare_for_start()), and carries a per-device EP0 max-packet table. It is the theoretically correct fix, and it drops in cleanly: the reference tree pins the exact 0.21.0 base, so its two files replace ours verbatim, compile and fit.

But on our hardware it enumerated fewer devices, not more. With the strict driver in place, the marginal second keyboard behind the hub was lost on most boots — a stable but incomplete count — where the tolerant workarounds above brought up all four every time. We did not fully isolate why: it may be a genuine sensitivity to a marginal device, or an interaction with the manual SE0 bus reset our firmware drives on restart (which MicroPython does not do). The correct diagnosis does not guarantee the stricter implementation wins on every device set.

Recommendation: treat #3533 as an option to evaluate, not a drop-in upgrade. If you carry a manual bus reset, test with it removed first. Validate against your real, marginal hardware — and if the tolerant workarounds already give you a reliable count, there is no urgency to switch until #3533 is merged and matured upstream.

Cheap and independent

Two more, regardless of path

  • RP2350 hub-timeout bit. Set USB_LINESTATE_TUNING_MULTI_HUB_FIX after tuh_rhport_init(). It is the controller's own accommodation for worst-case hub turnaround timing, off by reset default, and it addresses real hub delay rather than the latch race — complementary to everything above.
  • Task queue depth. Raise CFG_TUH_TASK_QUEUE_SZ from 16 to 64. Under several devices enumerating behind a hub the default overflowed, and a dropped completion is a silent stall in a release build.
How it was proven

Validating

  • All reset kinds, repeatedly. Software reset, hardware reset and cold power-on each brought up all four devices — every time. The race is probabilistic, so “first time, every time” across reset types is the only bar that counts.
  • MSC alongside HID. The failure needs an interrupt endpoint present to appear — a stick that enumerates alone but not beside a keyboard is the race, not a bad device.
  • Sustained transfer under load. A large read, or audio streamed straight off the flash drive, with HID live and no underrun.
  • Pull the marginal device and confirm its own connect/disconnect is reported, not a neighbour's.

Sources: TinyUSB #3533 (shared-latch race + reference tree), #2517, #2776. Approach validated in the PicoMite tinyusb-0.21 tree on a PicoComputer 3 (RP2350B): two keyboards, a multi-touch panel and a USB flash drive behind one hub — four devices on every software, hardware and power-on reset, with the stick reading ~8× faster than the 0.20 stack it replaced.
