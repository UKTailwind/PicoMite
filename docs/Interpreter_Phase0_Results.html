1 · Summary

Summary

  • The anchor is 81-87% interpreter overhead on every build and chip, measured against its own CSUB twin on the same build. MicroPython, with the same double-precision arithmetic on the same PC3 hardware, removes 38.8% of that overhead. That is the bar for Route A.
  • Operand work is two thirds of the time. Sampled on PICORP2350: evaluator 27.6%, name lookup 26.1% (findvar alone 25.1%), text walking 11.7%, ExecuteProgram 12.4%. The arithmetic itself is about 5%.
  • About 17% of the anchor's time goes on deciding which variable a name means: hashing the name 6.3%, probing the local table 6.5%, checks 2.75%.
  • An address-keyed memo can't reach it. A throwaway findvar memo keyed on program address gained 1.15%. The hot lookups are array references and the names inside copied index and argument text. Only symbol ids that travel with the text (S5/S6) can take this 17%.
  • The per-statement checks cost 12.7% on HDMIWEB, almost all of it ProcessWeb, even with WiFi off. The same checks cost 3.8% on HDMIUSB and 2.4% on PICORP2350.
  • Against MicroPython, statement by statement, MMBasic is 6-7x slower on arrays, 9-12x on IF, 6-9x on calls, 12x on literals, 20x on long names and 50x on a local read inside a SUB. It is 3.5x faster on strings and holds its own on float maths.
  • The placement floor is about 1%, not the historical 4%. Gains must beat 2%.
  • The corpus goldens are in place on both chips as the correctness reference. They turned up five firmware bugs, reported in section 8 and not fixed here.

The hot lines

  • File line 2845, 6.8%: findleap's linear search, If (jday >= jdleap(i) And jday < jdleap(i + 1)) Then, 27 passes over two arrays on each of 1,455 calls.
  • File lines 1669-1673, about 13%: nut2000_lp's series, each statement holding about seven 2-D reads xnut(k, i%) and a SIN or COS.
  • File lines 829-835, about 9.6%: sun()'s 50-term series over xsa, xsb, xsl and xsr.

The anchor's hot core is series evaluation dense with array references. That is where MMBasic trails MicroPython by 6-7x.

5 · Floor and ceiling

Placement floor and the address-keyed ceiling

  • Placement floor. Adding the sampler (+1.3 KB of flash and a little RAM code, never run) moved the anchor +0.96%. A 2 KB flash pad moved it −0.08%. P is about 1%.
  • findvar memo ceiling (0g, throwaway, never committed; the patch is kept in the session files). It memoised scalar lookups keyed on the name's program address, invalidated by a serial on every variable creation, ClearVars and ERASE. It gained 1.15%, golden output intact, and findvar still took 24.4% of the samples. So a binding cache keyed on addresses is the wrong mechanism, the trace cache's failure mode measured directly. The resolution work itself (section 3) is about 17% and real.

7 · Route A order

What gate G2 recommends

Ordered by measured share of the anchor, cost and risk. Every step is still one build and one commit, run against the goldens on both boards.

  1. S1a: ProcessWeb behind the 100 µs cadence on WEB builds, about 10% on HDMIWEB. Then S1b/S1c, an inline tail test, 2-4% elsewhere. Small and low risk.
  2. S5/S6: symbol ids in the stored image, with lazy binding, aimed at the ~17% resolution work and FindSubFun. It is the largest structural item, and the memo result says it must be symbols.
  3. S4: array indices evaluated in place, aimed at the hot array lines: the index copy, and part of makeargs and getclosebracket.
  4. S8: built-in arguments in place for the audited numeric functions (SIN and COS are everywhere in the anchor), removing getclosebracket, the temp page and memcpy.
  5. S2: RP2040 quick wins, the subfun count, and power-of-two variable tables (decision D4) so the hash % stops being a divider call, about 3% on the RP2040.
  6. S3: call descriptors, once a game profile shows calls are large.
  7. S5b label symbols for the RP2040 GOSUB/GOTO case. S7 partner tables and S9 comments have a small share on the anchor; keep them for workloads that show it.

The evaluator core, 27.6%, is left after Route A. That is the Route B question at G3.

8 · Goldens and bugs

The correctness reference, and what it found

The mmb2c corpus (112 programs) runs on both chips with Bas/bench/goldens.py. What each build prints is kept in Bas/bench/goldens/ as the reference later builds must reproduce. Against the translator's own expected output, the RP2040 VGA got 38 MATCH, 12 DIFF and 52 ERROR. PICORP2350, which has no display, got 35 MATCH, 9 DIFF and 66 ERROR. A classify-and-verify pass sorted every RP2040 mismatch: missing hardware 25, deliberate MMBasic behaviour 17, translator-only features 11, harness 5, formatting 3.

Firmware bugs found (not fixed; each is Peter's call)
  1. MATH M_INVERSE of a 1x1 array fails with "Not enough memory for 0 bytes": cofactor() calls determinant(0), which calls GetMemory(0). Repro: Option Base 0 : Dim Float s(0,0), si(0,0) : s(0,0)=4 : Math M_Inverse s(), si().
  2. An error in an ELSEIF condition is reported on the previous arm's line. The IF jump table stores each arm's own line where the next arm's is needed (Commands.c ~3817 against the comment at MMBasic.h:752).
  3. On VGA, BLIT FRAMEBUFFER with out-of-range source coordinates does nothing, silently, where BLIT FLASH and plain BLIT raise "Number out of bounds".
  4. PLAY SOUND accepts an invalid type string once the channel has played, because the local mode pointers start from the current waveform (io/Audio.c:2065) and the "Invalid type" check tests for NULL (:2210, :2238).
  5. A program that selects its own DefineFont and stops on an error breaks the next LOAD. "Invalid font number #10" appears and only a second LOAD works. Reproduced on PICORP2350.

Related: with no display, FRAMEBUFFER CREATE says "Not enough memory for 0 bytes" instead of "Display not configured", the same GetMemory(0) pattern as bug 1.
