Bugs found on main, September 2026

These turned up during the interpreter performance work on development. They were found by testing on the boards and by three read-only code surveys. Each one below is present on main. For each, the report gives where it is, what goes wrong, how to confirm it, and a suggested fix. None is fixed on main. Four are already fixed on development and can be ported.

Line numbers are main at cbd99fb (2026-09-25). "Confirmed" means seen on a board; "by reading" means found in the code and not yet reproduced.

Fixed on development, still on main

1 · PIO TX interrupt: wrong FIFO depth for SMs 1-3

Where: core/MM_Misc.c:10265, checkdetailinterrupts: int full = (pioinuse->sm->shiftctrl & (1 << 30)) ? 8 : 4;

  • What goes wrong: pioinuse->sm is the array, so this always reads state machine 0's SHIFTCTRL. For SMs 1-3 the "TX FIFO was full" depth depends on whether SM0's FIFO is joined, not their own. A PIO TX interrupt on SM 1-3 then fires on the wrong edge or never fires.
  • Confirm: join the TX FIFO on SM1 but not SM0, then arm a PIO TX interrupt on SM1 and fill the FIFO. The interrupt should fire when the level drops from 8.
  • Fix: pioinuse->sm[sm].shiftctrl, as on development in 791bf93.

2 · I2C slave: lost ready bit

Where: the clears are at core/MM_Misc.c:10410, 10416, 10422, 10428 (I2C_Status &= ~…). The ISRs set bits at io/I2C.c:391, 396 (and 407, 412 for I2C2).

  • What goes wrong: the main loop's &= is a load, a modify and a store. If the I2C interrupt sets the other ready bit between the load and the store, the store wipes it. A receive and a send request arriving together can lose one interrupt.
  • Fix: clear the bit with interrupts masked (save_and_disable_interrupts/restore_interrupts), as ClearI2CStatus() does on development in 791bf93.

3 · WEB SCAN without a WiFi connection finds nothing

Where: net/WiFi.c:304: if (!WIFIconnected && startupcomplete) goto flashonly; in ProcessWeb, and WEB SCAN's wait loop at net/WiFi.c:575.

  • What goes wrong: the build uses lwIP's poll mode, where scan results arrive only through cyw43_arch_poll(). Without a connection ProcessWeb skips straight to the heartbeat, so nothing polls. The only results that get through are ones processed during the next scan's start-up command.
  • Confirmed on the PC3 (HDMIWEB, no OPTION WIFI): one run listed no networks, the next listed one. Development listed them every time.
  • Fix: a flag (WebScanActive on development) set for the scan's wait. ProcessWeb polls whenever it is set, even with no connection (development a07e8f2).

4 · DO fast path truncates a fractional limit

Where: core/MMtrace.c:3497, dofast_fill: *out_limit_i = (ctype == T_INT) ? limi : (int64_t)limf;. This path is always on in the eleven trace-cache builds, even with the trace cache switched off.

  • What goes wrong: an integer variable compared with a fractional number compares against the truncated number. DO : INC i% : LOOP WHILE i% < 2.5 stops at 2; the evaluator (and every other build) runs to 3.
  • Fix: compare in float unless both sides are integers, as the evaluator does. On development the whole fast path was rewritten and moved into Commands.c (04361c0); Bas/bench/inttests/dotest.bas checks 16 condition forms against the evaluator. On main the smallest fix is to keep a float limit when the number is not an integer.

Found by reading the code

5 · STATIC after a nested call attaches to the wrong variable

Where: core/MMBasic.c:2629 sets CurrentSubFunName on every SUB/FUNCTION entry and nothing restores it. STATIC builds its backing variable's name from it at core/Commands.c:8778-8788 (SUBNAME + "\x1e" + VAR).

  • What goes wrong: in SUB A, a STATIC executed after a call to SUB B is mangled as B\x1eVAR. It can find or create B's static instead of its own, sharing or losing state. CurrentInterruptName also overrides the SUB name for every STATIC run inside an interrupt SUB, including in SUBs that the interrupt SUB calls.
  • Confirm: SUB A : B : STATIC n : INC n : PRINT n : END SUB with a SUB B that has a STATIC n of its own; call A several times and watch n.
  • Fix: save CurrentSubFunName in the frame and restore it on return. Alternatively, derive the name from subfun[index] of the current frame when the STATIC executes.

6 · OPTION LOCAL VARIABLES above the compile-time size overflows g_hashlist

Where: core/MMBasic.c:225 struct s_hash g_hashlist[MAXLOCALVARS]. maxlocalvars can be raised up to MAXVARS-32 at :6481, and each local is pushed with no bound at :5253.

  • What goes wrong: with more live locals than the compile-time MAXLOCALVARS, g_hashlist[g_hashlistpointer++] writes past the array into whatever follows in BSS.
  • Fix: size g_hashlist to MAXVARS, or cap OPTION LOCAL VARIABLES at MAXLOCALVARS, or bound the push and raise "Too many local variables".

7 · Probe loops that can hang

  • Global variables: probe_global_slot (core/MMBasic.c:4556) only checks for wrap-around when called from inside a SUB. At level 0 a global region full of live entries and tombstones loops forever.
  • Labels: hashlabels' guard if (originalhash < 0) (:3713) tests an unsigned value, so it is never true. A full funtbl loops forever at PrepareProgram.
  • SUB lookup: FindSubFun on the RP2350 probes funtbl with no bound.
  • Fix: a counted probe (at most the table size) on each loop, with an error on overflow.

8 · RP2350: GOTO a label that shares a SUB's name

Where: SUB/FUNCTION names and labels share funtbl. For a label, index is a line pointer; for a SUB it is a small subfun index. The RP2350 findlabel (core/MMBasic.c:3742) does not check which kind it found.

  • What goes wrong: GOTO/GOSUB/RESTORE naming a SUB (or a label and a SUB with the same name) returns the SUB index as a program pointer, and execution jumps to low memory. The RP2040 scans the program for real labels and is not affected.
  • Fix: accept only index >= MAXSUBFUN in findlabel, as FindSubFun accepts only < MAXSUBFUN. Either reject a label that duplicates a SUB name at PrepareProgram, or allow both and keep them apart.

9 · FindSubFun ignores its type argument on the RP2350

Where: the RP2350 FindSubFun at core/MMBasic.c:1966 never reads type. The RP2040 version at :2020 filters SUB/CSUB (0) from FUNCTION (1) and checks the suffix.

  • What goes wrong: a SUB or CSUB name used with () inside an expression is found as a function on the RP2350 but not on the RP2040, so the same program behaves differently on the two chips.
  • Fix: filter by kind on the RP2350 as the RP2040 does.

10 · Unchecked buffer lengths: CALL, and tokenise's output

  • CALL: cmd_call (core/Commands.c:8318) and fun_call (core/Functions.c:243) strcat the argument text onto the name in a 256-byte temporary string with no length check. A long argument list overruns it.
  • tokenise: tokenise never checks its output position in tknbuf (256 bytes). Output can be longer than input: the 2-byte line header, the line number, an inserted LET or PRINT, and the CALC MM.ANSWER insertion.
  • Fix: check the length before each strcat ("String too long"), and bound the tknbuf writes.

11 · IRETURN stub has no terminator

Where: core/MM_Misc.c:10213 static char rti[2] holds only the 2-byte IRETURN token. The END SUB of an interrupt SUB returns to it, and skipelement/checkend read the byte after it.

  • Fix: static char rti[4], zero-filled after the token.

12 · CountLines on lines longer than 253 bytes

Where: core/MMBasic.c:3953 p += p[0] + 2;. This is reached only for lines whose skip byte is 0xFE (length unknown). The label length is in p[1].

  • Fix: p += p[1] + 2;. Effect: a wrong line count for errors or listing positions in programs with very long lines.

13 · OPTION PROFILING frames unbalanced by interrupts and ON…GOSUB

Where: a SUB-style interrupt (GotAnInterrupt, core/MM_Misc.c:10527) and ON…GOSUB (core/Commands.c:8625) raise g_LocalIndex without EnterLocalFrame. Their END SUB or RETURN goes through cmd_return, which calls LeaveLocalFrame (:5976).

  • Effect: the frame of the SUB that was interrupted is popped, so OPTION PROFILING's per-SUB times are charged to the wrong SUB. Only the CACHE builds that keep these frames are affected; g_LocalIndex stays balanced.
  • Fix: call EnterLocalFrame at both entries.

14 · MM.INFO(VARCNT) stale

Where: g_varcnt is updated only when a variable is created. erase() (core/MMBasic.c:6577) and ClearVars(level) decrement g_Globalvarcnt/g_Localvarcnt but not the total. MM.INFO(VARCNT) is at core/MM_Misc.c:9358.

  • Fix: return g_Globalvarcnt + g_Localvarcnt, or update g_varcnt alongside them.

15 · CSUB header: int dims[] only for PICORP2350 (to verify)

Where: PicoCFunctions.h:400 selects int dims[MAXDIM] only #ifdef PICORP2350, else short. Every RP2350 firmware build uses int dimtbl[5], and the variable-table layout is part of the CSUB ABI (CallTable 0x60).

  • Check: how CSUBs are compiled for the other RP2350 targets (HDMI, HDMIUSB, VGARP2350 …). If PICORP2350 is not defined for them, a CSUB that walks g_vartbl reads the wrong offsets.

16 · Leak when a nested call's argument errors under ON ERROR SKIP

Where: DefinedSubFunMem (core/MMBasic.c:536) is one global sentinel. It is set during argument processing (:2387) and cleared on success (:2628). In Foo(Bar(x), bad) the inner call clears it. If the outer call's later argument then errors under OPTION ERROR SKIP, the error handler does not unwind the outer frame.

  • Effect: the gosub frame and the heap argument buffers leak. Fix: a per-call sentinel saved and restored around the argument evaluation.

17 · Trace cache keeps global indices it never invalidates

Where: core/MMtrace.c. Its LET/INC ops store global slot indices and raw pointers. TraceCacheInvalidateAll (:3287) is called only by the trace cache's own option commands, although the file's comments say DIM, ERASE, REDIM and CLEAR invalidate it.

  • Effect (only with OPTION TRACECACHE ON): after ERASE or REDIM, a cached LET can write into a slot now used by another variable. Status: the trace cache was removed on development (04361c0).

Stepper (RP2350)

18 · RUN during a stepper job wipes the heap under the ISR

  • What goes wrong: RUN clears and reinitialises the heap while the stepper timer interrupt may still be walking planner blocks and arc buffers that live in it.
  • Fix: stop the stepper subsystem (disable its IRQ and drop the queue) before ClearRuntime and InitHeap, as END should.

19 · STEPPER ESTOP leaks the executing arc's buffer

  • What goes wrong: ESTOP drops the queue, but the buffer of the arc being executed is not handed to the retired list. Fix: one line: retire the current block's payload in the ESTOP path.

20 · Arcs slower than the requested feed rate

  • What goes wrong: on the PC3 test rig, arcs ran at about 2.4 mm/s with F6000 requested; straight moves were not affected. Next step: check the arc segment feed-rate clamp and the per-segment junction speed against the planner.
