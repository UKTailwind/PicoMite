Variable table · design for review

A compact variable table

Today every possible variable has a full 56- or 64-byte entry in a static table, used or not. That is 26.9 KB of the RP2040 VGA's RAM, more than a quarter of its 100 KB heap, and 47-49 KB on the RP2350 builds. This document reviews Peter's proposal to keep only a small slot per variable in the table and to give each variable its full record from the heap when it is created. It recommends doing it, with four changes, and sets out the design, what it costs, what it would break, and how to build it in stages.

Branch development at 0b7528f (V7.0.00b2) · evidence: two read-only code surveys for this review (the table's internals; everything outside the interpreter that depends on its layout), an offline count of the names in six real programs and the 112-program test corpus, and the 2026-09-30 heap investigations of la_24_2.bas and Bad Apple on the RP2040 VGA. No code has been changed.

Summary

  • The idea is sound and the gain is large. Replacing the static table with an 8-byte slot per global, and allocating full records only for variables that exist, frees 22-26 KB of static RAM on the RP2040 builds and 42-44 KB on the RP2350 builds. In whole 4 KB steps that is +24 KB of heap on the RP2040 VGA and +40 KB on the RP2350 VGA and HDMI builds.
  • Typical programs keep most of it. la_24_2.bas has about 61 globals and Bad Apple about 39, against the RP2040 VGA's 240 global slots. Each would need three chunks of records (5.25 KB), leaving about 19 KB more heap than today: far more than the 3-5 KB the symbol tables took, so neither would need OPTION SYMBOLS OFF.
  • Programs that fill the table roughly break even. Elite and Prince of Persia, which come close to the RP2350's 544 global slots, would gain 2-4 KB. Only a program that fills both the global table and the local stack at the same moment comes out a few KB worse than today.
  • Four changes to the proposal:
    1. Tell names apart with a 16-bit hash and the length, not the first three letters. In the six programs measured, a third to two thirds of all names share their first three letters with another name; length plus hash16 separated every one.
    2. Keep the record layout exactly as it is, with the 32-byte name. Shortening names to 8 bytes would move every field, which breaks PEEK(VARHEADER) offsets (Bad Apple uses Peek(varheader y1())+36) and the layout CSUBs are given, to save 24 bytes per variable.
    3. Chunks of 32 records on both chips: 7 pages on the RP2040 (as proposed), 8 on the RP2350 (not 7), so a local's record is found with a shift rather than a division.
    4. Locals need no hash slots at all. They are already a stack, so their records can be a stack of chunks indexed by slot number.
  • One new failure mode needs care: creating a variable can now fail for lack of heap. Allocating one chunk of globals and one of locals at RUN, before the program's own allocations, means a program with up to 32 of each never meets it.
  • Three things break and need a decision: the CSUB call table's pointer to the table (offset 0x60), PEEK/POKE VARTBL, and SAVE CONTEXT images written by older firmware. See Decisions.
  • Five phases, the first a pure refactor that must change nothing, each tested on the RP2040 VGA and the PC3 before the next.

How it works today

  • Globals occupy slots [maxlocalvars, MAXVARS) and are found by open addressing with linear probing on a 32-bit FNV-1a hash of the name (probe_global_slot, MMBasic.c:5017-5080). ERASE frees a global's slot outright if the next slot is empty. If the next slot is in use, a later variable may have probed through this one to reach its own, so the slot is marked T_BLOCKED (name[0]='~') instead. A lookup walks on past a blocked slot, so the chain stays intact; if the name is not found further along, the new variable takes the blocked slot it passed (MMBasic.c:5038-5075, 7187-7199). A blocked slot is therefore both a link in a chain and free for reuse.
  • Locals occupy slots [0, maxlocalvars) and since P6 are a stack, not hashed: a new local goes at g_localtop, g_hashlist records its slot and level, and a SUB's exit drops its locals (MMBasic.c:5433, 5807-5815, 6974-7016).
  • V7's symbol bindings (SymG, SymL, int16) hold slot numbers, so after the first lookup a name goes straight to its slot.
  • Much code keeps pointers into entries across statements, which is safe only because entries never move: the FOR stack, the DO fast path, by-reference parameters, STATIC, a FUNCTION's result, Route B's bind cache, and the IR, KEYPAD, PLAY STREAM and TCP STREAM writers, some of them in interrupts.
  • Short strings live inside the entry (val.s = &dimtbl[1]). The free paths skip them only because the table is outside the heap's address range: FreeMemorySafe ignores addresses it does not own.

The proposal, point by point

1. A small slot per variable yes

The slot table replaces the entries for globals. 8 bytes per slot: a state byte, the name's length, a 16-bit hash, and the record's address. 240 global slots take 1,920 bytes instead of 13,440.

The proposal puts the type in the slot. The design keeps it in the record only: the type and its flags are changed after creation (T_PTR on parameters and STATICs, the marker DIM sets while it allocates, ERASE), and read in many places, so a copy in the slot would have to follow every change. The slot needs only free, in use or blocked.

2. Records on demand, in 7-page chunks yes, adjusted

Seven pages hold exactly 32 RP2040 records, as proposed. On the RP2350 seven pages hold 28; eight hold 32. Using 32 on both chips makes a local's record a shift and a mask from its slot number.

Chunks must come from the SRAM heap only. GetMemory can fall back to PSRAM, which would slow every variable access, and SAVE CONTEXT does not capture PSRAM contents.

3. First three letters in the slot change

The aim, settling a probe without touching the record, is right. Three letters do not do it: 32-64% of names share their first three letters with another, and every STATIC's hidden global starts with its SUB's name. The FNV hash findvar already computes supplies a 16-bit check for free, and with the length it separated every name in all six programs. The record is still read once to confirm a match.

4. ERASE: waste, or reuse via a LIFO LIFO

A free list costs almost nothing: an erased record's first word links to the next free one, and creation takes from the list before the chunk. The slot itself is freed or marked blocked exactly as today, so chains stay intact and the slot is reused by the next new variable that probes through it.

5. 8-byte names, pointer for longer not now

It would save 24 bytes per variable (records of 32 / 40 bytes). But 4-34% of names in the programs measured, and 18% in the test corpus, are longer than 8 characters and would need a second allocation; every name comparison and print would need a helper; and the fields after the name would move, which breaks PEEK(VARHEADER) offsets (Bad Apple's +36), the layout CSUBs are given, and the Structures manual. With items 1-4 even full tables break even, so the saving is not needed. Revisit only as a deliberate compatibility break.

Recommended design

Data

struct s_gslot {                // one per global slot (MAXGLOBALVARS of them)
    uint8_t  state;             // GS_FREE 0, GS_USED 1, GS_BLOCKED 2 (T_BLOCKED today)
    uint8_t  namelen;           // 1..32
    uint16_t hash16;            // top 16 bits of the FNV-1a hash
    struct s_vartbl *rec;       // the record; NULL when free
};
struct s_vartbl                 // unchanged: 56 bytes on the RP2040, 64 on the RP2350
#define VREC_PER_CHUNK 32       // 7 pages on the RP2040, 8 on the RP2350

static struct s_gslot   g_gslot[MAXGLOBALVARS];
static struct s_vartbl *g_lchunk[(MAXLOCALLIST + 31) / 32];   // local record chunks, kept for the run
static struct s_vartbl *g_gfree;                               // erased global records (LIFO)
static struct s_vartbl *g_gnext, *g_gend;                      // next unused record in the current chunk

The index space stays as it is: slots below maxlocalvars are locals, the rest globals. So g_VarIndex, SymG, SymL, SymLShadow, SymLCanon, g_hashlist and the FOR/DO stacks keep their meaning. One accessor maps an index to its record:

#define VREC(i) ((i) < maxlocalvars ? &g_lchunk[(i) >> 5][(i) & 31] \
                                     : g_gslot[(i) - maxlocalvars].rec)

The ~350 uses of the variable findvar has just found take VREC(g_VarIndex). A cached g_VarRec, set by findvar, was tried in phase 1 and dropped: solar_eclipse ran 0.8% slower on the RP2040 VGA and 1.6% slower on the PC3. Whether to cache the record is decided in phase 2, measured against the real VREC.

Creating, finding and erasing a global

  • Find: hash the name as today, take hash % maxglobalvars, and probe. A free slot ends the search; a blocked slot is passed but remembered, and a new variable takes it if the name is not found further along, as today; a used slot whose namelen and hash16 match is confirmed against rec->name. The probe reads 8-byte slots instead of 32-byte names.
  • Create: take a record from the free list, else from the current chunk, else allocate a new chunk of 32 from the SRAM heap (top-down, like any persistent allocation). Clear it, fill it as today, then fill the slot.
  • Erase: free the variable's data as today, put the record on the free list, and free the slot or mark it blocked exactly as today (blocked if the next slot is in use).
  • Clear (RUN, NEW, CLEAR): the heap is reset anyway, so clearing the slot table and the chunk pointers is enough.

Locals

A local's record is g_lchunk[slot >> 5][slot & 31]. When the stack first reaches a new multiple of 32, a chunk is allocated; chunks are kept until the run ends, so a program allocates them only the first time its call depth reaches a new high. Making and dropping locals is otherwise unchanged. OPTION LOCAL VARIABLES n becomes a cap on the local stack alone: raising it no longer takes slots from the globals.

Seeding at RUN

RUN allocates the first chunk of globals and the first chunk of locals before the program runs (3.5 KB on the RP2040, 4 KB on the RP2350). A program with up to 32 globals and 32 live locals then never allocates for variables during the run, and so can never fail to make one for lack of heap. Larger programs allocate further chunks mostly while declaring their globals, near the top of the program, before their large buffers.

Things that must change with it

  • Short strings stored inside the record. Once records are in the heap, every free site would treat &dimtbl[1] as heap memory. Done in phase 1: VAR_INLINE_STR(rec) (val.s == &rec->dimtbl[1]) guards ClearVars (locals, and the whole table), erase, a SUB's string argument and a FUNCTION's string result in MMBasic.c, and STATIC and CONST in Commands.c. The first survey missed STATIC and CONST. MEMORY already made the same check and now uses the macro. A struct parameter needs no guard: its data is always heap memory.
  • SAVE CONTEXT copies the slot table and chunk pointers instead of the table. The records are in the heap, which it already copies to the same address. Add a header (version, the global/local split) so an image left by older firmware is refused instead of restored blindly. That hazard exists today.
  • Route B (RBBindAll, Stream.c:3880-3921) takes VREC(i) instead of &g_vartbl[i]. Its cache of record pointers stays valid because records never move.
  • MEMORY reports the slot table plus the records, which are now in the heap. "General" must not count them twice.
  • The heap and the flash layout. The freed RAM goes to HEAP_MEMORY_SIZE in whole 4 KB steps. Where a build has MAX_PROG_SIZE == HEAP_MEMORY_SIZE, MAX_PROG_SIZE must first be set to its current value, or the flash layout moves and A: is wiped on the update.

Speed

  • Bound lookups, the normal V7 path, gain one load for a global (slot to record) and swap a multiply for a shift and a load for a local. Against statements that take 5-150 µs this should not show; bench_micro will say.
  • Text lookups (the first lookup of each name, programs with OPTION SYMBOLS OFF, the command prompt) get faster. A probe reads 8-byte slots and touches a record only when the length and hash16 match, where today it compares names in 56- or 64-byte entries.
  • Route B is unchanged: compiled code uses the pointers it cached.
  • Creating a variable costs one chunk allocation per 32 variables.

Risks

Hazards to design for
  • Short strings inside records would be freed into the heap as if they were allocations. Every free site is guarded (phase 1).
  • Running out of heap while making a variable: mitigated by seeding a chunk of each kind at RUN, and by keeping local chunks for the run.
  • Width of the change: about 615 lines in 27 files mention g_vartbl, and about 155 call findvar. Most uses follow findvar and take VREC(g_VarIndex); the walkers (ClearVars, erase, LIST, MEMORY, SAVE CONTEXT, Route B binds, the symbol layer) need care. This is why phase 1 changes no behaviour.
  • A record in PSRAM would be slow and invisible to SAVE CONTEXT: the chunk allocator must use the SRAM heap only.
  • Interrupt writers pointing at a LOCAL already write into reused memory after the SUB returns. Heap records would make that worse, not new. See Found on the way.

Phases

1refactor

Accessors, no change in behaviour

Every indexed use of g_vartbl goes through VREC(i), defined for now as &g_vartbl[i]: 664 sites in 22 files, and every object the same size as before on both builds. The short-string guard at every free site. The SAVE CONTEXT header is covered by the magic-number decision. A cached g_VarRec was tried and moved to phase 2 (see Recommended design).

Gate: goldens identical on the RP2040 VGA and the PC3; solar_eclipse and bench_micro within noise; flash size noted.

Result: goldens unchanged on both boards apart from timings (and webudp, now fixed). solar_eclipse 26.683 s on the VGA (b2 26.684 s) and 16.219 s on the PC3 (b2 16.207 s). Flash +72 bytes (VGA), +176 bytes (HDMIWEB).

2globals

Global slots and record chunks

The slot table, SRAM-only chunks of 32, the free list, the seeded chunk, the PEEK/POKE VARTBL emulation, MEMORY and LIST, and the chosen meaning of call-table 0x60.

Gate: goldens; varcnt14, locvars6, symchain, rbf2, rbp5d; ERASE and REDIM, PIO MAKE RING BUFFER, STATIC, CONST short strings, VAR SAVE/RESTORE; solar_eclipse and bench_micro.

3locals

The local record stack

Chunk pointers, the seeded chunk, chunks kept for the run, OPTION LOCAL VARIABLES as a cap.

Gate: as phase 2, plus deep recursion (rbdepth), by-reference parameters and interrupts during SUBs.

4heap

Give the RAM to the heap

Per build, in whole 4 KB steps, with MAX_PROG_SIZE pinned so the flash layout and A: are unchanged.

Gate: every build's fit check; la_24_2 and Bad Apple with symbols on and no OPTION SYMBOLS OFF; the games on the PC3.

5optional

Afterwards, if wanted

Raise MAXGLOBALVARS where useful, since a slot costs 8 bytes; bind globals to record pointers rather than slot numbers.

Decisions

Decided, 2026-10-01
  1. Phase 1 goes ahead, on the branch compact-vars from development.
  2. CSUB call table 0x60 will point at the new slot table, with its layout published in PicoCFunctions.h. 0x64 (g_varcnt) stays.
  3. PEEK/POKE VARTBL are removed: they were unusable with the hashed table anyway.
  4. One chunk of globals and one of locals is seeded at RUN.
  5. Names stay 32 bytes in the record; 8-byte names are not pursued now.
  6. SAVE CONTEXT: the phase that changes its format also regenerates every build's magic number, so A: (and an old /.vars) is wiped on the first boot, as for any layout change.
  7. No g_VarRec in phase 1: it cost 0.8% on solar_eclipse (VGA). It is reconsidered in phase 2.

Found on the way

From the two surveys. Fixed on development before this branch was made:

  • Possible hang at level 0: fixed in 213f35b, tested with names chosen by simulating the hash.
  • Counter drift and g_varcnt: fixed in ee1abbf.
  • 32-character names and LIST VARIABLES: names are now at most 31 characters, as the manual says (2c747af).
  • Interrupt writers and LOCALs: 16 commands keep a variable past the statement; those that can refuse a LOCAL now do (57b74f8, 3bcbf49), WEB TCP CLIENT REQUEST/READ let their buffer go before returning, and the manual says so (c3d2103).
  • WEB UDP INTERRUPT 0, found by the goldens: fixed in 526331c.

Still as found:

  • SAVE CONTEXT has no version check: a /.vars written by another firmware is restored blindly. Handled for this work by regenerating the magic numbers (see Decisions).
  • Documentation: PicoCFunctions.h calls byte 35 dummy and omits T_STRUCT. Memory.c's memory-map comment (1860-1892) still describes a growing variable table.
