Route B · VM review

Making a compiled statement cheaper

The compiler now takes almost everything a typical program runs: the TSCP chess bench executes 99.9% of its statements compiled. It still runs 47 times slower than the same search converted by mmb2csub. Coverage is no longer the limit. The cost of each compiled statement is, and that cost is set by the executor (RBRun, the stream and the helpers it calls), not by what the compiler accepts. This review measures that cost piece by piece on the PC3 and proposes eight changes to the executor, ranked by what they would buy and what they would risk. Every proposal keeps the design's contract: the interpreter's state is exactly the text interpreter's wherever anything can look at it.

Measured 5 October 2026 on COM9: PicoMiteHDMIWEB RP2350B, V7.0.00b4, 378 MHz, OPTION COMPILE ON, PSRAM fitted (the stream in PSRAM, the test arrays in SRAM). Programs: Bas/chess (the bench), and three timing programs listed under Method. Nothing in the firmware was changed for this review. R0, the measurement phase, ran the same day on COM16 (the released V7.0.00b5, 315 MHz) and COM9; its results are in R0 results and change the order of work.

Summary

  • Outcome (5 October): the chess bench went from 58.9 s to 37.4 s compiled (-36%), Exile from 15.7 to 11.6-11.8 s (-25%), Elite from 6.9 to 6.1-6.2 s (-12%) and solar_eclipse from 6.9 to 6.0 s (-13%). D1, V4 (in part), V2 (in part) and V3 were done; see What was done for each step, what was tried and dropped, and why further VM tuning now pays less than it costs.
  • R0 found a defect worth fixing first (D1). After any SUB return or FUNCTION call, compiled statements stop chaining until a string temporary is freed, because a temporary-memory flag stays set. In the chess bench that is about a fifth of the time. The measured profiles then put calls and locals, the record boundary and stream fetches ahead of the ops themselves, and the order of work below follows that: D1 (done), V4, V2, V1, V3, then V6 and V5.
  • A compiled statement costs about 890 cycles in the chess bench; the C version does the same work in about 19. The bench to depth 3 runs 20,013,119 statements in 47.0 s compiled (19,985,062 of them as compiled code) and in about 1.0 s as a CSUB. That ratio, not coverage, is the 47x.
  • Five things make up that cost, and each was measured on its own.
    • About 175 cycles at every record boundary before a statement's own work begins: x = j costs 209 with two ops.
    • About 17 cycles a VM op.
    • Array elements cost 88 (1-D), 264 (2-D) and 352 (3-D) cycles on top of a scalar.
    • Calls: 1,197 cycles for a SUB with nothing in it, about 840 for each parameter, about 1,350 for each LOCAL made, and about 190 to 375 cycles for each statement of the called routine, which binds its variables again on every call.
    • Fetching the stream from PSRAM. The same statement costs 253 cycles when 50 of them loop, 534 when 400 do and 1,009 when 2,000 do. Once the hot code is bigger than the 16 KB XIP cache, each record is read from PSRAM again. The chess stream is 86 KB.
  • Eight proposals, cheapest and safest first.
    • V3: array descriptors addressed inline.
    • V4: a cheaper record boundary.
    • V1: a stream layout whose hot part stays in the cache.
    • V2: calls that make their parameters and bind their locals without findvar.
    • V5 and V6: fused ops and a cheaper NEXT.
    • V7: running a straight run of compiled statements as one block.
    • V8: native code, which is a different project, bounded here only so its size is known.
  • What to expect. Together, V1 to V7 might take the chess bench from about 890 to about 300-450 cycles a statement, roughly 2-3x. That is an estimate; R0, a measurement step, is proposed first to turn it into a figure. Getting near the CSUB's 19 cycles needs native code. No change to the VM alone gets there.
  • One measurement came before any code (done, see R0). A C-level profile of the chess bench and two games, on a build whose ELF is kept, and the same bench with the stream in flash rather than PSRAM, would replace this review's estimates of the split with figures. That is R0 in Order and gates.

Tried and dropped

  • A successor cache in each record (V4's first idea): two words more a record made Exile 9.1% slower through the XIP cache. Records must not grow.
  • ClearVars stopping below the level it frees while the local list is in order: no gain anywhere (Elite +2.5%), 260 bytes of RAM.
  • findvar's short path on the RP2040: solar_eclipse -0.4% and the logic analyser's trace redraw +1.2% on the PicoMiteVGA, for 770 bytes of RAM, so it is the RP2350's only.
  • RBRun's RAM functions kept at -O2 inside an -Os Stream.c: solar_eclipse unchanged, but most of the chess gain lost.

What limits further tuning

  • Code placement. Flash code and the PSRAM stream share the 16 KB XIP cache, so any change moves the games by about ±2% through which lines collide: a given image repeats to the millisecond, the next build reshuffles. V3 is 2.6% faster on chess and 1.5% on solar_eclipse, and 1.6-1.8% slower on Exile and Elite, which barely index 2-D arrays. A change worth less than about 3% cannot be measured, or kept, reliably.
  • RBRun's register allocation. A dozen lines in one op once cost every statement 8 cycles (spills, not the op's own code). Changes inside RBRun are kept to one path and few live values.
  • The stream's size. A record that grows costs more in misses than it saves.

R0 results

The measurement phase ran on 5 October:

  • C-level PC-sampled profiles on COM16, which runs the released V7.0.00b5 HDMIWEB image at 315 MHz with COMPILE ON;
  • XIP cache counters read during runs;
  • one run on COM9 with PSRAM switched off, so the stream sat in flash.

Nothing in the firmware was changed. COM16's flash was checked against the released uf2 with fwsum.py.

D1 · a defect, not a design question

After any SUB return or FUNCTION call, the compiled chain stays broken until a string temporary is freed.

  • RBReturn (Stream.c:4634) and RBCallFun (Stream.c:4240) set g_TempMemoryIsChanged, as the text path's return does.
  • ClearTempMemory (Memory.c:1967) clears the flag only inside its loop, that is, only when it frees a block.
  • With nothing allocated, the flag stays set, and the chain's test (Stream.c:5404) sends every following statement back through RunStream and RBTail.

A 50-statement loop costs 252 cycles a statement; right after an empty SUB call, 391 to 411; after the call followed by s$ = Str$(1), 255 again. In the chess engine, which uses no strings, this holds for nearly the whole search. RunStream, RBTail, RBFind and ClearTempMemory together take 21.3% of the bench (Exile 11.4%, Elite 6.1%), most of it this round trip.

Fix: clear the flag when ClearTempMemory finishes, whether or not it freed anything. Every later allocation and every return sets the flag again, so nothing that needs the check can miss it. The text path calls the same function, and loses only an unneeded call per statement.

Expected: 15-20% off the chess bench, less on programs that use strings between calls.

Applied and measured (R1, 5 October). The flag is now cleared at the end of ClearTempMemory (core/Memory.c). It was built for HDMIWEB with no change in RAM (bss_end the same) and flashed on COM16, at 315 MHz:

  • the loop after an empty SUB call: 270 cycles a statement (391-411 before);
  • the chess bench to depth 3: 49.84 s (58.91 s before), -15.4%, with the same nodes, scores and PVs;
  • Exile's physics test: 14.60 s (15.69 s), -6.9%;
  • Elite's demo: 6.67 s (6.95 s), -4.0%;
  • solar_eclipse, on two identically configured PC3s (b5 on COM9, D1 on COM16): 6.566 s against 6.903 s in MODE 1 (-4.9%), 6.028 s against 6.369 s in MODE 2 (-5.4%).

Each ran the same number of statements as before. rbp4d, rbp5c, rbp3d, rbp3b and rbcache pass (OFF, ON and SHADOW identical). A leak check (40,000 rounds of string FUNCTIONs, a SUB with a LOCAL string and string temporaries) leaves the heap exactly as it was after its first round, as text and compiled.

A timing trap found on the way: the display mode moves solar_eclipse by about 8% through console scrolling (MODE 2 is faster). A b5 run left in MODE 2 by an earlier program first made D1 look 4.5% slower. Every timing now sets the mode and clears the screen first.

  • A miss costs about 0.25-0.3 µs (80 cycles at 315 MHz, 100-118 at 378), from PSRAM and from flash alike. So a stream in flash would not be faster.
  • Flash streams lose the bind cache (a flash record cannot be written), which adds 115 cycles to the plainest statement.
  • A record that misses costs about 6.5 misses, one per 8-byte cache line of a roughly 48-byte record.
  • The chess bench makes 2.33 misses a statement, about 190 cycles: about 20% of its time. Its calls account for about 370 of its 5,200 misses a node. Most of the rest come from fetching the 86 KB stream.
  • A FUNCTION call runs about 1,300 XIP accesses' worth of flash code (findvar and the type checks). Moving that code to RAM is not an option, as RAM is stack.

What changes in the plan

  • D1 comes first: one line, the largest single gain, and it makes every later measurement truer.
  • V4 (boundary) next (Peter, 5 October): every program gains on every statement, it is the lower risk, its share grows once D1 keeps the chain whole, it should give RBRun RAM back, and V1 and V7 build on its successor field and attention word.
  • V2 (calls and locals) after it. It is the largest part in call-heavy programs, and it includes taking the type checks out of the run.
  • V1 (layout) follows V4. Both shrink what a record costs, and storing the successor in the record (V4) is also part of making the hot part small (V1). R0 settles V1's question: the stream's working set is the main source of misses, so a smaller hot record is worth more than where the stream lives.
  • V3 (elements) matters for array-heavy programs like the chess bench (8.3%), and little elsewhere.
  • V5 (fused ops) drops to last among the VM changes: the ops are 7-13% and each fused op costs RAM.

Proposals

Each proposal says what it changes, why the measurements point at it, what it costs, what it might gain, and how it keeps the state identical. Gains are estimates from the unit costs above; R0 replaces them with measurements.

V1LAYOUT

Hot code that stays in the cache

largest uncertain gain  stream format; the executor's reads  ·  RAM: none for (a) and (b); heap for (c)

Why. The size table: the same statement costs up to four times as much once its loop's records outgrow the 16 KB XIP cache, and the chess stream is 86 KB. A x = x + 1 record is about 48 bytes: a six-word statement header (the STMT word, the text key, the CMD word, the token, the cmdline and nextstmt offsets), the code length, the bind count, the stamp, the bind descriptors, the bind cache and nine words of code. Of those, a compiled statement that binds from its cache reads the header, the stamp, the cache and the code; the descriptors, the token and the fallback offsets are read only when it binds or falls back.

Proposal.

  1. Split each record into a hot part and a cold part. The hot part holds the flags, the successor (see V4), the stamp, the bind cache and the code. The cold part, in a parallel array indexed by record number, holds the text key, the fallback's token and offsets, and the bind descriptors. For x = x + 1 that halves what a run reads.
  2. Keep the hot parts of a unit together and in the order they run, which the compiler already writes. A loop body is then a few cache lines rather than a few dozen.
  3. Consider an SRAM code cache, only if R0 shows that (a) and (b) leave PSRAM fetches significant. The hot parts of the most-run units would be copied into an arena taken from the SRAM heap at RUN, and the executor would run from there. This costs heap, not static RAM, so it does not take stack; how much heap is a decision.

Identical state. Nothing observable changes; only where the executor reads its own data. RB_VERSION moves, so every stream recompiles once.

Gain. Between nothing and most of the stream-fetch share, which may be the largest part of the remainder. 10-30% on the chess bench is a guess until R0. Every program whose hot code exceeds the cache gains: Exile's stream is 81 KB, Elite's 303 KB.

Risk. Low for correctness. It touches the compiler's writer and every executor read of a record, so it is a large mechanical change.

V2CALLS

Calls that do not look names up

needs a decision  RBCallSub, RBCallFun, RBMakeParams, LOCAL, binding  ·  flash a few KB; heap for templates

Why. A call costs 1,197 cycles before anything is passed, about 840 a parameter, and about 1,350 a LOCAL. Every statement of the called routine then binds its variables again, because the call made new locals at its level, at 190-375 cycles a statement. The bench makes about 30 calls a node to routines of a few statements each. Each parameter, the FUNCTION's result and each LOCAL is made by findvar with V_LOCAL: a name copied out of the definition, the symbol's paths, the checks for an existing local and a SUB of that name, a 64-byte entry filled, SymLocalMade. A FUNCTION's body also runs in a nested ExecuteProgram and RunStream, two C frames a level.

Proposal.

  1. A parameter template per unit, made at PrepareProgram from the layout P6's F1 already reads. Each parameter's and the result's name, type and kind are known. A call takes their entries at g_localtop in one go: the template copied, the level set, SymL pushed for each, and the value or pointer stored directly, with no findvar.
  2. LOCAL made the same way. The entry is the next one up and its template is known, but it is made only when the LOCAL statement runs, as now.
  3. Locals bound through the frame, not by name. Parameters and the result sit at fixed places from the frame's base. A LOCAL is made only when its statement runs, so its place can vary (a LOCAL inside an IF); each call therefore keeps a small map, one word for each name in the unit's list, filled as its LOCALs are made. A compiled statement names a local as "entry k of this frame" and reads it through the base or the map, so only its globals go through the bind stamp, and a call no longer makes the callee's statements bind again. P6 planned binding by offset as F4's first option and chose option 2 because the frame was not reserved at entry; this keeps that reason intact (see Identical state).
  4. FUNCTION bodies run inside RBRun, as SUB bodies already do, with a small return record (the caller's record, pc, stack depth and bind slots) instead of a nested ExecuteProgram. This also gives the C stack back at every FUNCTION level, which matters for recursion; rbdepth measures it.

Identical state. The frame stays a run of g_vartbl entries, so the 298 places that read g_vartbl[g_VarIndex] see what they see now. Parameters are made in the same order with the same type rules, BYREF demotion and errors (an error while making them still unwinds through DefinedSubFun's recovery). LOCALs are not reserved at entry, so "Not enough Local variable memory" comes at exactly the point it does now; that was the reason the reserved frame was not made in P6. A FUNCTION run inside RBRun must save and restore what DefinedSubFun saves around its nested loop (nextstmt, cmdline, cmdtoken, CurrentLinePtr, ErrNext), and an interrupt, an error or END inside the body must find the stacks as the text path leaves them.

Gain. Calls perhaps from 1,200-10,000 cycles to 400-1,500, and the re-binding gone. 10-20% on the chess bench; more on programs built from many small SUBs (the anchor, Exile, Elite).

Risk. Medium. Calls have many paths, and interrupts and errors arrive at awkward moments. rbp3a, rbp3b, rbp3d, rbf2, rbcache and the interrupt tests cover them.

V3ARRAYS

Array elements addressed inline

low risk  RC_IDX, RC_LDEL, RC_ADEL, RBElementAt  ·  flash small; RAM about one op's worth

Why. A 2-D element costs 264 cycles over a scalar and a 3-D one 352, against 88 for a 1-D one. Anything but a 1-D element in bounds calls RBElementAt in flash. That function counts the array's dimensions again, checks each index against DimUpper and g_OptionBase, and multiplies its way to the element, on every access. Each index has already been through RC_IDX, its own op.

Proposal.

  • Check the number of dimensions once, at bind time. A mismatch fails the bind, so the statement goes to its fallback and raises "Array dimensions" exactly as now.
  • Add LDEL2 and LDEL3 (and their address forms) that convert, check and combine two or three indices inline.
  • Fold RC_IDX into the element op when the index is an integer, which is nearly always the case.

Identical state. The same checks in the same order, so the same errors: "Index out of bounds" after the conversion, "Dimensions" below OPTION BASE.

Gain. A 2-D element perhaps from 264 to about 110, a 3-D one from 352 to about 140. 5-15% on the chess bench, which indexes 2-D arrays on most lines of its evaluation and move generation.

Risk. Low. rbp4a and rbp5c already cover the element forms and errors.

V4BOUNDARY

A cheaper record boundary

every program gains  RBRun's entry and its done: path  ·  RAM: should shrink RBRun

Why. About 175 cycles of every statement are spent getting into and out of its record. x = j costs 209 with two ops, and line bookkeeping is only 6 of that.

At each boundary RBRun:

  • decodes the header (RB_HDR);
  • finds the successor by walking past the code and any IF parts;
  • computes the bind generation from three globals and compares it with the stamp, and aligns the cache pointer;
  • counts RBRan and RBCode;
  • tests the successor's kind, OptionErrorSkip, g_TempMemoryIsChanged, TraceOn and the housekeeping countdown;
  • rebuilds the text pointer from the key (RBImage(RBKeyAt(r))).

Proposal.

  1. Store the successor and whether it can be chained in the record when compiling, so the walk goes.
  2. One attention word that everything which can stop the chain sets: OptionErrorSkip, temporary memory, TRACE, an abort, an interrupt. The chain then tests one word.
  3. Check the bind stamp only where it can have moved: at a unit's entry, after a call and after a fallback. The compiler knows where those are, and records between them share the stamp already checked.
  4. Count statements per chain, not per statement. Add the chain's length when it ends.
  5. Keep the text pointer in a register and materialise nextstmt where the tail, a fallback or the chain's end needs it. The design's own table lists those as its only readers (interrupts, Ctrl-C, fallback control flow).

Identical state. CurrentLinePtr and TraceBuff stay eager, since they cost 6 cycles and the PC sampler and errors read them. nextstmt is set wherever it can be read. Proposal 5 needs a short survey to confirm that nothing else reads nextstmt mid-chain.

Gain. Perhaps 175 down to 70-90 cycles a statement. About 10% on the chess bench and on any compiled loop.

Risk. Low to medium. The chain conditions were found one by one in P3c and P3e, and each must survive. rbp2c, rbnopchain, rbstamp and the interrupt tests cover them.

V5OPS

Fused ops

costs RAM  the compiler's emit; new labels in RBRun  ·  RAM: each op is RBRun code

Why. An op costs about 17 cycles: a dispatch and an 8-byte cell moved to or from the stack. Statements are short sequences of the same few shapes. x = x + 1 is LDG, LK, ADDI, STG; an IF on a comparison is two loads, CMPI and JFI.

Proposal. A peephole pass picks the commonest pairs and triples from a count over the corpus's streams: add a small constant in place, compare-and-branch with a variable or literal operand, an element load whose index is a variable, and the store that copies one variable to another. Each fused op runs the same helpers in the same order as the ops it replaces.

Gain. 20-40% of the op share. About 5% on the chess bench.

Risk. Low for correctness. The cost is RAM: RBRun is RAM, which is stack, in 256-byte steps. Each op is perhaps 30-60 bytes, so this is weighed against recursion depth op by op.

V6LOOPS

A cheaper NEXT

low risk  RC_NEXT; FOR's push  ·  RAM: neutral

Why. An empty FOR iteration costs 281 cycles. NEXT is a record of its own, so it pays a boundary. It then searches g_forstack from the top, calling skipspace on each entry's text, before it adds the step and tests the limit in integer or float. The chess program's board scans are 64-iteration loops, several of them every node.

Proposal.

  • Look at the top entry first, comparing it with a pointer the compiled FOR stored already normalised. Fall back to the search only when the top entry is not this loop's.
  • Give integer loops with a literal step their own path.
  • Fold NEXT into the body's last compiled record, once V7 exists.

Identical state. The same g_forstack entry and the same closing rule, including NEXT-in-recursion's level test (5b90865). EXIT FOR, CONTINUE FOR, a fallback NEXT and ClearVars see what they see now.

Gain. Perhaps 281 down to about 120 an iteration. A few percent on the chess bench, more on tight-loop programs.

V7BLOCKS

Straight runs of statements as one block

structural  records, the map, binding, the chain  ·  after V1-V6 are measured

Why. After V4 each statement still pays a boundary. The CSUB's 19 cycles a statement show what is spent once statements have no boundaries at all.

Proposal. A run of compiled statements with no fallback and no call (a basic block, typically a loop body) is compiled as one record:

  • one bind set (the union of the run's variables) and one stamp check;
  • between its statements, a one-word BOUNDARY op that updates CurrentLinePtr at a line start, counts down the housekeeping counter and tests the attention word (V4 proposal 2);
  • when attention is set, the executor materialises the interpreter's state for that statement from a small side table, and leaves the block at that boundary. So an interrupt, Ctrl-C, TRACE or ON ERROR SKIP still meets the state the text loop would leave.

Each statement keeps its map entry, which then points at its block and offset, so a GOTO, NEXT or RETURN into the middle of a block still lands correctly.

Identical state. Kept at every point anything can look at it, by materialising at the boundary where the executor stops. That is what the design already does at its chain's end, applied inside a record.

Gain. The boundary drops to tens of cycles for straight-line code. With V3 and V5, the largest single step available inside the VM.

Risk. High. It changes the record model that P1 to P6 were built on, and SHADOW, the map, binding and the stream dump tools all follow it. It belongs after V1 to V6 have shown what is left.

V8NATIVE

Native code, for scale only

a different project

The CSUB sets the ceiling: 19 cycles a statement against about 890 now, and perhaps 300-450 after V1-V7. Closing the rest means generating Thumb-2 for the M33 from the stream: copy machine-code templates per op, keep the value stack in registers where a block allows, and call the firmware's helpers for anything not trivial. That needs an SRAM arena to execute from (PSRAM through XIP is slow for code), templates in flash, and the same materialise-on-attention scheme as V7 for errors and interrupts. It is named here so the VM work can be judged against it. It is not proposed.

What stays fixed

  • The text is the program and the stream a cache of it. A missing, stale or refused stream still runs as text.
  • State identical wherever it can be read. The Route B design's "Staying identical" table is the specification. Proposals V4 and V7 move some writes to the points where the state is read, and each needs that table re-checked against the code, not assumed.
  • RAM is stack. RBRun runs from RAM, and every byte of RAM code lowers the stack's floor for every program, text or compiled, in 256-byte steps (AllMemory's alignment). V4 should shrink RBRun; V5 grows it; V2 moves FUNCTION calls into it but takes C frames off every level. Each step is measured with rbdepth.
  • Flash. HDMIWEB had about 200 bytes left in its step at V7.0.00b5's offsets. Route B work may take further 16 KB FLASH_TARGET_OFFSET steps (agreed), each of which wipes A: on upgrade, so they should be batched into releases.
  • RP2350 only. Nothing here applies to the RP2040, where the CSUB route is the answer.

Order and gates

R0MEASURE

Measure first done

  • A PC-sampled profile, at C-function level, of the chess bench, Exile and Elite, on a build whose ELF is kept with it.
  • The chess bench with the stream in the hidden flash area (OPTION PSRAM PIN DISABLE, then back to GP47), to separate PSRAM from cache size.
  • A count of ops and elements per executed statement, from a stream dump and the RAN counts.

Gate: the "Where the cycles go" table holds measured shares, and V1's size is decided from them.

R1DEFECT

D1: the temporary-memory flag done

One line in ClearTempMemory. The test is the after-a-call loop (252 against 391-411 cycles now) and the chess bench, with the goldens for the text path, which shares the function.

R2BOUNDARY

V4, then V1

The successor in the record, one attention word, the stamp only where it can move, and the hot part of each record made small. The tests are the size table, which should flatten towards the 50-statement figure, the XIP misses a statement in the chess bench (2.33 now), and every program's profile.

R3CALLS

V2

After the decision on parameter templates. It starts with the type checks the compiler can settle (FindStructType, checkstring, CheckIfTypeSpecified at run time). The call tables are the test, with rbdepth for the stack and Exile, whose time is mostly calls.

R4ARRAYS

V3

For array-heavy programs; the element timings are the test.

R5OPS

V6, then V5

V6 first (NEXT costs a boundary every iteration); V5 only by an op-pair census, each fused op weighed against its RAM.

R6BLOCKS

V7

Only if R1-R5 leave the boundary as the largest remaining part.

Every step's gate
  • Goldens and SHADOW clean.
  • The rb* tests, the interrupt tests, symchain and cmtloop unchanged.
  • The three games pass their checks.
  • The chess bench gives 130, 3,441, 8,911, 141,331 and 550,727 nodes with the same scores and PVs, and its time is recorded.
  • rbdepth not lower than before.
  • Every variant builds within its flash and RAM.

Decisions

For Peter
  1. D1: may ClearTempMemory clear the flag when it finishes, on both paths? (R0 needed no flashing: COM16's released image matched a rebuilt ELF.)
  2. V2: parameter and result templates per unit, with locals bound by their place in the frame (LOCALs still made only when they run, so the local-memory error comes where it does now). And should FUNCTION bodies run inside RBRun?
  3. V1(c): if R0 shows it is needed, how much SRAM heap may an arena for hot code take at RUN?
  4. V5: how many 256-byte steps of RAM may RBRun grow by for fused ops, given that each costs recursion depth?
  5. V7: is a block model that materialises state at the boundary where it stops acceptable in principle, so that R1-R4 can be shaped towards it?

Method

  • Board: COM9, a PicoComputer 3 (PicoMiteHDMIWEB RP2350B), V7.0.00b4, 378 MHz, OPTION COMPILE ON. Its test arrays were at 0x2004xxxx, in SRAM.
  • Chess bench: Bas/chess/chessiter.bas (with search renamed, so it runs beside the CSUB library) to depth 3, and the CSUB version (chesscsub.bas and chesslib.bas) to depth 5. MM.INFO(COMPILE) was read after the depth-3 run. The node counts per routine come from a Python transliteration of the program that reproduces the bench's five iterations exactly.
  • Construct costs: three programs in the session's scratch directory.
    • rbcost.bas: the first table.
    • rbcost2.bas: calls, elements, the boundary and the in-SUB size test, generated by mkcost2.py.
    • rbcost3.bas: the main-level size test.
    Each times 20,000 to 50,000 runs with TIMER and subtracts the empty loop's 281 cycles. Repeats agreed within 1-2%. All three report CODE within 0.01% of RAN, so every statement timed ran compiled. They can go into Bas/bench with the R0 work.
  • R0: the ELF was rebuilt at 696d52c in a worktree at C:/Dropbox/PicoMite/PicoMite (a path of the same length as the real tree, so the image matches the release within 8 bytes); COM16 checked with fwsum.py; profiles by Bas/bench/rbprof.py and pcs_report.py, with two scratch helpers that split one function's samples by source line; XIP counters read with PEEK(WORD &H400C800C) and &H400C8010; the games from the census's profiling copies (A:/gb/gbxphysp.bas, gbelitep.bas); PSRAM off and on again on COM9 with OPTION PSRAM PIN DISABLE and GP47.
  • Estimates are marked as such. The shares in "Where the cycles go" multiply measured unit costs by counted events; the remainder is what is left over.
