## Changed since RC0

RC1 is RC0 with the fixes below. **Coming from RC0 your board keeps its
settings**, unless you run `PicoMiteRP2040`, whose flash region has moved - see
*Memory and flash layout*. Coming from b12 or anything earlier, the reset
described above applies exactly as it did for RC0.

- **`DIM` of a user-defined `TYPE` could fail with `Not enough memory for 0
  bytes`**, reported against a line that was perfectly correct, and adding an
  unrelated statement elsewhere in the program made it come and go. The
  `IF`/`END IF` jump table and the table of `TYPE` definitions both live in the
  BASIC heap, and clearing that heap did not tell either of them, so the jump
  table went on to release memory that by then held a `TYPE` definition and was
  rebuilt over the top of it. Found from a report by G@bor. It is not new to
  this release - it needed a particular arrangement of memory to show itself.
- **The first flash write after a power-on now waits a second for the supply to
  settle.** The boot counter is written to `A:` early in start-up, and on a
  board whose 3.3 V rail sits close to the flash chip's minimum that write
  could reach the wrong sector, leaving a board that booted once more and then
  not at all. Only a cold start waits; a reset button or `CPU RESTART` does
  not.
- **`MM.VER` tells release candidates apart.** RC1 reads `6.040051` and RC0
  reads `6.040050`. Every `RCn` used to read a bare `6.04`, so a board you had
  just reflashed looked identical to one you had not.
- **`PLAY BBC SOUND` queues 16 notes per channel** instead of 8, and
  `MM.INFO(BBC BUFFER [channel])` reports how many more notes a channel will
  take without waiting. With no channel it answers for the emptiest of the
  four, which is the figure that is safe whichever channel comes next.
- **Out of memory now names the size**, as in `Not enough memory for 16000008
  bytes`. The three earlier messages - `Not enough PSRAM memory`, `Not enough
  Heap memory` and `Not enough System Heap memory` - have become this one.
- `LIBRARY LOAD` says a source file **is empty** rather than reporting it as
  missing.
- A drive format requested during start-up is no longer **repeated** by an
  unrelated `OPTION PLATFORM` change afterwards.
- On the WiFi builds, a full connection table no longer writes past the end of
  the connection arrays.
- Writes to the `A:` drive are bounded at run time, so a bad block number can
  no longer become an erase at a computed address.

## Arrays

**A dimension can hold exactly one element.** `DIM a(0)` under `OPTION BASE 0`
and `DIM a(1)` under `OPTION BASE 1` used to raise `Dimensions`, which made a
row vector, a column vector or a 1x1 result impossible to declare:

```basic
Option base 0
Dim rowv(2,0), colv(0,2), dot(0,0)
Math M_MULT rowv(), colv(), dot()    ' a dot product
```

It works everywhere an array does: every type, any dimension of a
multi-dimensional array, `LOCAL`, `STATIC`, arrays passed as `arr()`, `REDIM`,
structure member arrays, `VAR SAVE`/`VAR RESTORE` and the `MATH` functions.
One consequence: `BOUND()` now raises an error for a dimension the array does
not have, or on a variable that is not an array, where it used to return 0. A
program that tested rank with `If Bound(a(), 2) = 0` needs changing.

**Whole-array assignment.** `b%() = a%()` copies one array into another in a
single memory move. Same type (and `LENGTH` for strings, structure type for
structures), same total number of elements; the shapes may differ.

**Functions can return arrays.** `Function f(n%) As Integer(5)` (integer and
float only) sets its result by assigning to elements of its own name and is
consumed by a whole-array assignment, `m%() = f(3)`. It cannot appear anywhere
else in an expression, and reading an element of the function's name inside
the function is a recursive call, so build the result in a `LOCAL` array if
intermediate values must be read back.

## Libraries

**`LIBRARY LOAD file$ [, O] [, RAM]` lets a program install its own library.**
It must be the program's first statement, it asks before replacing a library
that is already there unless `O` is given, and it is idempotent: a hash of the
source is kept, so a run that finds the same library already in flash touches
nothing. Up to eight files can be named and are joined in order into one
library, so a library can be kept as separate sources and assembled on the
board:

```basic
LIBRARY LOAD "graphics.bas", "sound.bas", "maths.bas"
```

Nothing is written until every file has been read. Not on `PicoMiteRP2040MIN`.

**A library in RAM, alongside the one in flash** (RP2350 with PSRAM). With the
`RAM` keyword the library goes into RAM slot 5 and takes the place of the flash
library, which is left exactly as it was, until `END` or the next `RUN`. A
program can bring a large library of its own without disturbing the routines
you keep in flash. Without PSRAM the keyword is ignored.

**A CSUB costs the library its binary only.** `LIBRARY LOAD` no longer stores
the hex text of a CSUB, which had cost about 3.4 times the code.

**`READ` falls through to `DATA` in the library** when the program's `DATA`
runs out or it has none, and a library routine can read its own `DATA`.

**`FLASH ERASE` works from inside a running program**, so a program can
manage its own slots.

**A corrupt library can no longer lock a board out.** The boot-time walks of
the library are bounded to the slot and the image is checked before anything
reads it; one that fails is erased with the message `Library was corrupt and
has been discarded`. Previously a damaged image hung the interpreter before
the prompt, and reflashing did not help because a .uf2 leaves the library
where it is.

## Image slots in PSRAM (RP2350)

On an RP2350 with PSRAM, **image slots 4 to 8 are the RAM slots 1 to 5**, and
`FLASH LOAD IMAGE`, `BLIT FLASH`, `TILEMAP` and `MM.INFO(FLASH ADDRESS)` take
them by number:

```basic
FLASH LOAD IMAGE 4, "tiles.bmp", O        ' RAM slot 1, every start
TILEMAP CREATE mapdata, 1, 4, 16, 16, 16, 20, 15
BLIT FLASH 4, F, 0, 0, 100, 40, 32, 32, 0
```

A RAM image loads in milliseconds, costs no flash wear and leaves the three
flash slots free. `RAM LIST` and `FLASH LIST` report `image w x h` for a slot
holding an image, `RAM SAVE` refuses one, and both loaders reject a bad or
oversize file before anything is erased. Odd-width images, which were stored
one byte short per row and drew skewed, are now packed the way `BLIT FLASH`
reads them.

## Sprites over a background on VGA and HDMI

**`FRAMEBUFFER MERGE [colour] [, B]`** composites framebuffer 2 over the main
framebuffer into the display in one pass, without the tearing that drawing
into the live layer produces:

```basic
FRAMEBUFFER CREATE          ' the background, F
FRAMEBUFFER CREATE 2        ' the moving things, 2
FRAMEBUFFER MERGE 0, B      ' 2 over F into the display, at vertical blank
```

A full mode 3 merge takes about 11 ms, one frame at 75 Hz. `FRAMEBUFFER CREATE
2` shares the video memory the layer would otherwise use, and `BLIT FLASH`,
`BLIT FRAMEBUFFER` and `TILEMAP DRAW` accept buffer 2. RP2350 only, as `CREATE
2` is. The background merge on LCD panels no longer overflows core 1's stack on
wide displays.

## A BASIC routine compiled to a CSUB, without writing C

**mmb2csub** (in the attached zip) takes one SUB or FUNCTION out of your
program, compiles it to machine code and puts it back as a CSUB. Your call
sites do not change. Loops, arithmetic and array work run 10 to 35 times
faster; the Julia set demo renders in 5.9 s instead of 119 s on an RP2040. The
generated code calls the firmware's own routines through the CallTable, so
`SIN`, `MID$` or `RGB` inside a CSUB mean exactly what they mean in BASIC, and
one converted program, the same bytes, runs on the RP2040 and the RP2350 and
on every variant. `--list` reports what every routine in a program would gain
before anything is written; anything unsupported is refused by name.

With it the CSUB interface has grown: 64-bit arithmetic, `memcpy`/`memset`/
`memmove` and the string routines are in the CallTable, `PIN(n)` and
`PIN(n) = v` work from a CSUB (20,000 write-then-read passes in 83 ms rather
than 654 ms), a CSUB may take sixteen arguments on the RP2350, and the same
CSUB now runs on both chips, unless it reads the variable table or `Option`,
whose layouts differ. `docs/armcfgen.md` and the mmb2csub manual cover
it; `PicoCFunctions.h` no longer declares the wrong variable-table layout for
the RP2040.

## PicoCFunctions.h: the CSUB header has been updated

Anyone compiling a CSUB in C or assembler should take the `PicoCFunctions.h`
from this release (it is in the repository and inside the mmb2csub zip) and
rebuild. It is now at v2.3.0 and differs from the 6.03.00 header in these
ways:

- **The variable-table layout for the RP2040 was wrong.** A CSUB built from
  the old header against an RP2040 build read every variable's value from the
  wrong offset. `MAXDIM` is now 5 on the RP2350 and 6 on the RP2040, the
  `rp2350` define is set so the option struct's padding resolves, and the
  struct matches the firmware's 896-byte `Option`, including the new
  `LIBRARY_HASH` field.
- **New CallTable vectors, all appended so existing CSUBs keep working:**
  64-bit integer helpers `LMul`, `LDiv`, `LMod`, `LShl`, `LAsr`, `LLsr`
  (0x140-0x154); `memcpy`, `memset`, `memmove` (0x158-0x160); the MMBasic
  string routines `MtoC`, `CtoM`, `Mstrcpy`, `Mstrcat`, `Mstrcmp`
  (0x164-0x174) and `StrRight`, `StrCase`, `StrMid`, `StrChar`, `StrFill`
  (0x178-0x18C); `INSTR`, `STR$`, `TIMER`, `RND`, `log`, `tan`, `VAL` and
  `TIMER = n` (0x190-0x1AC); the current `COLOUR` foreground and background
  (0x1B0-0x1B4); and `PinVal` and `PinPut`, which read and drive a pin as
  `PIN(n)` and `PIN(n) = v` do (0x1B8-0x1BC).
- **A CSUB may take sixteen arguments on the RP2350**, ten on the RP2040 as
  before.

The CallTable is found at run time through the VTOR register, so one compiled
CSUB runs on the RP2040 and the RP2350 and on every variant; a CSUB built with
the new header needs this release or later. The exception is a CSUB that reads
the variable table (its `dims[]` are five `int`s on the RP2350 and six `short`s
on the RP2040) or the `Option` structure (laid out per variant): that must
still be built for the chip, or variant, it runs on. `docs/armcfgen.md` lists every
vector with its signature.

## USB host

The USB host stack is now **TinyUSB 0.21** with PicoMite's patches on top.

- **Reads from a USB flash drive (C:) run at several hundred KB/s** instead of
  about 64 KB/s, faster than the SD card on the same board, so `PLAY MP3
  "C:/track.mp3"` streams without underruns.
- **Several devices behind a hub enumerate reliably** on every kind of reset.
  The connect chime plays once, after enumeration, instead of from inside it.
- **Plugging in one device no longer silently kills another**: a recycled
  endpoint slot could capture a live endpoint's completions.
- **RP2040 keyboards no longer fault on plug-in**: control transfers are
  double-buffered again on RP2040, where single buffering walked into erratum
  E4. RP2350 keeps its single-buffered fix.
- **Recoverable USB conditions recover and report** (`[USB DATA_SEQ 3 @181]`)
  instead of taking the interpreter down with a bare `*** FAULT`. The counts
  are readable with `PEEK`.
- **`UPDATE FIRMWARE` is in every build**, so the USB host variants can reach
  the bootloader without the BOOTSEL button.
- **GPS on a USB serial port**: `OPEN "COM3:" AS GPS` through `COM6:` now
  starts the parser, as the UARTs always did.
- **Mouse reports are decoded from the mouse's own HID descriptor** when
  `OPTION MOUSE SENSITIVITY` is set, so mice with extra buttons, padding,
  report IDs or wide movement fields work.

## Sound

**`PLAY BBC SOUND channel, amplitude, pitch, duration`** and **`PLAY BBC
ENVELOPE`** are the BBC Micro's `SOUND` and `ENVELOPE` statements with the same
parameters, units and behaviour, on every variant including the RP2040: three
square-wave channels and a noise channel, eight-deep queues per channel, sync
marks for chords, `&H10` to flush, sixteen envelopes with three-section pitch
envelopes and ADSR amplitude at the authentic 100 Hz, and all eight of the
BBC's noises including the two clocked by channel 1's pitch.

```basic
FOR p = 53 TO 101 STEP 4 : PLAY BBC SOUND 1, -15, p, 5 : NEXT p
```

Also: the VS1053 `PLAY SOUND` right-channel sawtooth and silent-channel DC
offset are fixed, and the computed square and sawtooth waveforms are
band-limited. `PLAY SOUND` type N takes a dwell rather than a pitch.

## Cameras (RP2350)

**OV5640 support**: `CAMERA OPEN OV5640` with QVGA RGB565 preview, motion
detection (`CAMERA CHANGE`) and JPEG capture at VGA to 5MP in three qualities.
White balance is frozen at the preview's converged setting for stills, and the
pixel clock follows the CPU speed. `CAMERA OPEN` no longer needs a display for
JPEG capture and motion detection; a misconfigured or disconnected camera
reports which signal stalled instead of freezing; capture no longer disturbs
the PSRAM/flash controller; the capture inner loops are faster.

## New commands and functions

- **`LOAD file$ [, C] [, R]`** crunches a program as it loads, as `AUTOSAVE C`
  and `XMODEM C` already could, so a program too big for memory can come off a
  disk rather than being pasted up the console. The suffix letters are now
  matched in full, so `LOAD "p.bas", RUN` is a syntax error rather than `,R`.
- **`TILEMAP LOAD file$, id, slot, tileW, tileH, tilesPerRow`** reads a tile map
  from a text file (`.map` by default) so a large map need not live in `DATA`.
- **`MATH CLAMP in(), lo, hi, out()`** limits every element to a range, integer
  or float, strided; 16 elements in 14 us.
- **`BASE$(base, number [, chars])`** for bases 2 to 36.
- **`MM.ERRLINE`** is the line of the last error, beside `MM.ERRNO` and
  `MM.ERRMSG$`.
- **`MM.INFO(TELNET)`** (WiFi builds) is 1 while a Telnet client is attached.
- **`MM.INFO$(BOOT)`** reports a brown-out reset distinctly on the RP2350.
- **`WEB PING address$ [, count] [, timeout_ms] [, avgvar]`** (WiFi builds).
- **`TURTLE`** colour commands accept `COLOR` as well as `COLOUR`.
- **`KEYDOWN()` works on the PicoCalc's built-in keyboard**, and Ctrl+C typed
  quickly on a PicoCalc no longer produces a literal `c`.
- **SHIFT with the left and up arrows** now has key codes of its own, `LEFTSEL`
  (&HA2) and `UPSEL` (&HA4), beside the existing down and right codes.
- **`MAX3D` is 32**, up from 8, so a scene can hold 32 `DRAW3D` objects.
- **PicoComputer 3 configures itself at boot** on the RP2350 builds.

The `HELP` command reads a file called `help.txt` on the A: drive. Three are

|---|---|---|
| `help.txt` | 573 KB | the full entry: syntax, description, everything |
| `helpmin.txt` | 250 KB | syntax and a one-line summary |


## Boot robustness

- The library check above.
- **The PSRAM bring-up can no longer hang the boot.** Its two QMI handshake
  waits had no timeout and run inside the boot watchdog window, so a PSRAM
  that did not answer rebooted the board into the same wait: a silent boot
  loop that also rewrote the option sector every cycle. The waits are now
  bounded; a chip that does not answer is reported as `PSRAM not responding`
  once the console is up and the option is kept for the next boot.
- **A magic key mismatch is a full clean**, A: drive included (see the box at
  the top). A firmware version change of the same variant resets nothing.
- **RP2040 boot loop fixed**: littlefs's lookahead buffer lost its alignment
  when `FileIO.c` was compiled for size and the boot-time mount of A: faulted.
- **`SAVE IMAGE` writes the colours the screen is showing**, including after
  `MAP SET`.

## Fixed

Two of these have been in the firmware for a long time and are worth calling
out. Both were found while chasing a Game*Mite report on PicoMiteRP2040MIN,
and both were proved on hardware before and after the fix:

- **SD-card access straight after a background framebuffer copy failed** on
  any board where the card shares the system SPI with the display, which is
  every Pico-ResTouch and Game*Mite. The only workaround was a `PAUSE` tuned
  to the CPU speed. Details under *Files and drives*.
- **Reading the screen after a framebuffer session rebooted the board** on an
  SPI panel that cannot be read back, such as the ILI9488W on the ResTouch
  3.5: `SAVE IMAGE`, `BLIT READ` or `PIXEL()` after `FRAMEBUFFER WRITE N`
  went through a null pointer. Details under *Graphics*.

Files and drives

- **A file operation straight after a background `FRAMEBUFFER COPY ,B`
  (or `MERGE ,B` / `BLIT ,B`) no longer fails with an I/O error** when the SD
  card shares the system SPI with the display. The copy runs on core 1 after
  the statement has returned, and the next `PLAY MODFILE`, `LOAD BMP` or file
  read used to drive the same bus at the same time; the only cure was a
  `PAUSE` tuned to the CPU speed. The SD driver now waits for the burst to
  finish before touching the card. The continuous background `MERGE` is
  unchanged: it restarts itself, and a program still has to keep file
  access away from it.
- Reading part of a file after `SEEK` on an SD card started up to 512 bytes
  late (`MEMORY INPUT`, `LONGSTRING LOAD`, structure `LOAD`); `LOC()` could be
  wrong after a seek; `EOF()` could say there was more after a seek to or past
  the end, on SD and on flash.
- The file manager froze or faulted copying directories from a USB drive: its
  5.8 KB stack frame overflowed core 0's 8 KB stack. `EDIT` from the file
  manager could then run out of heap; fixed as well.
- The HDMIUSB build crashed launching a program from the file manager.
- `OPTION DISK SAVE` dropped the platform name and the telnet console mode.
- `RAM FILE LOAD` left the running program without its subroutines, wrote 1 KB
  past the PSRAM allocation map, and `RAM ERASE ALL` cleared 128 KB beyond the
  end of the PSRAM and into the heap.

Graphics

- **`SAVE IMAGE`, `BLIT READ` or `PIXEL()` after a framebuffer session
  hard-faulted on an SPI panel that cannot be read back** (ILI9488W,
  ST7789, ILI9481, GC9A01, the ST7735s and others). `FRAMEBUFFER WRITE N`
  restored the panel's drawing routines but left the read routines bound to
  the framebuffer reader with no framebuffer selected, so the next read went
  through a null pointer and the board rebooted. They now report "not
  available on this display" as they do before any framebuffer is created.
  On these panels `SAVE IMAGE` reads the framebuffer while `FRAMEBUFFER
  WRITE F` or `L` is in force and is refused for `N`; on panels with read-back
  it reads the screen for `N`.
- `FRAMEBUFFER CLOSE L` and `CLOSE T` were transposed and a selective close
  discarded the other buffers; the mode 5 layer and the mode 2 and 5 top layers
  were never freed.
- `FRAMEBUFFER LAYER` drew behind the display on the HDMI builds in modes 2
  and 5 when no `LAYER TOP` existed.
- `DRAW3D()` never returned a value; `CLOSE ALL` left the last object; `LIGHT`,
  `SET FLAGS` and `RESET` faulted on a missing object.
- The mouse cursor could leave a block of corruption behind on GUI and
  on-screen keyboard redraws; OSK keys could not be clicked with a mouse under
  `OPTION GUI CONTROLS 0`; the GUI TEXTBOX pop-up keyboard could not produce
  lower case.
- `CIRCLE` with an aspect greater than 1 and a one-pixel line left gaps; font
  7's percent sign was mirrored; the brownian demo left sprite trails.
- The editor mis-placed a mouse click or tap on a horizontally scrolled line
  and did not refresh its status line after a terminal click.

Interpreter and maths

- `REDIM` recreated arrays as the default type, losing INTEGER and STRING data.
- `MATH CHI` indexed past its table above about 8x8 and had wrong degrees of
  freedom under `OPTION BASE 1`; `MATH M_INVERSE` leaked a row per call;
  `MATH CRC12` masking, the CRC `reverseOut` argument and `Q_CREATE` angle units
  were wrong; assorted argument checks in the MATH array helpers.
- `JSON$` could read 8 bytes past its source array under `OPTION BASE 1`.
- Regular expressions: `{n}` matched n or more times.
- `MM.VER` read past the end of the version string on a release build.
- The console emitted the autowrap escape before every input line; it is now
  sent once at reset and once when the editor exits.
- `PIO SYNC` wrote the wrong PIO's CTRL register and PIO DMA completion
  disabled the wrong state machine on PIO 2.
- dr_wav's 4 KB scratch buffers come from the heap, not the stack.
- The interpreter had become about 7% slower in b2 because newlib's `strlen`
  and `strchr` moved to flash; both are RAM-resident on every variant, and the
  reference benchmark is faster than before.

Network

- `WEB TCP CLIENT REQUEST/READ/STREAM` could write 8 bytes past the
  destination array; `WEB SCAN` and the receive commands reject an array too
  small for any payload; the CRLF terminating a transmitted HTTP body was in
  the wrong order.
- The GPS monitor could overflow the stack when printing to a display console.
- `MM.DEVICE$` said `WebMite` on PicoMiteHDMIWEB; `RAM FILE LOAD` wiped the sub
  table on that build.
- Bluetooth console and keyboard fixes.

## Memory and flash layout

- The MMBasic heap is smaller on the USB host builds to give the new USB
  host stack the C heap it needs: `PicoMiteRP2040USB` 124 KB,
  `PicoMiteRP2040VGAUSB` 96 KB, `PicoMiteRP2350USB` 296 KB and
  `PicoMiteRP2350VGAUSB` 160 KB. The maximum program size follows the heap
  on the RP2350 builds and on the VGA builds; the plain RP2040 builds keep
  their 120 KB program size.
- Several variants moved their flash region during the beta cycle. That no
  longer matters for upgrading: every board is reset by this release anyway.
- **`PicoMiteRP2040` moved again in RC1**, 912 KB to 928 KB. Flash moves only
  in 16 KB steps and the step comes out of the A: drive. That board therefore
  resets and reformats when it first boots RC1 even if you are coming from
  RC0; no other variant moved.

## For anyone building from source

- The firmware builds with **pico-sdk 2.3.0**. The USB host is **TinyUSB
  0.21.0** in a sibling `../tinyusb-0.21` tree with PicoMite's patches; run
  `tinyusb-patches/setup-tinyusb` once and it fetches the release and applies
  them. The README build instructions are written around this.
- `buildpicomite.bat` takes the version from `Version.h`, pins a Release build,
  stops on the first variant that fails its flash/RAM/heap/alignment fit
  checks, and runs those checks before copying the .uf2 into `uf2/`.
- `tools/release_preflight.py` gates a release: binaries present and named for
  the version, fresher than the last firmware commit (by commit time, never
  mtime), manual PDF byte-identical to the master, tree committed and pushed.
- `misc/FileIO.c` compiles at `-Os`. `strlen` and `strchr` are RAM-resident.
- `SaveProgramToFlash` takes the flash region to write; `ImageSlotAddress()` is
  the one place a slot number becomes an address; `LibPresent()` means "a
  library is active"; `PrepareProgramExt()` bounds its walks to
  `MAX_PROG_SIZE`; `LibraryImageValid()` is the boot check.
- `Option` gains `LIBRARY_HASH` in its last four bytes with the struct still
  exactly 896 bytes, asserted at compile time. `MAXIMAGESLOTS` is 3 on the
  RP2040 and 8 on the RP2350. `PSMAPWORDS` in Memory.h sizes the PSRAM map
  once; static asserts guard the RAM slot reserve and the context save.
- The CallTable has grown by appending; existing CSUBs are unaffected.
  `armcfgen` compiles with `-fno-jump-tables`.
- Board tests in `Testfiles/`: `ArrayCopyTest`, `ArrayCopyStructTest`,
