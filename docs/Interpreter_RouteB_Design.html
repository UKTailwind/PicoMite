Route B · design for review

A compiled statement stream

The G3 prototype showed that the interpreter's overhead is not in any one routine but in re-reading text. The same kernels run as typed wordcode were 8.8-22x faster than the interpreter with symbols, on both chips. This design turns that prototype into firmware without changing what a program means. The tokenised program stays the master copy. A compiler turns it into a stream of statement records, kept in a program slot. An executor runs the stream and leaves the interpreter's state exactly as the text interpreter would at every statement boundary. Anything not compiled runs through its existing command handler, so a program is always runnable, whatever the compiler has not learned yet.

Branch development at 8740953 · evidence: G3 (commit 3140045, Bas/bench/results/g3), the Phase 1 report, and four read-only code surveys for this design (statement loop and control flow; calls and variables; evaluator and built-ins; storage, lifecycle, interrupts and errors).

Summary

  • The text stays the program. LIST, EDIT, SAVE, the library, CSUBs, error lines and TRACE all work from the tokenised image as today. The stream is a cache derived from it. If the stream is missing, stale or refused, the program simply runs as text.
  • Compiled at RUN, only when the program has changed. Everything that runs a program passes through PrepareProgram(true). There, a CRC of the image is checked against the stamp in the stream slot, and the program is compiled only if the two differ. That covers every way a program arrives (LOAD, AUTOSAVE, EDIT, XMODEM, FLASH/RAM LOAD and RUN, CHAIN, LIBRARY LOAD) without touching any of the image writers.
  • One record per statement. Each record starts with a statement marker that does the interpreter's per-statement work. It is followed by either compiled code or a fallback that calls the statement's own command handler with exactly the cmdline, nextstmt and cmdtoken the text loop would give it.
  • Same variables, same stacks. Variables stay in g_vartbl and the heap and are reached through the S5/S6 bindings. FOR, DO, GOSUB and SUB frames use g_forstack, g_dostack, gosubstack and g_LocalIndex exactly as the text interpreter does. So interrupts, ON ERROR, CHAIN, SAVE CONTEXT and any fallback statement see nothing different.
  • Same arithmetic. Operators, conversions and number parsing are moved into shared helpers that the text evaluator and the executor both call. They cannot drift apart. A shadow mode evaluates each compiled expression both ways and stops on the first difference.
  • Five phases, each with a gate.
    • P1: fallback records only; the plumbing, at no loss of speed.
    • P2: numeric statements on globals.
    • P3: locals and calls.
    • P4: arrays, SELECT, GOTO/GOSUB and simple strings.
    • P5: the value splice for built-in functions and graphics commands.
  • Cost: 15-25 KB of flash in the end, grown phase by phase, and under 1 KB of static RAM. During development the stream lives in RAM slot 4 on the PC3 and flash slot 2 on the RP2040.

The prototype's figures are an upper bound for three reasons. This design pays for all three to keep state identical, so the firmware result will be lower. P2 and P3 each measure it.

The shape

Compiler

Runs inside PrepareProgram(true) when the image's CRC does not match the stream's stamp. It walks the tokenised image, the same bytes the text interpreter reads. It asks the interpreter's own code every structural question (which NEXT closes this FOR, where this IF's ELSE is, what this label resolves to) so the answers cannot differ. It writes the stream unit by unit, sequentially, straight into the slot.

Executor

A computed-goto loop, like the prototype's. ExecuteProgram hands over to it whenever the next statement lies in the program image and a live stream exists. The executor hands back when control leaves the image: library code, the prompt's tknbuf, EXECUTE, or the empty statement that ends a FUNCTION body.

Shared helpers

The code that must give identical answers is factored out of the text interpreter and called by both paths: operators, conversions, the number parser, element addressing and the block scans. The interpreter's behaviour does not change; its code is moved, not rewritten.

Fallback

Any statement the compiler does not handle becomes a fallback record, which calls commandtbl[token].fptr() or DefinedSubFun with exactly the globals the text loop would set up. P1 is nothing but fallback records. The compiled subset grows phase by phase behind the same interface.

The stream

A slot holds one stream: a header, a statement map, the code and a unit table.

PartContents
Header
  • Magic "RB01" and the format version.
  • A firmware build hash: opcode numbers and helper indices are private to a build, so a stream from another build is stale.
  • The stamp: the image's length and CRC32, and its SymTabProg count.
  • The offsets and sizes of the other parts.
Statement map
  • One entry per statement, sorted by text offset: text offset (24 bits) to record offset (24 bits), 6 bytes each.
  • Used only when control arrives from a text pointer: an interrupt, IRETURN, a fallback that changed nextstmt, or ON ERROR SKIP.
  • A 64-entry direct-mapped cache in RAM keeps a loop driven by a fallback NEXT from searching it every pass.
Code
  • 16-bit words: opcode in the low byte, a small operand in the high byte, extension words after it, as in the prototype.
  • Records appear in text order, one per statement. Jumps are relative, so the stream runs from any address.
  • Integer and float constants are inline, parsed at compile time by the interpreter's own number parser.
Unit table
  • For each SUB/FUNCTION (by subfun[] index): the entry record, and the compiled parameter list (see Calls).
  • For each label the program jumps to: its record.

The statement record

Every record begins with STMT. It carries the statement's text offset and a line-start flag, and does two jobs:

  1. The tail of the statement before it. This is what the text loop does after each statement (MMBasic.c:2114-2126):
    • the ON ERROR SKIP count;
    • ClearTempMemory if g_TempMemoryIsChanged;
    • the core 1 stack check;
    • CheckAbort and check_interrupt unless OPTION NOCHECK.
    Before any of these, nextstmt is set to this statement's text, which is exactly what the text loop has in nextstmt at that moment. So an interrupt's InterruptReturn and Ctrl-C's ContinuePoint come out the same.
  2. The head of this statement. At a line start it sets CurrentLinePtr to the line's T_NEWLINE, writes TraceBuff, and prints [n] under TRACE ON, as at MMBasic.c:2003-2031.

Entering the executor starts at the head, skipping the tail, just as the text loop has no tail before its first statement. The tail's cheap tests are inlined: IntReady.any, MMAbort, the routinechecks 100 µs cadence and the ProcessWeb cadence on WEB builds. The functions are called only when a test says so, as the prototype's marker did.

After STMT comes one of:

  • CMD (fallback): the command token, and the cmdline and nextstmt offsets precomputed by the same skipspace/skipelement the loop uses. It sets cmdtoken, cmdline, nextstmt, CmdTokenPtr and targ = T_CMD, expands symbols for commands not on SymAwareNames, and calls the handler.
  • SUBCALL (fallback): the text loop's user-SUB path, FindSubFun then DefinedSubFun(false, ...) (MMBasic.c:2082-2091).
  • NOP: a comment, or a line with nothing to run (a label or a line number alone). The text loop runs such a line's head and nothing else, not even a tail, and the record does the same. It is there so that a GOTO, LOOP or NEXT that lands on the line finds it in the map; without it, a loop whose body starts with a comment dropped to text on every pass.
  • Compiled code for the statement.

After a fallback, if the handler left nextstmt at the precomputed end of its element (the common case), execution continues with the next record. Otherwise the new nextstmt is looked up in the cache and the map. If it lies outside the image, the executor returns it to the text loop.

Compiling

When

  • PrepareProgram(true) runs for RUN, FLASH/RAM RUN and CHAIN, CHAIN, LIBRARY LOAD's restart, EDIT's save-and-run, and the boot autorun.
  • With OPTION COMPILE on, it computes the image's CRC32. That takes a few milliseconds for the largest images.
  • If the CRC matches the stamp, it only checks the header and maps the stream. Otherwise it compiles.
  • The prompt's PrepareProgram(false) never compiles.
  • Images saved without symbols (OPTION SYMBOLS OFF, or older images) are not compiled: operands name variables by symbol id.

How

  1. Survey pass. One walk over the image finds:
    • the units (the main program, and each SUB and FUNCTION);
    • each unit's parameter list;
    • every declaration's type (DIM, LOCAL, STATIC, CONST, AS types, OPTION DEFAULT in text order);
    • the statement count, which sizes the map;
    • anything that makes a unit unsafe to compile beyond fallback, such as a GOTO into the middle of a loop body from outside it.
  2. Per unit, two passes.
    • The first pass measures each statement's code and records its offset in a table for that unit.
    • The second emits, with every forward jump inside the unit already known.
    • Jumps between units go through the unit table.
    There is no whole-program parse tree and no global fix-up list. Compile RAM is the largest unit's offset table (4 bytes a statement), two 256-byte page buffers (code and map), the header page and the unit table.
  3. Output is written sequentially: code pages and map pages as they fill, and the header last.
    • On the PC3 the slot is PSRAM, written directly.
    • On the RP2040 it is flash: the slot's sectors are erased as the write reaches them, and pages are programmed with the existing safe_flash_range_* wrappers.
    • If the stream would exceed MAX_PROG_SIZE the compile is abandoned and the program runs as text. MM.INFO reports why.

Structural answers come from the interpreter

The compiler must match FOR to NEXT, DO to LOOP, IF to ELSEIF/ELSE/ENDIF and SELECT to CASE exactly as the handlers do at run time, including their odd cases. So those scans are factored out of the handlers and called by both:

  • the FOR scan with NextNamesVar (Commands.c:5026-5168);
  • the DO/LOOP scan (5470);
  • the SELECT/CASE scan (4603);
  • IfTableLookup, already built by PrepareProgram (Commands.c:3241-3541);
  • findlabel/findline for labels.

Where a structure is irregular (NEXT naming two variables, a GOTO into a loop, a CASE list containing strings), the statements involved are compiled as fallback. The text handler then does exactly what it does today.

Running

  • Hand-over. The top of the text loop gains one test: while a stream is live and p lies in the program or library image, it calls RunStream(p). At the top rather than after p = nextstmt, so it also catches a loop's first statement and the statement after a comment line, which the comment fast path reaches with continue. That covers:
    • RUN, which only sets nextstmt = ProgMemory inside the prompt's ExecuteProgram(tknbuf);
    • a library SUB returning into the program;
    • MM.END/MM.PROMPT calls;
    • a FUNCTION body's nested ExecuteProgram, from its first statement.
    The test costs nothing while the stream is off, and two compares per statement while library or prompt code runs.
  • Hand-back. RunStream returns the text pointer at which the text loop should continue. That happens when control leaves the image; the "\0\0\0" that cmd_endfun leaves in nextstmt ends the nested loop as it does now. END and errors leave by longjmp, as they do from any handler.
  • Return addresses. gosubstack keeps its text pointers, because fallback RETURN, error()'s unwind and CHAIN read them. A parallel array of record addresses, indexed by gosubindex, lets a compiled RETURN or END SUB go straight back without a map lookup. The executor uses that record address only if the gosubstack text pointer is the one it recorded, so a frame pushed by text code is never misread.
  • Nesting. A compiled FUNCTION call runs the body in a nested RunStream. It saves and restores ErrNext, nextstmt, cmdline, cmdtoken and CurrentLinePtr exactly as DefinedSubFun and getvalue do around their nested ExecuteProgram (MMBasic.c:2925-2934, 3545). The executor's C frame is kept small, because the core 0 stack is 8 KB and deep recursion already reaches it.

  • ON ERROR SKIP/IGNORE. While OptionErrorSkip is non-zero, the executor switches to a variant that arms setjmp(ErrNext) around each statement, as the text loop does (MMBasic.c:2099-2112). On a caught error it restores g_LocalIndex and temporary memory, then continues at the record after the failing statement's map entry. The executor's position is kept in a global, not a register, so the longjmp cannot lose it.
  • Interrupts are taken at the same boundaries with the same effects.
    • GotAnInterrupt redirects nextstmt to the handler's text; the executor maps it to the handler's record.
    • IRETURN (a fallback) sets nextstmt back to the interrupted statement, and the map finds it.
    • PAUSE and the touch waits call check_interrupt mid-command and re-run their statement through InterruptReturn = CmdTokenPtr. They are fallbacks, so this is unchanged.
  • Ctrl-C and CONTINUE: ContinuePoint = nextstmt at the mark landing is a text pointer, so CONTINUE re-enters through the map.
  • CHAIN, SAVE/LOAD CONTEXT and RAM FILE LOAD save and restore only interpreter state, never executor state. The executor keeps nothing across a statement boundary that cannot be rebuilt from that state and the map.

Variables and types

  • Operands are symbol ids.
    • At stream load, SymCanonOf is filled for every program id, so an operand reaches its canonical entry with one load.
    • A local is found by SymL[k] when g_vartbl[slot].level == g_LocalIndex.
    • A global is found by SymG[k] when !g_LocalIndex || !SymTextLocals. This is findvar's fast path (MMBasic.c:5203-5225), without the call and without the text.
    • Otherwise the operand takes the slow path: findvar on a short buffer holding the symbol bytes. It returns exactly findvar's result, including implicit creation and the OPTION EXPLICIT error.
  • Bound once per statement.
    • A compiled statement starts by binding each distinct variable it uses. Each binding checks the variable's type and T_PTR against what the code was compiled for.
    • If a check fails, the statement runs as a fallback instead, before anything has happened.
    • Variables used after a user FUNCTION call in the same statement are re-bound after the call. The callee can create globals, and in principle ERASE one.
    • T_PTR (BYREF parameters, STATIC, array parameters) is resolved during binding, so the operations themselves only ever see a data address.
  • Static types. The survey pass gives each name a type per unit, from:
    • its suffix;
    • its declarations (DIM/LOCAL/STATIC/CONST AS, FUNCTION AS);
    • the OPTION DEFAULT in force at that point in the text.
    A name whose type cannot be fixed (declared with two types, or used before a conditional OPTION DEFAULT) is dynamic. Statements that use it are fallbacks. The binding check makes a wrong guess cost a fallback, never a wrong answer.
  • Not compiled at first: struct and dotted names (FINDVAR_DOTBLOCKS), and STATIC declarations. Statements using them are fallbacks. STATIC variables themselves are ordinary T_PTR locals once made, so reading them is compiled.

Expressions

  • Same grammar. The compiler climbs precedence exactly as doexpr does (MMBasic.c:3293-3398), from the same tokentbl[].precedence values, left-associative at equal precedence. Unary - + NOT INV bind tighter than ^ (-2^2 is 4). Operands are evaluated left to right, so user FUNCTION side effects occur in the same order.
  • Same promotion. doexpr's rules are applied at compile time, since types are static:
    • string against number is left to the fallback, which raises the error at the same moment it does today;
    • T_NBR-only operators (/) convert integers to float;
    • T_INT-only operators (\ MOD AND OR XOR << >>) convert floats with FloatToInt64;
    • mixed operands of other operators promote the integer to float;
    • comparisons return integer 0/1.
  • Same code. Each operator body in Operators.c becomes a value-level inline helper: for example the float add with its +INF "Overflow" check, the integer power loop, divide-by-zero, and compare(). The existing op_* functions and the executor both call these helpers.
    • Integer add, subtract, multiply and the bitwise operators are inlined, because their semantics are the machine's.
    • Assignment to an integer uses FloatToInt64; subscripts use FloatToInt32.
    • Numeric literals are parsed once at compile time by getvalue's own parser, factored out (MMBasic.c:3597-3691), including its fast /scale path and fast_strtod. The constants are therefore bit-identical to what the text path computes.
  • Shadow mode (OPTION COMPILE SHADOW). Each compiled LET right-hand side, IF/ELSEIF condition and FOR limit is also evaluated through the text evaluator on the statement's own text, and the two results are compared bit for bit.
    • Expressions that call user FUNCTIONs or RND, TIMER, INKEY$ and the like are marked unshadowable at compile time, because evaluating them twice would change the program.
    • A mismatch stops the program with both values and the line.
    • This is the main test tool from P2 on, and it runs on any program.

Calls

  • For each SUB and FUNCTION, the survey pass decodes its parameter list once: names (as symbols), AS types, BYVAL/BYREF, and array parameters. This is the work DefinedSubFun repeats on every call, splitting both argument lists with makeargs. Phase 1 put that at 21% of a call loop.
  • A compiled call evaluates its arguments, then reproduces DefinedSubFun's effects in the same order (MMBasic.c:2450-2959):
    1. errorstack and gosubstack are pushed (NULL for a FUNCTION).
    2. Variable arguments are passed by reference (T_PTR to the caller's data, with the same type-mismatch demotion to a copy); expressions are passed by value.
    3. g_LocalIndex++, and EnterLocalFrame on SUBPROFILE builds.
    4. Each parameter local is created with its name, through the same creation code findvar uses, so SymLocalMade runs as usual.
    5. CurrentSubFunName is set (STATIC relies on it).
    6. For a FUNCTION, the result variable is created and the body runs nested.
    END SUB, EXIT SUB and the end of a FUNCTION do what cmd_return and the FUNCTION epilogue do.
  • Left to DefinedSubFun as fallbacks: CSUBs, struct parameters, element-addressed array arguments such as a(3) passed as an array, missing arguments, array-returning FUNCTIONs, and CALL/CALL(). The compiled path covers the forms the corpus uses; the census counts them in P3.

Built-ins and the value splice

A built-in function or a graphics command reads its arguments from text: getnumber(ep), or getargs and then getnumber(argv[i]). The value splice gives them values already computed, without changing the handlers:

  • A new token byte, T_VALUE, followed by one index byte, refers to an entry in a small table of values in RAM. The byte comes from 0x08-0x1D, which never occurs in program text because tokenise turns control characters into spaces (MMBasic.c:1411-1416).
  • getvalue learns this one case: it returns the entry and its type.
  • The index byte is drawn from printable characters that none of the byte scanners react to. That excludes " ( ) , ' =, and 0. So makeargs, getclosebracket, skipexpression and skipelement pass a spliced argument through as an ordinary operand.
  • Compiled code evaluates the arguments, fills the table, and writes T_VALUE i , T_VALUE j , … into a temporary buffer.
    • A command's handler is called with cmdline pointing at that buffer.
    • A function's handler (tokentbl[f].fptr) is called with ep pointing at it, and its result is read from fret/iret/sret and targ.
  • This skips the parsing of every argument but runs the handler unchanged. It is exact by construction, because the handler does not know the difference.
  • P5 starts with SIN, COS, TAN, ATN, SQR, ABS, INT, FIX, SGN, EXP, LOG, DEG, RAD and PI, then PIXEL, LINE and BOX. Commands whose handlers compare argument text (checkstring on keywords) keep those keywords as text in the buffer and splice only the numeric arguments.

Where the stream lives

  • Route B is RP2350-only (decision of 27 September). On the RP2040, Stream.c compiles to nothing and OPTION COMPILE is not an option.
  • RP2350 with PSRAM: a region of its own, what the 2 MB PSRAM reserve leaves above the context-save area and the five RAM slots (PSRAMstream, PSRAMstreamsize in configuration.h): 944 KB with HDMIWEB's 144 KB slots, 164 KB at the largest heap. It is written at memory speed and is lost at power-off. It is nobody's slot, so every RAM slot stays the user's; RAM slot 4 was used until Prince of Pico, which fills all five, showed why it could not be.
  • RP2350 without PSRAM: flash slot 2 for now. Slot 3 holds the library, and slot 1 is left for the user. The slot is rewritten only when the program has changed since its last compile, so an edit-and-run cycle costs one erase of the slot, as saving the program already does. While OPTION COMPILE is on, the flash slot commands refuse slot 2. A hidden flash slot of its own comes later (see the decisions).
  • Before any figure is quoted it is confirmed once from a flash slot, because PSRAM and flash timings differ behind the XIP cache.
  • Where the stream lives in a release is deferred until the concept is proven, as you asked. So are the capacity-optimal alternatives (a stream written beside the image at save time, or a single image that LIST decompiles).

Phases and gates

P1plumbing

Records only

Stamp and slot handling, the compiler's survey and emit skeleton, STMT/CMD/SUBCALL records, the map and its cache, the executor's entry and exit, and OPTION COMPILE ON|OFF.

  • Built (core/Stream.c): P1a OPTION COMPILE and the slot guard, P1b the stamp, P1c the records and the map, P1d the executor, with NOP records for comment and label-only lines. MM.INFO(COMPILE) returns OFF, TEXT: why, or COMPILED (NONE once another program has been prepared) followed by compiles, reuses, records and RAN, the statements the last run executed from the stream. Test: Bas/bench/rbstamp.py; stdset.py --compile runs the standard set compiled.
  • Gate status, 27 September 2026 (results in Bas/bench/results/routeB):
    • Behaviour: met. With OPTION COMPILE ON the goldens match on both boards; only printed timings, the PC3's real RTC status (rtcreg) and rtest's dependence on wtest's file differ. The interrupt tests, symchain, cmtloop and every stdset CHECK are unchanged, and the Exile and Elite checks pass compiled. TRACE and ON ERROR SKIP print the same as text.
    • Prince of Pico could not run compiled while the stream sat in RAM slot 4, since it loads its artwork into all five RAM slots. The stream now has a PSRAM region of its own, and PoP passes all 274 checks compiled.
    • RP2040: with the executor in flash the standard set ran 27-62% slower compiled (XIP thrash with findvar), and RAM for it would have cost a 4 KB page of heap. Route B is now RP2350-only.
    • Speed on the PC3, accepted by Peter with the gap left to P2. Three changes took the games from Exile +6.0%, Elite +3.2%, PoP +8.2% to Exile +3.0%, Elite +1.1%, PoP +5.3%, and the solar eclipse anchor from +2.1% to level (15.767 s text, 15.766 s compiled): a bucket index beside the map, so a cache miss costs a bucket read and one or two entries instead of an 11-probe binary search in PSRAM; the executor's position in locals rather than volatile globals, with ON ERROR SKIP's setjmp in a helper's own frame; and lookups that find nothing remembered (a true single-line IF sends nextstmt into its own element). What is left is the round trip to the text loop for the part after THEN and similar, which P2c removes by compiling IF.
    • Placement moves text speed between builds. pixart as text on the VGA: 10.8 s (merge build), 12.9 s (P1 with Route B code), 11.2 s (Route B removed from the RP2040); sombrero on the PC3: 11.3, 12.4 and 13.0 s over three builds. Nothing in the text path changed. Compare OFF and ON on the same firmware only.
  • The only possible gains are the per-statement header walk, the skipelement pre-scan and the token decode, which the records precompute. Expect 0-5%.
  • Gate:

P2numbers

Numeric statements on globals

The expression compiler, the shared helpers and shadow mode; compiled LET, IF/ELSEIF/ELSE, FOR/NEXT, DO/LOOP and EXIT on global numeric scalars.

  • Steps, each built and run on the PC3 before the next:
    1. P2a, the compiled record. A CODE record after STMT carries the statement's binds, its wordcode and the fields of its fallback. The executor binds each variable (SymG through the canonical entry, the type and T_PTR checked, no local of that name live), runs the fallback if any bind fails, and otherwise runs the wordcode: computed goto, 16-bit words, a stack of 64-bit cells, as the G3 VM. First statements: LET g = literal and LET g = g2 for global integer and float scalars. OPTION COMPILE SHADOW evaluates each compiled right-hand side through the text evaluator as well and stops on a difference. Done. A compiled statement is its CMD record with RB_COMPILED and the code after it, so the record is its own fallback. A variable's first two assignments run the fallback (findvar makes it, then binds its symbol when it next finds it). Two assignments in a loop run 1.96x faster compiled; the goldens are clean in SHADOW mode. Test: Bas/bench/rbp2a.py.
    2. P2b, expressions. Operator bodies move out of Operators.c into value-level helpers that op_* and the VM both call; literals go through getvalue's own number parser. Compiled: + - * / \ MOD ^, the comparisons, AND OR XOR NOT, unary minus, brackets, with doexpr's precedence and promotion. Shadow mode on the goldens and the games. Done, without moving code: float and integer + - * run inline with op_add's and op_mul's overflow check, and every other operator calls its own op_ function with the arguments doexpr would give it, so the answers cannot differ; literals are read at compile time by getvalue itself. An expression loop runs 2.96x faster compiled. The games pass in SHADOW mode but compile almost nothing yet: they type their variables by declaration and OPTION DEFAULT, which the next step (the survey) reads. Test: Bas/bench/rbp2b.py.
    3. P2b+, the survey. Done. One walk before the first pass reads every declaration so an unsuffixed name compiles with the program's type: DIM with a type word or AS, a suffix, CONST with a literal; OPTION DEFAULT is followed in text order. A name that is a local anywhere (LOCAL, STATIC, a parameter, a FUNCTION's name, a CONST inside a SUB) is not compiled in P2, since its bind would fail at every run; the first survey, without that, made Exile slower (+4.85%) by compiling statements whose binds always failed. A name with no visible declaration under DEFAULT NONE (Elite's globals are declared in its library) is guessed float and checked. Exile now runs 71,568 statements compiled and is 2.1% behind text (P1: 3.0%); all three games pass in SHADOW mode.
    4. P2c, IF. Multi-line IF/ELSEIF/ELSE/ENDIF through IfTableLookup, and single-line IF with its THEN and ELSE parts compiled inline, which also ends the round trip to the text loop that costs P1 most of its remaining gap. First half done: a multi-line IF whose next arm is ELSE or ENDIF (the false target from IfTableLookup at compile time) and a single-line IF whose THEN and ELSE parts are assignments; false with no ELSE skips the rest of the line as cmd_if's skipline does. An IF-heavy loop runs 3.4x faster; PoP compiles 134,000 statements (was 58,000); goldens and games clean in SHADOW mode. ELSEIF chains and IF ... GOTO stay text. Test: Bas/bench/rbp2c.py. Second half done: records for a single-line IF's THEN part (no ELSE) and ELSE part, marked RB_PART and skipped when running on, so cmd_if's jump into its own element stays in the stream whatever the part is. More now runs from the stream (PoP 2.98M statements, was 2.82M) but the games' gap hardly moved (Exile +2.0%, PoP +5.5%): the round trips were not the cost.
    5. The tail's cadence. Done. A PC-sampled compiled loop spent 39% of its time in CheckAbort and check_interrupt, called after every statement as the text loop does (ProcessWeb 10.5% with WiFi up, routinechecks and its 64-bit timer read, OSK_IsActive). The stream now calls them at once when MMAbort or IntReady says so, and otherwise every 100 us, routinechecks' own cadence; ProcessWeb still polls at least every ms. Interrupt tests unchanged, Ctrl-C stops a compiled loop at once. Compiled loops 3.0-4.8x faster than text; the games are now faster compiled than text (Exile -3.2%, Elite -2.3%, PoP +1.3%).
    6. P2d, loops. FOR/NEXT keeping g_forstack as the text path does, DO/LOOP with g_dostack, EXIT FOR, EXIT DO and CONTINUE. FOR done: cmd_for's stack work and evaluation in its order, its NEXT found at compile time by cmd_for's own scan, now ForFindNext in Commands.c; NEXT, EXIT FOR and CONTINUE stay fallbacks. Binds name variables by symbol id (SymCanonById), one load instead of decoding the symbol's bytes, and from anywhere. K1 of the G3 kernels at program level runs 6.4x faster than text (5658 -> 883 ms), past the gate's 5x. The games are now all at or ahead of text (Exile -3.6%, Elite -2.5%, PoP -0.1%). Test: Bas/bench/rbp2d.py. DO and LOOP done: cmd_do's stack work (the DO fast path left off: the compiled LOOP evaluates the condition, and a fallback LOOP the text) and entry test, its LOOP found by cmd_do's own scan, now DoFindLoop; LOOP finds its entry as cmd_loop does and evaluates the DO's condition (compiled again at the LOOP, binds being by id), its own, or none. K3 (Julia, floats, DO WHILE) 4.38x, short of 5x: binding is 28% of its time and the dispatch switch 18%. The games are now all faster compiled: Exile -4.7%, Elite -3.1%, PoP -1.6%.
    7. The dispatch and the bind cache. Done. The VM dispatches by computed goto through a table in RAM (the switch was 18% of K3), and SHADOW's checks are emitted only when compiling in SHADOW mode. Binding was a quarter of a compiled loop's time. In a stream in PSRAM each compiled record now keeps the addresses its binds found, stamped with SymBindGen, and uses them again while the stamp matches. SymBindGen is bumped by everything that can change what a name binds to: new bindings, every variable gone, one erased, a local made or freed, and a change of OPTION DEFAULT. A live local made from text, which may hide a global, sends the record to its binds. A stream in flash cannot be written, so there every record binds each time. A stream used again has every stamp cleared first. K1 runs 7.76x faster than text (734 ms), K3 6.32x (240 ms). The games compiled against text: Exile -4.3%, Elite -1.5%, PoP +0.7% (inside the 1% noise).
    8. P2e, libraries. LIBRARY SAVE writes symbols, so library names bind like the program's. Done. LIBRARY LOAD saves the library's names as library symbols (0x06 and 0x07), counted over exactly the lines it writes, with a table of their own after the 0xFFFFFFFF marker and ahead of the CSUB and font records. The bindings give library symbols canonical entries after the program's (SymCanonLibBase plus the library's id), shared by spelling, so a name is one variable wherever it is read, and library code binds as the program's does (its locals were text locals before, which stopped global bindings being trusted inside any SUB while one lived). Everything that walks a library image reads the table: the boot check (LibraryImageValid), LIBRARY DISK SAVE's byte count, LIBRARY SAVE (which keeps the old library's symbols and carries its table over; the program it adds is still saved as text), and RAM LIST and FLASH LIST, which now spell a slot's names from the slot's own table. A RAM library saved by older firmware is read again (RAMLIB_MAGIC "RLI2"); a flash library saved by older firmware stays text and runs as before. Compiled records bind library symbols (RC_LIB), and the survey reads the library's declarations as well as the program's. Test: Bas/bench/rbp2e.py (RAM, flash, a restart, LIBRARY SAVE on top, DISK SAVE/DELETE/DISK LOAD, each OFF, ON and SHADOW). Elite, whose kernel is a RAM library, now runs 26,979 statement executions compiled where it ran 4,905, and runs 3.0% faster compiled than as text (was 2.5%); Exile -4.5% and PoP -0.2% are unchanged. Most of Elite's time is in SUBs with locals, which is P3's work. Shadow mode is clean on the goldens and the games.
  • Gate:
    • shadow mode clean on the goldens and the games;
    • the G3 kernels rewritten at program level are at least 5x faster than text on the PC3, which shows the prototype's speed survives in firmware (Route B is RP2350-only).
  • Gate status, 27 September 2026: both met. With OPTION COMPILE SHADOW the PC3's goldens differ from text only in printed timings and the real RTC, with no SHADOW errors, and the three games pass their checks (Exile 18 of 18, Elite's demo, PoP 274 of 274). K1 is 7.76x and K3 6.32x faster than text. P2e (libraries) comes next, before P3.

Decisions (Peter, 26 September 2026)
  1. Compile at RUN when the image has changed, stamped by a CRC of the image: yes.
  2. Stream slots while developing: RAM slot 4 on the PC3 and flash slot 2 on the RP2040, refused to the user while OPTION COMPILE is on: yes.
  3. OPTION COMPILE ON | OFF | SHADOW as a RAM-only development switch, off by default until the P3 gate: yes.
  4. Libraries are compiled too, not left as text. Consequences: the stamp's CRC and the statement map cover the library image as well as the program, so the executor stays in compiled code across a call into the library; LIBRARY SAVE gains symbols (the library table the symbol format already reserves, found through SymTabLib), added in P2 so library names bind like the program's; and library SUBs leave the list of DefinedSubFun fallbacks in P3.
  5. Bugs found while preparing this: all fixed on main (the comment fast path e49d3ff, MAX/MIN 50c9aa0, ABS/SGN 16d0413) and merged into development with V6.04.00RC2 (ac6ca56).
Decisions (Peter, 27 September 2026)
  1. Route B is RP2350-only. The RP2040 has no 4 KB page of RAM below the heap for the executor, and from flash it runs slower than text. Removing Stream.c from the RP2040 build also returned its flash margin (8.4 to 12.4 KB) and RAM margin (212 to 820 bytes).
  2. The stream gets a PSRAM region of its own instead of RAM slot 4: agreed. For boards without PSRAM Peter asked whether a new flash area is the equivalent. It is; it would sit after the program area, cost the A: drive MAX_PROG_SIZE on every RP2350 variant (the layout is fixed at build time, while PSRAM is a run-time option), and reformat A: once on upgrade. Agreed: flash slot 2 for the moment; a hidden flash slot of its own is added later, with the release that makes Route B a user feature.
  3. OPTION LOCAL VARIABLES is reset at RUN, NEW and LOAD (ClearRuntime(true)), not on CHAIN, whose saved variables were placed with the split in force: agreed and done on development (e670e0a); main gets it later.

Found on the way

  • Fixed on development (c8a1d56), open on main: LIBRARY LOAD's "Library too big" check for a flash library could never fire.
    • SaveLibraryImage compared realflashpointer, an offset in flash, with LibMemory, an XIP address, so the difference was always negative.
    • The binary records are bounded when the file is read, but the tokenised text is not, so a library whose text outgrew its slot would be written past the slot's end, into program flash, instead of being refused. It needs about 144 KB of library text, so it is unlikely to happen in practice.
    • On development the check measures from realflashpointer's value when writing starts; main needs the same one-line change.
  • Open, to be tackled later (Peter, 27 September): a reproducible PC3 hard fault after WS2812/BITSTREAM.
    • The goldens' pioout.bas (WS2812 B, O, S and W on gp7, BITSTREAM on gp2, from Integer and Float arrays) faults about 30% of the time just after it ends, at the prompt: 6 in 20 runs with OPTION COMPILE OFF, so not Route B.
    • The fault is in IntToStr (MMBasic.c:6626, LR=10003F2B), reading at 0x20082000, the top of core 0's stack (CFSR 00008200, a precise bus fault), or at PC=2004FF00 with an invalid state: the top of the stack is corrupted.
    • This matches the intermittent PC3 fault seen during uploads on 18 September (a zeroed return address near the stack top while idle), which had no recipe. It points at the WS2812/BITSTREAM PIO and DMA path writing near the top of core 0's stack.
    • Recipe: LOAD another program, LOAD pioout.bas, RUN, watch for FAULT; repeat (scratchpad faultrep.py).
  • Fixed on development, 8740953: a loop whose first line ends in : ' comment ran once.
    • FOR i = 1 TO 3 : ' c ran its body once, and DO : ' d left after one pass. A GOSUB line ending the same way returned past its next line.
    • Cause: the comment fast path in ExecuteProgram skipped to the line after the last T_NEWLINE crossed, but NEXT, LOOP and RETURN come back mid-line.
    • The code is in the repository's first commit, so 6.03.00 onward have it. Without the colon (FOR i = 1 TO 3 ' c) the comment is part of the FOR statement and was never affected.
    • Test: Bas/bench/cmtloop.py (fails before the fix, passes after, on both boards).
  • Fixed on development, 8d3ee25: symbols after CHAIN.
    • This was a bug in the S5/S6 work. CHAIN prepared the new program's bindings in a fresh heap and then restored the old heap over them.
    • Result: DIM z = x * 10 + y printed 0 in the chained program.
    • The bindings are now rebuilt in SaveContext/RestoreContext. Test: Bas/bench/symchain.py, which covers CHAIN and SAVE/LOAD CONTEXT.
  • Not fixed, confirmed on the PC3: MAX and MIN clamp at the single-precision limit.
    • MAX(-1e300, -2e300) gives -3.402823466e+38, and MIN(1e300, 2e300) gives 3.402823466e+38.
    • Cause: fun_max_min starts from -FLT_MAX or +FLT_MAX (Functions.c:1855).
  • Not fixed, confirmed: ABS(1e19) raises "Number too large".
    • fun_abs and fun_sgn evaluate their argument with an integer target, so a float beyond 263 goes through FloatToInt64 (Functions.c:555, 1232).
  • By reading only, not tested:
    • FloatToInt64 lets NaN and exactly 263 through to an undefined C conversion (MMBasic.c:7174-7183).
    • op_subtract has no infinity check, unlike add and multiply.
    • The BYVAL check reads g_vartbl[0] for an expression argument (MMBasic.c:2702-2723).

Route B reproduces each of these exactly, because it calls the same helpers. Fixing one changes both paths at once.
