01

How this was measured

Rather than read for plausibility, I built the keyword inventory the firmware actually has and diffed the manual against it. Three extractions, all repeatable:

  • Token tables per variant. arm-none-eabi-gcc -E run over AllCommands.h and the other table headers with each variant's real macro set from CMakeLists.txt, giving the exact commandtbl[] and tokentbl[] contents for all sixteen builds. Cross-check: HDMIWEB comes out at 126 function tokens plus the NULL entry — 127, the known 7-bit ceiling.
  • Second-level keywords. Every checkstring() literal in the tree (1,832 sites) tagged with its enclosing cmd_/fun_ handler and its live #if stack. This is where OPTION …, MM.INFO(…), panel names and sub-commands live.
  • Manual reference rows. The five reference tables pulled out of the .docx with run-level underline formatting preserved, so the underlined-caps version flags could be read as data rather than prose.

Group tokens — base$(, SChange$(, TopBottom(, ~( — were excluded from the missing-from-manual counts. The manual correctly documents HEX$, LCASE$, MIN, MM.HRES and the rest by their user-facing names.

What is already in good shape. The manual is far more complete than it is accurate; the gaps are concentrated rather than diffuse.

  • Coverage of the command and function tables is essentially total. Six command rows and nine function rows have no matching code token, and every one is explained — shortcut syntax such as *file and A:, or names the tokeniser rewrites into group tokens.
  • Only three OPTION keywords are missing from the Options table, and one of those (OPTION F8) is already covered by the OPTION FNKey row.
  • The GUI Integration chapter's input-device matrix and the HDMIWEB resolution list are both correct against the code, which is evidence that the per-variant approach works when it is actually applied.

Fourteen variant-specific entries carry no flag at all

These read as universally available. E7

OPTION KEYBOARD: two layouts missing, one unavailable

The manual lists US, UK, GR, FR, BR and ES. The PS/2 branch accepts IT and BE as well; the USB and BTH branch accepts only US, FR, GR, IT, UK and ES — so BR is documented but rejected on every USB and Bluetooth-host build. The optional capslock, numlock and repeat arguments are also silently ignored on those builds, where OPTION KEYBOARD REPEAT is the route.

On HDMI and HDMIUSB, OPTION RESOLUTION 1024 means 1024×768. On HDMIWEB it means 1024×600. The manual prints one combined short-form list, so the same command silently does something different depending on the image loaded.

04

The systemic weakness

Every individual error above is cheap to fix. The reason there are errors at all is that variant applicability is carried as free prose rather than as data, so nothing can check it and it drifts silently between releases.

Three measurements make the case:

Reference sectionRowsCarrying a version qualifierVariant-specific in the code
Commands3795131 of 217 command tokens
Functions105512 of 125 function tokens
Options81063 of 157 keywords
— after phase 038643the remaining 43 rows are genuinely universal
Read-only variables37125 — MM.PS2/MM.USB, MM.SUPPLY, the three WEB strings

Where a flag does exist it is written in roughly twenty different ways: VGA VERSION ONLY alongside VGA VERSIONS ONLY; HDMI AND VGA VERSIONS ONLY alongside VGA AND HDMI VERSIONS ONLY; and, for the identical meaning, both NOT VGA OR HDMI VERSIONS and NOT VGA AND HDMI VERSIONS, which read as opposites. Some are underlined runs; some are ordinary sentences such as "RP2350 only" that neither a reader nor a tool can distinguish from body text.

The fix is a closed vocabulary, not more prose. The build system has only nine independent axes — chip, video (none / VGA / HDMI / cut-down HDMI), input (PS/2 / USB host / BLE host), network, Bluetooth, GUI controls, raycaster, structures, and the MIN build. All 36 variant-specific keywords resolve to just 17 distinct availability signatures, listed below. Naming those 17 and tagging each entry with one makes the claim checkable against a generated matrix.

06

The 180 undocumented sub-keywords

These appear nowhere in the manual text. They are not one problem but four, and each needs a different decision before any writing starts.

A

Owned by a companion manual — about 120 tokens

GUI (BARGAUGE, CHECKBOX, LISTBOX, SLIDER, SPINBOX, TEXTBOX, NUMBERBOX, CAPTION, DISPLAYBOX), SPRITE, RAY, FRAME, TILEMAP, TURTLE, 3D, STEPPER (ESTOP, GCODE, HWLIMITS, JERK, SCURVE, SPINDLE), MEMORY SHARE, STRUCT SIZEOF. Decision needed: whether the main manual carries a complete keyword index pointing into the companion PDFs, or whether a reader is expected to know which companion to open. Note that CTRLVAL() and MSGBOX() have no entry in the main reference at all despite being present on 12 of 16 builds.

B

US-spelling aliases — 6 tokens

OPTION DEFAULT COLORS, MM.INFO(FCOLOR), MM.INFO(BCOLOR), TURTLE CURSORCOLOR, FILLCOLOR and the COLOR command. Decision: one sentence stating that US spellings are accepted throughout, rather than six more rows.

C

Diagnostics — 9 tokens

MM.INFO(HEAPEND), STACKPEAK, CHEAPMAX, CHEAPTOTAL, TLSHEAP, TLSHEAPMAX, TLSHEAPERR. Decision: document them as an explicitly unsupported diagnostic set, or leave them undocumented — but say which, once, so it is a choice on record rather than an omission.

D

Genuinely missing user-facing syntax — about 45 tokens

The residue that belongs in the main manual: ST7365P and ST7365PBUFF, OPTION LOCAL KEYBOARD, OPTION PS2 PINS, MM.CODE, COPY A2A|A2B|B2A|B2B, FLASH MODBUFF LOAD, GAMEPAD MONITOR SILENT, Turtle ARECTANGLE and the Turtle one-word aliases.

Two corrections. Several apparent gaps were false positives from matching contiguous strings: the manual writes LOAD[BMP] and ENCRYPT/DECRYPT CBC/ECB/CTR, and C_MULT/CARG are aliases of the documented C_MUL/C_ARG. And the board names (SWEETIEPI, RP2040GEEK, PICORESTOUCHLCD2.8…) are not OPTION PLATFORM values — that takes free text. They are the configurations accepted by OPTION RESET cfg / CONFIGURE cfg, which are already documented and self-describing at runtime via OPTION RESET LIST, so no enumeration is needed or wanted.

07

Plan for the finished manual

Ordered by dependency rather than size. Phases 00–02 change the manual's failure mode; 03–06 are execution against them.

00

Land the checker in the repo

  • Move the four extraction scripts into docs/tools/manual_audit/: docx to text, per-variant token tables via gcc -E, the checkstring scan, and the diff.
  • Emit two artefacts: keyword_matrix.csv (313 keywords × 16 variants) and manual_diff.txt.
  • Add it to the release pre-flight beside the existing .uf2 mtime check.
Why first: every later phase is verified by it, and without it the same drift returns on the next edit.
01

Fix the hard facts

  • E1–E8, G1–G3, S1–S2 above. Bounded, no restructuring, no policy decisions.
  • Re-run the checker; the 15 explained no-token rows and the group tokens are the expected residue.
Ships independently. If nothing else in this plan happens, this phase alone removes every error that puts a syntax error in front of a user.
02

Adopt one applicability notation

  • Name the 17 signatures with short stable labels — for example RP2350 ONLY, NON-VIDEO, VIDEO, USB HOST, WEBMITE, HDMI, GUI CONTROLS, NOT PICOMITEMIN.
  • One rendering only: an underlined small-caps run at the head of the description. Retire "RP2350 only" written as ordinary prose.
  • Resolve the two phrasings that read as opposites by dropping the "NOT … AND …" form entirely.
  • Add a generated appendix carrying the full matrix, so a reader can always resolve a label and the checker has something concrete to compare against.
Output: a one-page style rule in the repo, plus the appendix. Everything after this is mechanical.
03

Tag the Options table

  • Apply a label to each of the 63 variant-specific OPTION keywords. This is the single largest accuracy win available in the document.
  • Split the rows where one entry currently describes two different behaviours: OPTION KEYBOARD (PS/2 against USB and BTH), OPTION CPUSPEED (three ranges), OPTION RESOLUTION (HDMI against cut-down HDMI short forms).
Scope: 63 rows touched, roughly 12 of them split.
04

Take the four sub-keyword decisions

  • Groups A–D in section 06. Only group D is writing; A–C are one-time policy calls that close about 135 tokens at a stroke.
  • The one needing real thought is A: whether GUI, CTRLVAL() and MSGBOX() — present on 12 of 16 builds — belong in the main reference rather than only in Advanced Graphics Functions.
Recommendation: keep the companion manuals, but add a complete keyword index to the main manual in which every keyword resolves either to a page or to a named companion PDF.
05

Rationalise the companion set

  • The manual references nine companion documents; roughly twenty ship. Add a single "Companion manuals" appendix giving title, one line of purpose, and which variants it applies to.
  • Fix the filename mismatches — Raycaster_User_manual.pdf against the actual Raycaster_User_Manual.pdf — and confirm every referenced PDF is genuinely in the release zip.
Why it matters at 6.03.02: the companions are where most of the new capability of the last two releases landed.
06

Final pass and rebuild

  • Version stamps: the worked filename example, the sixteen-file table, the "a sixteen" typo.
  • Review the Obsolete section — it still warns that entries "may be removed in the future to recover memory". For a final release, say whether they are staying.
  • Confirm HDMIBTH remains unshipped and unmentioned.
  • Rebuild the PDF through the proven pipeline: Word COM export, then add_manual_bookmarks.py run from docs/. The old baseline was 283 pages / 39 headings / 533 leaves; Appendices K, L and M add three Heading 1s (38 → 41 in the .docx) and several pages, so expect 42 headings — do not treat that as a regression.
  • Run the phase-00 checker once more and archive its output alongside the release.
Gate: ship only when the checker reports zero unexplained differences.
